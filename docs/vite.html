01

初识 Vite：为什么需要它

用「开餐厅」理解构建工具存在的理由，再看 Vite 凭什么火遍前端圈

写网页不就是写 HTML + CSS + JavaScript 吗？为什么还要一个「构建工具」？这一章不讲任何操作，只回答两个问题：没有它会怎样，以及 Vite 凭什么取代老前辈。

1.1 浏览器的「菜单」其实很挑剔

浏览器是全世界最挑剔的食客：它只认三道原汁原味的菜——HTML、CSS、原生 JavaScript。可现代前端厨房里的食材早就五花八门了：

你实际想用的「食材」浏览器直接吃会怎样
Vue 的 .vue 单文件组件❌ 完全不认识，直接报语法错误
JSX（React 的写法）❌ 同上，浏览器没有这道菜
最新的 JS 语法（在老浏览器上）❌ 老食客咬不动新菜
SCSS / Less（样式预处理语言）❌ 不在菜单上
项目里几百个互相 import 的文件⚠️ 能吃，但端菜速度慢得离谱
没压缩的源码、带注释的大文件⚠️ 用户流量白白多花几倍

于是需要一间中央厨房：把你爱用的食材统一加工成浏览器认的三大件，顺手做优化（压缩、合并、按需加载）和适配（翻译成老浏览器也懂的语法）。这间中央厨房，就叫构建工具（build tool）。

类比构建工具就是餐厅里的后厨加工车间：食客（浏览器）只点「三道经典菜」，但你仓库里堆着全世界的食材（Vue/JSX/SCSS/新语法）——车间负责洗切烹调，把一切翻译成食客能入口的形态端出去。

1.2 旧时代之痛：等满汉全席上齐才开饭

Vite 之前的老构建工具（以 Webpack 为代表）的工作方式是：无论你改哪道菜，都把整桌满汉全席从头重新做一遍——项目一大，开发时的「冷启动」要等十几秒甚至几分钟；你只是把按钮颜色从蓝改成红，也要等整锅重新炖。

1.3 Vite 的身世：Vue 作者的「副业」

2020 年，尤雨溪（Evan You）——框架 Vue.js 的作者——受够了每次改一行代码等半天编译，动手写了 Vite。因为作者身份，Vite 与 Vue 天生一对；但它完全不绑定 Vue：React、Svelte、Solid、原生 JS 项目全都官方支持。如今主流框架的新项目脚手架几乎都默认用它，生态插件数以千计。

名字冷知识Vite 在法语里就是「快」，国际音标 /vit/，中文圈普遍读「维特」。别读成「外特」——虽然大家听得懂，但面试官可能会心一笑。它还有个小彩蛋：官方吉祥物是一台闪电滑板上的咖啡机。

1.4 双模式：白天的餐厅与深夜的中央厨房

Vite 有两种工作模式，对应餐厅的两种营业状态——这是全书最重要的「地图」，后面所有命令都在这张图上：

模式命令类比它做什么
开发模式npm run dev营业中的餐厅：现点现做，追求快和即改即见起一个本地开发服务器，代码改完浏览器瞬间更新（热更新 HMR），不压缩不打包
生产构建npm run build深夜打烊后的中央厨房：批量精加工，追求小和稳把整个项目优化、压缩、打包成几个带指纹的成品文件，放进 dist 目录，随时可部署上线
一句话记住开发用 dev，上线用 build，验收用 preview（第三条命令第 13 章讲）。整个教程 16 章，本质上都在讲怎么把这张表玩明白。

02

地基：Node.js 与 npm

Vite 这台机器的供电与物流系统——装好它们，后面每一步都顺

Vite 本体是个用 JavaScript 写的程序，而「在电脑上直接运行 JS 程序」需要 Node.js。本章把地基打牢：安装、验证、加速，还有三个绕不开的概念。

2.1 三层关系：电、快递、餐厅

类比Node.js 是供电（没电餐厅开不了门），npm 是随电开通的物流系统（全球最大的 JS 软件仓库 + 快递员，收发包裹不要钱）。装好 Node，npm 就自动到岗——它俩是绑定的。

2.2 Windows安装 Node.js

  1. 下载：打开 nodejs.org，选左边绿色的 LTS（长期支持版）——「稳」字当头，Vite 对它支持最好（主力功能版本号是偶数或标 LTS 的那颗）；
  2. 安装：双击 msi 安装包，一路 Next（安装位置、组件全默认即可），最后 Finish；
  3. 验证：新开一个 PowerShell（开始菜单搜 PowerShell），敲下面两条命令。
PowerShell（或 CMD）
node -v                        # 查看 Node 版本号：出现 v22.x.x 之类即安装成功（-v = version）
npm -v                         # 查看 npm 版本号：随 Node 附带，出现 10.x.x 之类即物流系统在岗
多版本需求（可选）以后若要在多个 Node 版本间切换（比如老项目要旧版），Windows 可装 nvm-windows（GitHub 搜 nvm-windows，有图形安装器）。零基础阶段先用官方安装包 + 一个 LTS 版本完全够用。

2.3 Linux安装 Node.js

Ubuntu / Debian 系

apt 路线

终端
sudo apt update                # 刷新软件目录（老规矩：先看价目表）
sudo apt install -y nodejs npm # 安装 Node 与 npm（-y 自动确认）
node -v && npm -v              # 双验证：两个版本号都能打出来即成功

注：部分发行版仓库里的 Node 偏旧，若低于 Vite 要求，用右侧 nvm 路线装新版。

通用

nvm 路线（推荐）

终端
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash   # 下载并运行 nvm 安装脚本（版本号以其 GitHub README 最新为准）
source ~/.bashrc               # 重载配置，让 nvm 命令立刻可用（或重开终端）
nvm install --lts              # 安装最新长期支持版 Node
nvm use --lts                  # 当前终端切换到 LTS 版（node -v 验证）

nvm 是「Node 版本车库」：多版本并存、随手切换——WSL 用户对这套流程应该很眼熟。

版本红线Vite 新版本要求较新的 Node（以你安装时 Vite 官方文档标注为准，大致 18 或 20+）。版本太老会在创建项目时直接报错退出——这是新手第一坑，急救站第 15 章有对照表。装 LTS 版本即可高枕无忧。

2.4 给物流提速：换国内镜像（可选但真香）

双平台通用npm 默认从境外仓库发货，国内网络偶尔「快递龟速」。一行命令把发货仓搬到国内：

终端（PowerShell / CMD / Linux 通用）
npm config set registry https://registry.npmmirror.com   # 把默认仓库地址换成国内镜像（npmmirror，原淘宝源）
npm config get registry        # 查看当前生效的仓库地址：确认已换成功
# 想换回官方源时：
npm config set registry https://registry.npmjs.org      # 恢复默认官方仓库地址

2.5 三个绕不开的概念：清单、仓库、快捷键

名字它是什么类比
package.json项目根目录的小文件：记录项目信息、依赖清单、命令脚本采购清单 + 菜谱封面——用什么食材（依赖）、按什么流程做（脚本）全写在上面
node_modules/所有已下载依赖包真实存放的文件夹，通常几万个文件食材仓库——按清单自动进货并码放整齐；体积巨大，永远不手动改、不上传 Git
scriptspackage.json 里的一段，把长命令起短别名后厨快捷键面板——npm run dev 一按，等于替你敲完整的长命令
文件：package.json（脚手架生成的样子，节选）
{
  "name": "my-app",             // 项目名字（快递单上的寄件人）
  "private": true,              // 私有项目：npm 拒绝误发布到公共仓库（保险栓）
  "version": "0.0.0",           // 版本号（还没上线，零蛋起步）
  "type": "module",             // 声明本项目用 ES 模块规范（import/export 那一套）
  "scripts": {                  // 「快捷键面板」：左边是别名，右边是真实命令
    "dev": "vite",              // npm run dev = 启动开发服务器（营业！）
    "build": "vite build",      // npm run build = 生产构建（打烊精加工）
    "preview": "vite preview"   // npm run preview = 本地预览构建产物（出餐前试吃）
  },
  "devDependencies": {          // 开发期依赖清单：只在后厨用、不给食客的「厨具」
    "vite": "^5.4.8"            // Vite 本体；^ 表示「允许 5.x 内的小版本升级」
  }
}

03

十秒创建第一个项目

npm create vite 一条命令开店——含「免提问直出」与三步点火流程

地基打好，开张只需一条命令。双平台通用（Windows 用 PowerShell，Linux 用终端，命令一字不差）。

3.1 交互式开店：一问一答

终端（先 cd 到你想放项目的目录）
npm create vite@latest        # 官方脚手架：拉取 create-vite 问你几个问题后生成项目骨架
                              # @latest = 用最新版脚手架（create 后面跟的就是「开店向导」这个小程序）
? Project name: › vite-project        ← 问题 1：项目叫什么（敲 my-app 回车）
? Select a framework: › - Vanilla     ← 问题 2：用什么框架（方向键选择）
  Vanilla / Vue / React / Preact / Svelte / Solid / Lit / Others
? Select a variant: › JavaScript     ← 问题 3：要不要 TypeScript（零基础先选 JavaScript）

Scaffolding project in ...\my-app...  ← 正在生成骨架
Done. Now run:                        ← 生成完毕，它把「点火三步」也告诉你了：
  cd my-app
  npm install
  npm run dev
类比npm create vite 像商场里的开店向导机：投一句命令，它问三个问题（店名、菜系、用不用新式厨具），然后「啪」地吐出一间精装修到能直接营业的空店铺——招牌、后厨、电路全接好，你只管往里填菜。
本教程的选择问题 2 选 Vanilla（香草 = 纯原生 JS）、问题 3 选 JavaScript——没有框架干扰，最适合零基础看清 Vite 本身。第 11 章再用同样一条命令开 Vue / React 分店，流程完全一致。

3.2 免提问直出：--template 一条龙

已知要什么时，可以跳过问答，把答案直接写进命令（注意 npm 的传参要两个横线 -- 打头）：

终端
npm create vite@latest my-app -- --template vanilla   # 店名 my-app + 纯 JS 模板，一步直出不再提问
npm create vite@latest vue-app -- --template vue       # 开一家 Vue 分店（.vue 单文件组件版）
npm create vite@latest react-app -- --template react   # 开一家 React 分店（JSX 版）
两个横线别丢npm 用 -- 把后面的参数原样转交给脚手架程序。少了它，Windows 的 PowerShell/CMD 会把 --template 当成 npm 自己的参数而报错——「命令不对劲」时先检查这个。

3.3 点火三步：进店、进货、开业

终端
cd my-app                     # 第一步：走进新店铺（所有后续命令都在项目目录里敲）
npm install                    # 第二步：按 package.json 清单进货（生成 node_modules 仓库；首次约几十秒）
npm run dev                    # 第三步：点火开业！开发服务器启动，浏览器即将有货可看
added 36 packages in 12s                    ← 进货完成（包的数量因版本而异）

  VITE v5.4.8  ready in 381 ms               ← 开业成功：381 毫秒就绪（这就是「闪电」）

  ➜  Local:   http://localhost:5173/         ← 本机访问地址：按住 Ctrl 单击（终端里）或复制到浏览器
  ➜  Network: use --host to expose           ← 想让同 WiFi 的手机/别的电脑访问？见第 5 章 --host
  ➜  press h + enter to show help            ← 按 h 回车可查看内置帮助（按 q 断开返回终端提示）

04

项目结构逐房间参观

每个文件和文件夹是餐厅里的哪个房间——先认门牌，后面才不迷路

脚手架生成的文件不多，但每个都身居要职。本章带你逐房间走一遍——之后所有章节的操作，你都能立刻定位「发生在哪个房间」。

终端 · 看看店铺全景
cd my-app                     # （如果还没进去）走进项目
ls -l                          # Linux / macOS / Git Bash：列出文件详情（Windows CMD 用 dir）
# 想连隐藏文件一起看：ls -a（.gitignore 是隐藏文件）
index.html          ← 大门：浏览器打开项目的唯一入口（在根目录！）
package.json        ← 采购清单 + 快捷键面板（第 2 章讲过）
vite.config.js      ← 后厨设置面板（第 8 章专门伺候它）

public/             ← 免加工直达货架（原样拷贝的静态文件）

4.1 index.html：餐厅大门（注意：在根目录！）

文件：index.html（骨架原文）
<!doctype html>                        <!-- HTML5 文档声明：告诉浏览器「用现代模式读我」 -->
<html lang="en">                         <!-- 网页根元素；lang 建议改成 zh-CN（中文站） -->
  <head>                                  <!-- 「头部」：给浏览器和搜索引擎看的元信息 -->
    <meta charset="UTF-8" />              <!-- 字符编码：UTF-8 才能正确显示中文 -->
    <link rel="icon" type="image/svg+xml" href="/vite.svg" />   <!-- 网站小图标：指向 public 里的 vite.svg -->
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />   <!-- 移动端适配：宽度随设备、初始不缩放 -->
    <title>Vite App</title>               <!-- 浏览器标签页上的标题，改成你的项目名 -->
  </head>
  <body>                                 <!-- 「身体」：真正显示给用户的内容 -->
    <div id="app"></div>                  <!-- 挂载点：一个空盘子，JS 会把整个应用端上来摆在这里 -->
    <script type="module" src="/src/main.js"></script>   <!-- 点火开关：以 ES 模块方式加载后厨主入口 -->
  </body>
</html>
和直觉最大的不同老工具的入口藏在构建产物深处；Vite 的 index.html 就光明正大躺在项目根目录——开发时它就是真实入口（开发服务器直接伺候这个文件），构建时它也是打包起点。改标题、加字体、调 favicon，直接编辑它。

  const setCounter = (count) => {  // 定义一个内部小函数：负责把数字写到按钮上（箭头函数写法）
    counter = count                // 记住最新数字
    element.innerHTML = `count is ${counter}`   // 把「count is N」写进按钮文字
  }
  element.addEventListener('click', () => setCounter(counter + 1))   // 每次点击：数字加一并刷新显示
  setCounter(0)                    // 初始化：页面一打开就先显示 count is 0
}

export { setupCounter }            // 把函数「挂牌」导出：别的文件才能 import 它（main.js 正是这么干的）
类比main.js 是主厨点火：一开场就摆盘（innerHTML）、挂菜（setupCounter）；counter.js 是独立档口：自己写好自己的手艺，挂上 export 招牌等主厨来点。这就是「ES 模块」——每个文件一间档口，import 点菜、export 挂牌。

4.3 public/ 与 vite.config.js：货架与设置面板

房间作用怎么被处理
public/放「不需要加工」的静态文件：favicon、robots.txt、大图等开发时原样伺服、构建时原样拷贝进 dist 根部；引用时写绝对路径 /vite.svg（第 7 章对比 assets）

node_modules/依赖包仓库npm 全权管理；删了可以用 npm install 重新进货
dist/（暂不存在）出餐打包区只有执行 npm run build 才会生成（第 13 章揭开面纱）

启动与热更新 HMR

开发服务器全解读：秒开、热更新、错误蒙层、局域网访问、换端口

开发模式是 Vite 的招牌。本章把 npm run dev 的每个细节讲透——包括那只「改完即见」的魔法之手到底怎么运作。

5.1 再看一眼启动横幅：每个字都有含义

终端
npm run dev                   # 启动开发服务器（= 执行 package.json 里 "dev": "vite" 这条快捷键）
  VITE v5.4.8  ready in 381 ms   ← 版本 + 就绪耗时：冷启动毫秒级（对比老工具动辄十几秒）
  ➜  Local:   http://localhost:5173/   ← 本机门牌：localhost = "本机自己"，5173 是 Vite 默认端口号
  ➜  Network: use --host to expose    ← 提示：想开放给同网络的设备访问，加 --host（见 5.4）
  ➜  press h + enter to show help     ← 服务器运行中按 h 回车：查看快捷指令（v 重启 / q 停止等）
类比localhost:5173 是你餐厅的内部门牌：localhost = 「本机」，5173 = 门牌号。这台「营业中的服务器」不止吐页面——你保存的每一份代码，它都即刻现做成浏览器能吃的形态递过去，这才是「开发服务器」的真身。

5.2 热更新 HMR：只换那盘菜，不动整桌

HMR（Hot Module Replacement，热模块替换）是 Vite 的成名绝技：改代码保存的一瞬间，浏览器不刷新整页、不丢当前状态，只把改动涉及的那「一盘菜」原位换新。

亲手做个实验，体会「状态不丢」有多爽：

操作 · 在浏览器里做实验
# ① 打开 http://localhost:5173 ，把 count 按钮点到 7        ← 制造一个「页面状态」
# ② 回编辑器打开 src/style.css，把 :hover 的颜色改成红色，保存
#    → 鼠标悬停按钮立刻变红；再看 count ——还是 7，纹丝不动！
# ③ 打开 src/counter.js，把 'count is' 改成 '已点击'，保存
#    → 按钮文字立即换新；这个模块更新了，整页仍没有刷新
# ④ 结论：样式/组件级改动走热替换；某些影响面大的改动（如改 main.js 入口）会整页刷新——属正常行为

5.3 错误蒙层：出餐口的质检报警器

代码写错了（语法错误、找不到模块）会怎样？Vite 不会让问题溜到控制台里让你翻找——它直接在页面上盖一层红色大蒙层：报错文件、行号、原因一目了然。改好保存，蒙层自动消失、页面自动恢复。

类比红色蒙层是出餐口上方的质检报警灯：菜品有问题（代码报错），整条传送带亮红灯暂停出餐——但后厨（你的编辑器）不受影响，改好那一刻灯灭复产。报错信息本身就是线索：先看第一行和行号，九成问题当场解决。

5.4 进阶驾驶术：换端口、局域网开放、CLI 直传参数

终端
npm run dev -- --host         # 开放局域网：启动后 Network 行给出 192.168.x.x 地址
                              # 同一 WiFi 下的手机/平板/同事电脑都能访问你的开发页（真机调试神器）
npm run dev -- --port 3000    # 换门牌：把默认的 5173 换成 3000（5173 被占用时的急救法之一）
npm run dev -- --open         # 自动帮你打开默认浏览器并直达页面（懒人福音）
npm run dev -- --host --port 8080   # 参数可叠加：开放局域网 + 指定端口
又是两个横线CLI 参数要经由 npm 转交给 Vite，所以同样要 -- 打头：npm run dev -- --host。如果你直接运行 vite --host（不经 npm，见第 16 章的 npx 说明）则不需要。

工作原理：为什么这么快

两条流水线的秘密：白天的「按需现做」与备菜间的「净菜预处理」

不深挖源码，只用厨房比喻把 Vite 的速度讲明白——理解这一章，你对 Vite 的所有「怪行为」（如依赖缓存、--force）都会豁然开朗。

6.1 白天：原生 ESM 按需现做

现代浏览器其实原生支持 ES 模块（import/export 那套语法）。Vite 开发模式的聪明之处就在于：干脆不打包——你写的每个模块，浏览器请求到哪个，服务器现场加工哪个、原样递过去：

类比旧工具是「不管你点不点，先把全菜单做好」；Vite 是「菜单先摆上桌（index.html 原样伺服），点哪道现做哪道」——页面打开只加载当前用到的模块，没点的菜一个字节都不浪费。项目越大，这份「懒」省得越多。

6.2 备菜间：依赖预打包（esbuild）

有个例外：你 npm install 的大量第三方依赖（如 vue、react）通常是 CommonJS 老格式、且内部几百个小文件。浏览器按需现做时「现切几百刀」就太慢了——所以 Vite 在首次启动时用超快的 esbuild 把它们一次性预处理成「净菜」：

终端
npm install lodash             # 示例：装一个常用工具库（之后 import 才有得吃）
npm run dev                    # 启动：首次会看到 "new dependencies optimized: lodash"
                              # ← 这就是「净菜预处理」：esbuild 把 lodash 转成单文件 ESM 净菜
# 净菜被缓存进 node_modules/.vite/ 文件夹：
#   下次启动直接取缓存，秒起；只有「依赖变了」或「缓存失效」才重新预处理
类比这就是法餐里的 mise en place（开档备菜）：葱姜蒜提前洗好切好装盒（依赖预打包），客人点单时主厨随手抓取（浏览器 import）——「现做」依然快如闪电的底气全在备菜间。esbuild 是用 Go 语言写的切菜机器人，比传统 JS 工具快一个数量级。

6.3 缓存与急救：--force 重备菜

终端
npm run dev -- --force        # 强制丢弃预打包缓存、重新备菜（一切从零切起）
                              # 使用场景：依赖更新后行为诡异、缓存疑似损坏、排障时「先重启再说」的进阶版
排查心法遇到「明明改了却不生效」的玄学问题，按顺序三板斧：硬刷新浏览器（Ctrl+F5）→ 重启 dev 服务器（Ctrl+C 后再 dev）→ --force 重备菜。九成玄学止步于第二斧。

07

样式与静态资源

CSS 导入、Sass、CSS Modules、图片处理——assets 与 public 的关键区别

Vite 把「样式」和「图片」也当模块对待：都能 import、都会被优化。本章讲清四件事：全局样式、预处理器、防串味的 CSS Modules、两个资源文件夹的分野。

7.1 在 JS 里导入 CSS

文件：src/main.js（相关行）
import './style.css'          // 一行导入全局样式：Vite 负责把它注入页面 <head> 里
                              // 开发时即时生效（改颜色保存立即变，走 HMR）；构建时抽取成独立 .css 文件
// 想拆细点也随意：建 src/base.css，再在 main.js 里 import './base.css' —— 全凭口味
类比CSS 文件像餐厅的整体装修方案：在入口（main.js）登记一次，全店生效。老时代要在 HTML 里手写 <link> 标签、还要操心顺序——现在谁 import、什么顺序，JS 里一目了然。

7.2 升级装备：Sass（嵌套写法）

原生 CSS 不能「嵌套」写选择器，写多了容易「起火」。装上 Sass 就能享受嵌套、变量等进阶语法——Vite 零配置支持，只要装包：

终端
npm install -D sass           # 安装 Sass 编译器（-D = devDependency：只给后厨用的「厨具」，不进成品）
文件：src/style.scss（新建后把 main.js 的导入改成它）
$主色: #7c3aed;               // 定义变量：$ 开头；一处定义处处使用（换主题只改这里）
.card {                        // 外层：卡片容器
  border-radius: 12px;         // 嵌套写在里面——自动编译成 .card { border-radius: 12px }
  button {                     // 嵌套：相当于 .card button，不用重复写前缀
    color: $主色;              // 使用变量：颜色统一管理
    &:hover {                  // & 指代父级自身：相当于 .card button:hover
      scale: 1.05;             // 悬停放大一点点
    }
  }
}
// 保存即编译即生效——Vite 全程自动，不需要任何配置
同理可得Less（装 less）、Stylus（装 stylus）也一样：装了对应包，.less / .styl 文件直接 import 即用。Vite 的哲学：「文件后缀即协议」——后缀对上就自动处理。

7.3 防串味神器：CSS Modules

多人协作时最怕「类名撞车」：你写 .title，我也写 .title，样式互相污染。命名文件为 xxx.module.css，Vite 自动开启「防串味」：

文件：src/card.module.css（新建）
.title {                      // 看似普通的类名……
  font-size: 20px;            // 但它只属于「导入它的那个文件」
}
文件：src/main.js（使用方式）
import styles from './card.module.css'   // 注意：带返回值地导入——得到一个「类名对照表」
// styles.title 的真实值类似 "_title_1a2b3"：Vite 自动加了独一无二的指纹前缀！
document.querySelector('#app').innerHTML = `
  <h1 class="${styles.title}">我不怕撞名</h1>   <!-- 用对照表里的真实类名，别人写的 .title 管不着我 -->
`
类比CSS Modules = 同姓客人挂牌制：两个都叫「.title」的客人进店，系统自动给他们挂上「.title_1a2b」「.title_3c4d」的号码牌——同名不同人，永不串味。构建后还会进一步哈希混淆，天然防冲突。

7.4 图片与两个文件夹的分野：assets vs public

对比项src/assets/（加工区）public/(直达货架)
怎么引用在 JS/CSS 里 import（或相对路径）写绝对路径，如 /logo.png
被处理吗✅ 参与优化：小图变 data 内联、名字加指纹、可被压缩❌ 原样伺服、原样拷贝，一个字节不动
名字会变吗构建后变 logo.a1b2c3.png（指纹防缓存）永远叫 logo.png
适合放和代码强相关的图：组件图标、会被替换的素材 favicon、robots.txt、约定俗成固定路径的文件
文件：src/main.js（两种引用方式对照）
import logoUrl from './assets/logo.png'    // 方式一（推荐）：import 得到「加工后的地址」
// 构建时 Vite 自动完成：小图转成 data: 内联（省一次请求）、大图改名加指纹、并写进产物
// 方式二：public 里的文件不 import，直接写绝对路径：
//   <img src="/vite.svg">    ← 引用的是 public/vite.svg，开发与构建都原样可用
选择口诀「要优化、跟代码走」放 assets；「要稳定、固定地址」放 public。拿不准就放 assets——优化的便宜不占白不占。

vite.config.js：设置面板

一台咖啡机的设置屏：端口、自动开浏览器、路径别名、插件插槽

想改默认行为（端口 5173 太顺手被占？想 @ 代替 src 长路径？），都在这个文件里说。它是唯一的设置面板——改完记得重启 dev 服务器。

8.1 最小可用面板

文件：vite.config.js（骨架自带，几乎是空的）
import { defineConfig } from 'vite'   // 导入「带提示的包装函数」：写配置时编辑器会自动补全提示

export default defineConfig({         // 把配置对象包一层导出——Vite 启动时会来读取它
  // 这里就是面板本体：下面所有小节都往这个对象里添东西
})
类比defineConfig 像设置面板的防呆边框：内容不填错位置、按键按错名字都会被编辑器当场标红（TS 提示）。空面板 = 全部用出厂默认值——Vite 的默认值已经调得极好，没有需求就别加配置。

8.2 server 小节：营业参数

文件：vite.config.js（常用配置逐行注释）
import { defineConfig } from 'vite'    // 依旧先导入包装函数

export default defineConfig({
  server: {                           // 「营业参数」小节：开发服务器的行为
    port: 3000,                       // 固定门牌号：默认 5173，改成 3000（被占时的根治法）
    open: true,                       // 启动后自动打开默认浏览器并直达页面
    host: true,                       // 等价于命令行 --host：开放给局域网设备访问
    // proxy: { ... }                 // 后端联调代理（第 10 章专门讲，此处先留个念想）
  },
})

8.3 resolve.alias：给长地址起简称

文件：vite.config.js（续）
import { defineConfig } from 'vite'
import { fileURLToPath, URL } from 'node:url'   // Node 自带工具：用来把「文件网址」翻译成「磁盘路径」

export default defineConfig({
  resolve: {                          // 「路径解析」小节
    alias: {                          // 别名表：左边是简称，右边是真实地址
      '@': fileURLToPath(new URL('./src', import.meta.url)),  // @ = 项目里的 src 文件夹
    },
  },
})
// 效果：以前 import x from '../../assets/logo.png'（跨三层目录的相对路径地狱）
// 现在 import x from '@/assets/logo.png'（永远从 src 出发的绝对感觉，搬文件不用改路径）
类比alias 是给仓库货架贴楼层导览牌：「@ = 三楼 src」。写地址时不用再数「上两层左转」，一句「去 @ 的 assets 区」直达——文件搬家、目录重构时，引用一行都不用改。

8.4 plugins 插槽与 base 出厂铭牌

文件：vite.config.js（续）
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'   // 示例：Vue 官方插件（第 11、12 章详讲；纯 JS 项目不需要）

export default defineConfig({
  plugins: [vue()],                   // 「电器插槽」：想加功能就往数组里插一个插件
  base: '/my-app/',                   // 成品挂载的「子目录铭牌」：部署到 https://xx.com/my-app/ 时必配
                                     // 不配（默认 '/'）+ 部署到子目录 = 线上白屏（第 15 章急救站常见案）
})
重启提醒vite.config.js 在启动时读一次。改了它却不生效？先 Ctrl+C 停掉再 npm run dev——「改配置不重启」是新手玄学问题的第一大来源。

  3. 体会一遍「改配置 → 不重启 → 不生效 → 重启 → 生效」的完整流程，形成肌肉记忆。

环境变量与模式

开发用测试服、上线用正式服——把「随环境变化」的信息贴在冰箱便签上

同一个项目，开发时连测试接口、上线后连正式接口——这类「随场合变化的配置」不该写死在代码里。Vite 的答案是：几张贴在冰箱上的便签（.env 文件）。

9.1 三张便签：默认、开发、生产

项目根目录新建三个文件
# 文件 1：.env                  —— 通用便签：任何模式都会读
VITE_API_URL = https://default.example.com   # 变量名必须 VITE_ 开头（规则见下节）
VITE_APP_NAME = 我的外卖店                    # 顺手放个店名：页面标题、页脚都能用

# 文件 2：.env.development     —— 开发便签：只在 npm run dev 时叠加生效
VITE_API_URL = http://localhost:3000         # 开发时后端跑在本地 3000（联调见第 10 章）

# 文件 3：.env.production      —— 生产便签：只在 npm run build 时叠加生效
VITE_API_URL = https://api.myshop.com        # 上线后的正式接口地址
类比三张便签都贴在同一台冰箱上：先读通用便签，再按「今天开哪种店」叠读对应那张——同名的以后读的为准（专属便签覆盖通用便签）。dev 读「开发」、build 读「生产」，切换全自动，代码一行不改。

9.2 前缀规则：为什么必须叫 VITE_xxx

出于安全，Vite 只把 VITE_ 开头的变量递交给前端代码——别的（比如没加前缀的 SECRET_KEY）一律留在 Node 侧、不进浏览器。这防止你不小心把密钥打包给全世界看。

文件：src/main.js（读取便签）
console.log(import.meta.env.VITE_API_URL)   // 在代码里读便签：import.meta.env 是 Vite 注入的「环境变量包」
console.log(import.meta.env.VITE_APP_NAME)  // 同理读取店名
console.log(import.meta.env.DEV)            // 内置布尔值：当前是否开发模式（true/false）
console.log(import.meta.env.PROD)            // 内置布尔值：当前是否生产模式（与 DEV 互补）

代理：与后端联调

浏览器的小区门禁（同源策略）与前台转接员（server.proxy）

前后端分家开发时，网页在 5173、接口在 3000——浏览器会以「跨域」为由拦下请求。Vite 的代理功能让你在开发期优雅绕过它，一行后端代码都不用改。

10.1 先懂规矩：同源策略

类比浏览器有个铁规矩叫同源策略：只允许「同一家公司」（协议 + 域名 + 端口全相同）的 JS 互取数据——像小区门禁：5173 栋的住户（你的页面）不能直接闯 3000 栋（后端）拿东西。这是防坏人的安全设计，但开发时也把自家同事拦在门外了。

生产环境通常由后端/网关配置 CORS（给浏览器「发通行证」）解决。但开发期最优雅的办法，是让 Vite 自己当前台转接员：

10.2 配置示范：五分钟接入真实后端

文件：vite.config.js（proxy 小节）
import { defineConfig } from 'vite'     // 老朋友：配置包装函数

export default defineConfig({
  server: {                            // 营业参数小节（第 8 章的老房间）
    proxy: {                           // 「前台转接规则」表：左边是拦截前缀，右边是转交目标
      '/api': {                        // 规则一：凡是以 /api 开头的请求……
        target: 'http://localhost:3000',   // ……都转交给本机 3000 端口的后端
        changeOrigin: true,            // 转交时把请求的「来源」改写成目标服务器自己（很多后端的鉴权需要）
        rewrite: (path) => path.replace(/^\/api/, ''),  // 改写路径：把开头的 /api 削掉再转交
        // ↑ 场景：前端写 /api/users，后端实际路由是 /users —— 削掉前缀刚好对上
      },
    },
  },
})
文件：src/main.js（前端这样请求）
fetch('/api/users')                  // 页面里只写「自家门牌」的相对路径：/api/users
  .then(res => res.json())            // 把响应翻译成 JSON（fetch 的固定套路）
  .then(data => console.log(data))     // 拿到后端真实数据！全程无跨域报错
// 实际链路：/api/users → Vite 削成 /users → 转给 localhost:3000 → 响应原路带回页面
注意改 proxy 配置要重启 dev 服务器（老规矩）。另外代理只服务开发期；上线后的跨域由部署架构（同域部署 / 网关 / 后端 CORS）解决——两套阶段，两套方案，别混。
动手练习 07
  1. 配一条 /api 代理指向 http://localhost:3000；
  2. 没有后端？用第 9 章便签里的 jsonplaceholder.typicode.com 当假后端，代理 target 填它、把 rewrite 削掉 /api，页面里 fetch /api/users 试试真数据。

框架实战：Vue 与 React

前十章的招式（dev/build、配置、样式、代理）对任何框架都原样有效。本章用同样的命令开两家「框架分店」，看看 Vite 与它们怎么配合。

11.1 开一家 Vue 分店

终端

cd vue-app                     # 进店

npm run dev                    # 开业：浏览器看到 Vue + Vite 的欢迎页

看懂 Vue 的招牌菜：单文件组件（.vue）

文件：vue-app/src/App.vue（改造的计数器示例）
<script setup>                  <!-- 「逻辑区」：setup 是 Vue3 的组合式 API 写法，代码更少 -->
import { ref } from 'vue'       // 从 Vue 借来 ref：把普通数字变成「响应式」的——它一变，页面自动跟着变
const count = ref(0)            // 声明响应式计数器，初始 0；JS 里要用 count.value 读写
function add() {                // 定义点击回调
  count.value++                 // 响应式数据 +1 ——页面上的数字自动刷新，无需操作 DOM！
}
</script>

<template>                      <!-- 「摆盘区」：长得像 HTML，里面的 {{ }} 会填入实时数据 -->
  <h1>Vue 分店：count is {{ count }}</h1>   <!-- 双花括号插值：count 一变这里立即变 -->
  <button @click="add">加一</button>            <!-- @click 绑定点击事件到 add 函数 -->
</template>

<style scoped>                  <!-- 「装修区」：scoped = 样式只作用于本组件（自带防串味） -->
button { padding: 8px 16px; }   /* 本组件的按钮样式，别的组件的按钮管不着 */
</style>
类比一个 .vue 文件 = 一间独立档口：逻辑（script）、摆盘（template）、装修（style）三位一体，全写在一张纸上。Vite 的 Vue 插件负责把这张「三段式菜谱」现切成浏览器认识的三道菜——保存的瞬间只重做这一间档口（HMR 精准到组件级）。

11.2 开一家 React 分店

终端

npm install                    # 进货
npm run dev                    # 开业：React + Vite 欢迎页
文件：react-app/src/App.jsx（改造的计数器示例）
import { useState } from 'react'   // 从 React 借 useState 钩子：给函数组件装上「记忆」（状态）
function App() {                    // 每个组件就是一个函数，返回要显示的内容
  const [count, setCount] = useState(0)   // 解构出「当前值 + 专用修改器」，初始 0
  return (                          // 返回 JSX：长得像 HTML 的 JS 扩展语法
    <div>
      <h1>React 分店：count is {count}</h1>   {/* 单花括号填入实时数据（JSX 用 {}，不是 {{}}） */}
      <button onClick={() => setCount(count + 1)}>加一</button>   {/* 点击调用专用修改器，页面自动刷新 */}
    </div>
  )
}
export default App                 // 挂牌导出：main.jsx 里 import App 用的就是它
Fast RefreshReact 模板里的热更新叫 Fast Refresh：改组件保存，连组件里的 state 都尽量保留——你把弹窗开着改样式，弹窗不会啪地消失。这是 Vite + React 日常开发的隐形福利。

插件生态

给咖啡机装扩展配件——四个最常用的官方/明星插件

Vite 的本事可以无限扩展：兼容老浏览器、自动导入 API、按需引入组件库……全都靠往 plugins: [] 数组里「插电器」。

12.1 插件是什么：面板上的电器插槽

类比Vite 是一台标准的商用咖啡机，正面留了一排插槽（plugins 数组）：磨豆机、奶泡机、糖浆泵……每个插件是一台「即插即用的电器」，插上就多一种饮品能力。你在第 11 章其实早就见过它——Vue/React 模板的 vite.config.js 里躺着 plugins: [vue()]，那正是让 .vue / JSX 被看懂的标配电器。
文件：vite.config.js（插槽的标准用法）
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'       // 第一步：import 插件本体（先 npm install 它）

export default defineConfig({
  plugins: [                              // 第二步：插进插槽（数组可以插多台，顺序有讲究的按文档来）
    vue(),                                 // Vue 电器：让 .vue 文件被正确编译
  ],
})

12.2 四台最值得认识的电器

插件它干嘛类比
@vitejs/plugin-vue / plugin-react让 .vue / JSX 被编译（模板自带）标配磨豆机——没有它，框架菜谱读不了
@vitejs/plugin-legacy构建时生成「老浏览器兼容包」老年食客套餐：同一道菜做成软烂版
unplugin-auto-import省掉手写 import { ref } from 'vue' 这类样板自动补货机械臂：常用食材自动上灶台
vite-plugin-compression构建时生成 .gz 预压缩文件真空包装机：出货体积更小、运输更快

进阶：分包与懒加载

按需上菜的艺术：路由级懒加载、手动分包、多页应用

项目变大后，「所有代码装一个箱子」会让首屏背着全店的重量。本章三招让浏览器「先吃到凉菜，硬菜慢慢炖」。

14.1 懒加载：import() 动态上菜

普通 import 是「点菜时全店备货」；而动态 import() 返回一个 Promise——菜在客人真的点的时候才下锅，Vite 自动把它切成独立的小包裹（chunk）：

文件：src/main.js（对比两种导入）
import { setupCounter } from './counter.js'   // 静态导入：构建时必然进「主包裹」，页面一打开就加载
// ↓ 动态导入：构建时切成独立小包裹，下面这行执行的那一刻才去下载
import('./counter.js')                        // 调用返回 Promise（一个「稍后送达」的承诺）
  .then(module => {                           // 包裹送达（module 就是那个文件的全部导出）
    module.setupCounter(document.querySelector('#counter'))   // 这时才挂上计数器
  })
// 实战最常见的用法是「路由级懒加载」：访问哪个页面，才下载哪个页面的包裹
// （Vue Router / React Router 里的写法长得就是这样：component: () => import('./views/About.vue')）
类比静态 import 是婚宴全席提前备好；动态 import() 是零点菜单：客人翻到「关于页」那一页，后厨才开火——没点过的页一个字节都不下载。首屏速度立竿见影。

14.2 手动分包：把「万年不变的」单独装箱

业务代码天天改（指纹天天变），而 vue/react 这类依赖几乎不动——分开装箱，用户就几乎永远命中缓存：

文件：vite.config.js（build.rollupOptions）
export default defineConfig({
  build: {                                   // 「深夜厨房」小节：构建行为参数
    rollupOptions: {                         // 透传给打包内核 Rollup 的选项
      output: {                              // 产物相关设置
        manualChunks: {                      // 手动分箱表：左边是箱子名，右边是「装进去的东西」
          vendor: ['vue'],                   // 名为 vendor（供应商）的箱子：装框架这类万年不变的重物
        },
      },
    },
  },
})
// 效果：dist 里多出一个独立 vendor-xxxx.js —— 业务改动重新发版时，它的指纹不变、用户缓存命中

14.3 多页应用：不止一扇大门

文件：vite.config.js（MPA 配置示意）
import { defineConfig } from 'vite'
import { resolve } from 'node:path'          // Node 的路径工具：拼接出各入口的磁盘地址

export default defineConfig({
  build: {
    rollupOptions: {
      input: {                               // 多入口 = 多扇大门：每个入口各出一套成品
        main: resolve(__dirname, 'index.html'),       // 大门一：主页（默认就有）
        about: resolve(__dirname, 'about/index.html'),// 大门二：关于页（按需访问 about.html）
      },
    },
  },
})
// 场景：传统企业站、活动页合集——每个页面独立 HTML，互不依赖；访问时才加载对应包裹
节奏建议零基础阶段先不碰本章配置——Vite 默认已经做了合理的自动分包（动态 import 自动切块）。等项目明显变大、首屏变慢了，再回来按需取用。提前优化是万恶之源。

创建项目时报 Node 版本不满足
engine / not supported		 Node 太老，Vite 不伺候 node -v 对照 Vite 官方文档的版本要求；去 nodejs.org 装 LTS 版（Linux 用 nvm，第 2 章）
npm install 卡住不动 / 龟速 默认境外仓库发货慢 换国内镜像（第 2 章 2.4）；仍卡则 Ctrl+C 中断，删掉 node_modules 与 package-lock.json 后重装
EADDRINUSE / 端口被占用
（5173 起不来或自动跳 5174）		 别的程序占着门牌号 最简单：让它自动换号（看启动横幅里的实际端口）；要固定端口就加 server.port；或按下面平台命令揪出占门者：
Win netstat -ano | findstr :5173 → taskkill /F /PID 进程号
Linux lsof -i :5173 → kill -9 进程号
页面空白 + 控制台 404 / MIME 错误
（直接双击 index.html 打开）		 file:// 协议不是开发服务器 必须 npm run dev 用服务器伺服——双击打开的静态文件没有模块加工能力，这是原理不是故障
Failed to resolve import
「./xxx」不能被解析		 路径写错或大小写不对 对照文件名逐字母检查（Linux 上大小写敏感：Counter.js ≠ counter.js）；文件真不存在就补上
改了 .env / vite.config.js 不生效 它们只在启动时读一次 Ctrl+C 停掉，重新 npm run dev——80% 的「玄学」到这就好了
依赖疑似抽风：装了新包行为诡异 预打包缓存过期 npm run dev -- --force 强制重新备菜（第 6 章）；再不行删 node_modules/.vite 重启
Cannot find module 'esbuild'
或平台二进制缺失		 跨平台拷贝 node_modules / 安装中断 删掉整个 node_modules 与 package-lock.json，重新 npm install（Windows 与 Linux 的二进制不同，别互拷仓库）
ERESOLVE 依赖版本冲突 两个包要求的第三方版本打架 优先按报错提示对齐版本；应急用 npm install --legacy-peer-deps（放松同行版本检查，先跑起来再说）
build 后线上白屏（本地 preview 却正常？不，preview 也白） 多半是 base 路径没配 部署在子目录（如 GitHub Pages 的 /仓库名/）必须配 base: '/仓库名/'（第 8 章）；对照 preview 是否正常逐项排查 env 与路径
手机访问 --host 地址打不开 不同 WiFi / 防火墙拦截 确认手机与电脑同一 WiFi；Windows 首次开放会弹防火墙询问，点「允许」；公司网络可能隔离设备，换手机热点试
HMR「失效」：改动触发整页刷新 不一定是故障 影响入口/依赖结构的改动本来就会整页刷新；组件级改动应走热替换——若全部整刷，检查是否有语法错误（红色蒙层挡着）
Sass 报 Cannot find module 'sass' 没装预处理器 npm install -D sass（第 7 章）；Less/Stylus 同理装对应包
代理转交后 404 / 接口路径对不上 rewrite 削多了或削少了 打印后端实际收到的路径核对：rewrite 只该削掉约定前缀（/api），后端路由本身需要的前缀别削（第 10 章）

15.1 万能排查三板斧

  • 第一斧 看报错原文：红色蒙层/终端输出的第一行 + 文件名 + 行号就是答案所在地，别跳着读；
  • 第二斧 重启三部曲：硬刷新浏览器（Ctrl+F5）→ 重启 dev 服务器 → --force 重备菜；
  • 第三斧 搜错误原文：整段贴进搜索引擎（加上 vite 关键词）——你永远不是第一个踩坑的人。

最佳实践与速查表

16.1 七条店长守则

  1. node_modules 和 dist 永远当它们不存在：不手动改、不进 Git、不跨平台拷贝；坏了就删掉重装/重构建；
  2. 改配置必重启：vite.config.js 与 .env 是「启动时读一次」的档案，改完不重启等于没改；
  3. 先 preview 再发版：build 之后本地试吃（4173），确认无恙再上线——双流水线的行为差异都在这一步暴露；
  4. 密钥不进 VITE_：凡 VITE_ 开头的都会被打包公开；真正的机密放后端（第 9 章安全清单）；
  5. 项目尽早交给 Git：脚手架自带的 .gitignore 已把该忽略的列好——配合本目录的《Git 零基础完全教程》第 5 章，五分钟完成首笔提交；
  6. 玄学问题三板斧：硬刷新 → 重启 dev → --force；止不住再删 node_modules 重装（终极手段）；
  7. 遇到新需求先查官方文档：cn.vitejs.dev（中文版）结构清晰，配置项一搜即达——比道听途说可靠一百倍。
