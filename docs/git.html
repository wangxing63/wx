01

初识 Git：什么是版本控制

用一个「惨案」理解为什么全世界程序员都离不开它

在学任何命令之前，先搞清楚两件事：我们到底要解决什么问题，以及 Git 是个什么东西。这一章不讲操作，只讲故事和比喻——但它们会成为你后面理解一切命令的地基。

1.1 一个程序员的至暗时刻

先看一个几乎每个人都经历过的场景。小王在写毕业论文，为了「保险」，他每次大改之前都另存一份新文件。三个月后，他的文件夹长这样：

小王的文件夹（真实的惨案现场）
论文.doc                 # 第一版，青涩懵懂
论文-修改版.doc          # 改了一些内容
论文-最终版.doc          # 自信满满
论文-最终版2.doc         # 老师说要改第三章
论文-最终版-真最终版.doc  # 老师又说第五章要改
论文-最终版-打死不改了.doc # 崩溃边缘
论文-最终版-打死不改了2.doc # 彻底崩溃
论文-改回来一点.doc       # 想找回上周删掉的那段话，发现找不回来了

比起文件夹的混乱，更绝望的是这三个问题：

  • 「上周三我删掉的那段话，还能找回来吗？」——不能。文件早被覆盖了。
  • 「这行数据是谁改的？为什么改？」——不知道。没有任何记录。
  • 「现在这份和三天前那份，到底差在哪？」——只能靠肉眼一行行比对。
类比这就像打游戏没有存档功能：打到最后一关，手一抖死机了，只能从第一关重来；想回到「打 Boss 前的那个状态」？门儿都没有。

1.2 版本控制：给你的项目配一位「私人史官」

版本控制（Version Control）就是解决上面所有问题的技术：它会自动记录项目中每一次修改的时间、内容、作者和原因，让你可以随时「穿越」回任何一个历史时刻，随时对比任意两个版本的差异。

而 Git，就是当今世界上 最流行、最强大 的那个版本控制工具，没有之一。

类比装上 Git 之后，你的项目就拥有了游戏级存档系统：
  • 随时存档——每完成一小步就存一次（commit，提交）；
  • 随时读档——搞砸了就回到任意一个存档点（reset，回退）；
  • 多个存档槽——同时尝试多种方案互不干扰（branch，分支）；
  • 云端同步存档——换台电脑也能接着玩（remote，远程仓库）。

同样是刚才那些让人抓狂的场景，用 Git 之后画风突变：

日常场景手动管理文件夹用 Git 之后
想回到上周的版本翻遍一堆「最终版」，凭记忆猜一条命令，3 秒回去
想知道某行为什么这么写无人知晓，玄学追溯查到是谁、哪天、为什么改的
想尝试大改动又怕搞砸复制整个文件夹「项目-备份2」开个分支随便折腾，失败就删
两人同时改一个文件互相覆盖，全员抓狂自动合并，真冲突了会清楚提示
电脑突然坏了一切归零，含泪重写从远程仓库完整复原

1.3 Git 的诞生：被逼出来的神作

2005 年，Linux 之父 Linus Torvalds（就是那个创造了 Linux 内核、养活了全世界服务器的男人）遇到了大麻烦：原本用来管理 Linux 内核代码的商业工具突然不让社区免费用了，而现有的开源工具又慢得没法管理几千万行代码。

于是这位大佬做了个符合他风格的决定——自己写一个。据说他只花了大约两周时间就写出了 Git 的雏形，第一个版本就能以惊人的速度管理整个 Linux 内核的代码。如今，Git 已经统治了整个行业：全球绝大多数开源项目、几乎所有互联网公司的代码，都用 Git 管理。

小知识「git」在英式俚语里是「讨厌鬼」的意思。Linus 一贯的自嘲风格：「我是个自负的家伙，所有项目都以自己命名——Linux 是我，git 也是我。」

Git 是分布式版本控制系统：每个人电脑里都存着一份完整的项目历史，不是只有一个中央服务器。这意味着——断网也能正常提交代码，服务器炸了也几乎不丢数据。

1.4 Git、GitHub、Gitee、GitLab 到底啥区别？

新手最容易把这四个名字混为一谈。用一张表 + 一个类比彻底分清：

名字它是什么一句话理解
Git命令行工具，装在你电脑上照相机本身，负责拍照和相册管理
GitHub存放代码的网站（微软旗下）全球最大的「冲印社 + 摄影社区」，大家把相册传上去分享交流
Gitee（码云）国内的代码托管网站开在你家楼下的分店，国内访问速度快
GitLab可自建的代码托管平台公司买来放在自己机房的「私人会所」，代码不出门
  • Git 可以完全离线、单机使用——不想上传任何东西？一点问题都没有，本教程前 7 章都不需要联网。
  • 不用 GitHub ≠ 不会 Git——就像不发朋友圈也能用手机拍照一样。
  • GitHub 上也不只是代码：笔记、电子书、课程作业、简历甚至菜谱，只要想留历史记录的东西都能放。

02

安装 Git

Windows 与 Linux 双平台安装指南，顺便认识你的「终端」

好消息是：Git 装好之后，Windows 和 Linux 上的命令是一模一样的。区别只在安装方式和打开终端的方法，本章就把这两件事一次讲清。

2.1 安装前必读：给 Windows 用户的一颗定心丸

在 Windows 上装 Git 时，会附带一个叫 Git Bash 的终端工具，它模拟了 Linux 的命令环境。本教程推荐 Windows 用户统一使用 Git Bash——这样一来，教程里的每一条命令你在两个系统里都能原样运行，不用做任何转换。

技巧Windows 用户用 Git Bash，就能和 Linux 用户「说同一种语言」。当然，你也可以在 CMD / PowerShell 里直接敲 git 命令，只是新建文件、查看文件这类系统自带命令两者写法不同（对照表见 2.5 节）。

2.2 Windows安装 Git

  1. 下载安装包：打开官网 git-scm.com/download/win，下载 64 位安装包（文件名类似 Git-2.x.x-64-bit.exe）。官网慢的话，可以搜索「Git 国内镜像」下载。
  2. 运行安装包：双击打开，前几页一路点 Next（安装位置、组件选择都用默认值即可）。
  3. 选择默认编辑器（Select the default editor）：如果电脑上装了 VS Code，建议选 Visual Studio Code；没有也不慌，保持默认的 Vim 完全能用（后文教你如何从 Vim 中「逃生」）。
  4. 调整初始分支名（Adjust the name of the initial branch）：建议选择 Override the default branch name，填 main——这是目前全世界的通行惯例，也和本教程保持一致。
  5. 调整 PATH 环境变量（Adjusting your PATH environment）：选第二项 「Git from the command line and also from 3rd-party software」（推荐项，让你在 CMD 和 PowerShell 里也能用 git）。
  6. 选择 HTTPS 传输后端：默认 OpenSSL，直接 Next。
  7. 配置换行符（Configuring the line ending conversions）：保持第一项 「Checkout Windows-style, commit Unix-style line endings」——这是为 Windows 量身推荐的选项，能避免日后恼人的换行符警告。
  8. 选择终端模拟器（Configuring the terminal emulator）：默认 MinTTY 即可，后面全部 Next 到 Install，等待完成点 Finish。
  9. 验证安装：桌面或开始菜单右键空白处，看到 「Open Git Bash here」（在此处打开 Git Bash）选项，说明安装成功。点击它，弹出的黑色窗口就是你的「驾驶舱」。
注意不同版本的安装器界面顺序可能略有差异，认准上面的英文标题关键词即可；不确定的选项一律保持默认，Git 的默认值对小白都非常友好。

2.3 Linux安装 Git

Linux 安装 Git 是全场最轻松的——一条命令搞定。不同发行版用不同的「包管理器」，对号入座即可：

Debian 系

Ubuntu / Debian / Deepin

终端
sudo apt update          # 刷新软件源：看看软件列表有没有更新
sudo apt install git -y  # 安装 Git；-y 表示所有确认询问都自动答「是」
RedHat 系

CentOS / Fedora / Rocky

终端
sudo yum install -y git  # CentOS 7 等老系统用 yum 安装
sudo dnf install -y git  # Fedora / 新版 RHEL 用新一代的 dnf 安装

sudo pacman -S git       # Arch / Manjaro 用户
sudo zypper install git  # openSUSE 用户

如果提示 git: command not found（找不到命令），先按上面的方法安装；多数 Linux 发行版其实自带 Git，早就装好了。

2.4 验证安装：让 Git 报个到

双平台通用打开终端（打开方法见下一节），输入下面这条命令：

终端
git --version      # 让 Git 自报版本号；--version 是几乎所有命令行工具的通用「报到」方式
git version 2.45.1        # Windows 上会显示 git version 2.45.1.windows.1 之类
# 只要出现「git version x.x.x」，就说明安装成功，可以开始浪了

想顺手确认 Git 装在哪里，可以再敲一条：

终端
which git         # Linux / Git Bash：显示 git 程序所在的完整路径
where git         # Windows CMD / PowerShell：与 which 同义，问「git 在哪」
/usr/bin/git              # Linux 上的常见位置
C:\Program Files\Git\cmd\git.exe   # Windows 上的常见位置

2.5 认识你的「驾驶舱」：终端

终端（Terminal）就是你敲命令的地方，长得像黑客电影里的黑窗口。它不可怕——只是把「点点点」的鼠标操作换成了「打字回车」，而且效率更高。

怎么打开终端

  • Windows三种方式任选：① 在任意文件夹里右键空白处 → 「Open Git Bash here」（最推荐，直接定位到当前文件夹）；② 开始菜单搜 Git Bash；③ 桌面右键 → Open Git Bash。
  • Linux按 Ctrl + Alt + T，或在应用列表里搜「Terminal / 终端」。

看懂「提示符」

打开终端后，最先看到的是一行「提示符」——它在告诉你：我现在在哪、等你下指令。

两种提示符长这样
user@ubuntu:~/project$          ← Linux / Git Bash 的提示符：用户名@电脑名:当前路径$
                                                     最后那个 $ 是「该你说话了」的意思
PS C:\Users\xiaowang\project>    ← PowerShell 的提示符：PS 路径>
C:\Users\xiaowang\project>       ← CMD 的提示符：直接就是路径>
技巧提示符不需要你自己输入，它自己会出现。教程为了省篇幅，之后所有代码块都不画提示符，你只管敲命令本体、按回车。

03

初次配置：领一张「工作证」

装好 Git 后只需做一次的全局配置，从此每笔提交都有你的大名

Git 是「多人协作」工具，所以它需要知道你是谁。就像进公司先领工牌——以后你提交的每一行代码，都会自动盖上你的名字和邮箱。这一步每台电脑只需做一次。

3.1 设置用户名和邮箱：报上名来

双平台通用在终端里执行下面两条命令（把名字和邮箱换成你自己的）：

终端
git config --global user.name "小王"               # 设置用户名：以后每次提交都署这个名字
git config --global user.email "xiaowang@qq.com"   # 设置邮箱：身份标识，也是平台给你发通知的地址
类比这两条命令相当于在快递单上填写默认寄件人：填一次，之后每个包裹（提交）都自动带上你的姓名和联系方式，收件人（同事）一看就知道是谁寄的。
注意这里的邮箱不需要注册、不需要验证，写什么都行——但如果你以后要用 GitHub，最好填 GitHub 账号的绑定邮箱，这样你的提交才能被认领到你的账号名下。

顺手把新仓库的默认分支名也设为 main（与第 2 章安装时的选择呼应）：

终端
git config --global init.defaultBranch main   # 以后 git init 创建的仓库，默认分支叫 main（新惯例）

3.2 查看与修改配置

终端
git config --list                    # 列出当前生效的全部 Git 配置（内容较多，滚动查看）
git config user.name                 # 只查看某一项：这里会打印你的用户名
git config user.email                # 只查看邮箱这一项
git config --global --unset user.email  # 删除某项全局配置（比如想换邮箱时，先删再重设）
user.name=小王                 ← 你的配置都存在这（示意）
user.email=xiaowang@qq.com
init.defaultbranch=main

改配置不需要任何「删除」步骤——同名命令再执行一遍就是覆盖。想把名字改成「老王」？直接再敲一次 git config --global user.name "老王" 即可。

3.3 配置存在哪：三层「规章制度」

Git 的配置分三层，作用范围从小到大，越具体的越说了算（就近原则）：

层级写法作用范围类比
系统级--system整台电脑所有用户公司规章制度（全员遵守）
全局级--global你这台电脑上的所有仓库部门惯例（本部门都这样）
仓库级（不写参数）仅当前这一个仓库项目组的特别约定（这个项目说了算）
技巧日常只管用 --global，一次配置全机生效。只有当你想让某一个项目用不同的署名（比如公司项目用真名、开源项目用网名）时，才在那个项目目录里去掉 --global 单独配置。

3.4 给命令起外号：别名配置（可选但超爽）

有些命令又长又常敲，可以给它们起「外号」（alias，别名），大幅减少打字量：

终端
git config --global alias.st "status"        # 之后敲 git st 就等于 git status（查状态）
git config --global alias.cm "commit -m"     # 之后敲 git cm "说明" 就等于 git commit -m "说明"
git config --global alias.lg "log --oneline --graph --all"  # git lg = 带图形的一行式历史（超好用）
技巧本教程正文一律使用完整命令，保证你查任何资料都能对上号；等你自己敲熟了，再按喜好启用别名不迟。

核心概念：三大区域与四种状态

全书最重要的一章——看懂这张「地图」，之后所有命令都不再是死记硬背

很多新手学 Git 半年还是晕，就是因为跳过了概念直接背命令。请花十分钟读完本章——之后你看到的每条 Git 命令，都能瞬间明白它「在地图上走了哪一步」。

4.1 一家「照相馆」：三大区域

Git 管理项目的方式，像极了一家照相馆。你的项目文件会流经三个地方：

① 工作区（Working Directory）—— 拍照现场

就是你在电脑上看得见摸得着的那个项目文件夹：你写代码、改文档、删文件，都发生在工作区。此刻它是什么样，打开文件夹看到的就是什么样。

② 暂存区（Staging Area）—— 上镜名单

一个看不见的「候场区」。执行 git add，就是把某些改动登记进这次的拍摄名单；名单外的改动，按下快门时不会被拍进去。

类比拍毕业合照前，老师会先点名：「小明、小红、小刚，你们三个站到台上来！」——点名就是 git add。没被点到名的同学（改动），快门按下时就不在照片里。这样你就能从容地分批提交：比如改了 5 个文件，只把其中 3 个相关的打包成一次干净的提交，剩下 2 个留到下一次。

③ 版本库（Repository）—— 相册

执行 git commit（提交），相当于按下快门：把「上镜名单」里的内容定格成一张永不褪色的快照，编上号，存进相册。从此它永远安全——想什么时候翻看、什么时候「读档」回去都行。

科普版本库实体就是你项目文件夹里那个隐藏的 .git 文件夹——它就是「相册 + 登记 + 档案室」本身。你可以进去参观（ls -a 可以看到它），但千万别手动修改里面的任何东西，就像别拿剪刀去剪相册的底片。

4.2 文件的四种「状态」

Git 眼中，工作区的每个文件永远处于四种状态之一。理解它们，git status 的输出你就能秒懂：

状态中文照相馆类比它想告诉你
Untracked未跟踪新面孔站在照相馆门口「这是新文件，Git 还没开始管理它」——需要 git add 收编
Staged已暂存已点名，站上台等着拍照「改动已进名单，下次 commit 会拍进去」
Unmodified未修改拍完照安静坐着「和最近一次快照一模一样」，啥也不用做
Modified已修改把自己弄乱了，还没补拍「和快照不一样了」——想存档就重新 add + commit
看色识状态git status 的输出里：绿色的文件 = 已进名单（staged），等着拍照；红色的文件 = 还没登记（untracked / modified）。一句话：绿的马上要拍，红的还没安排。

4.3 HEAD：相册里夹着的书签

你会经常见到 HEAD 这个词。它就是夹在相册里的书签，标记「你当前所在的位置」——正常情况下，它指向当前分支最新那张照片（最新一次提交）。

终端
# 「HEAD 指针」的常用写法（后面回退章节会大量用到）
HEAD          # 书签当前位置：即当前分支的最新一次提交
HEAD^         # 书签的上一个提交（^ 写几个就往回退几步）
HEAD^^        # 上上个提交（连续两个 ^）
HEAD~3        # 往回数第 3 个提交（比 ^^^^ 更省力的写法）
类比看小说时手指总停在当前页——HEAD 就是那根手指。翻到哪页（切换版本），手指跟到哪页；HEAD^ 就是「上一页」，HEAD~3 就是「往前翻 3 页」。

4.4 一张「命令地图」：想去哪，敲哪条

把本章所有知识压缩成一张表。之后每学一条新命令，先问自己：它在三个区域之间搬运了什么？

你想做什么命令在地图上发生了什么
把改动登记进拍摄名单git add 文件工作区 → 暂存区
按下快门，存入相册git commit暂存区 → 版本库
把文件从名单里撤下来git restore --staged 文件暂存区 → 工作区（改动不丢）
丢弃工作区的改动git restore 文件用快照内容覆盖工作区（改动丢弃）
整体回退到某个历史版本git reset 版本移动 HEAD 书签，可选是否保留改动
查看当前状态git status给三个区域拍一张「检查报告」
查看具体改了什么git diff逐行对比两个区域 / 两个版本
心法背下这张地图，胜过死记 50 条命令。后面每一章，本质上都只是在这张地图上「走更远的路」而已。

05

基础操作：完成你的第一次提交

从 git init 到 git log，手把手走完本地仓库的完整一生

概念备齐，现在开工。本章从「一个空文件夹」开始，带你走完 建仓库 → 改文件 → 查状态 → 存快照 → 看历史 → 比差异 的完整闭环。双平台通用每条命令都照着敲一遍，Git 就真正属于你了。

5.1 创建仓库：git init

仓库（repository） = 被 Git 接管的文件夹 = 一本开始记录的相册。让一个普通文件夹「变身」成仓库，只需一条命令：

终端
mkdir my-project    # 新建一个练习项目文件夹（名字随意）
cd my-project       # 进入这个文件夹——Git 命令都作用于「当前所在文件夹」
git init            # 变身！把当前文件夹初始化为一个 Git 仓库（生成隐藏的 .git 文件夹）
ls -a               # 查看所有文件，包括隐藏文件（CMD 用户用 dir /a）
Initialized empty Git repository in .../my-project/.git/   ← 初始化成功
.  ..  .git         ← 多出来的 .git 就是「相册本体」，从此这个文件夹有了记忆
注意git init 只需要做一次。如果在一个已经有 .git 的文件夹里（或它的上层）再次执行，不会有伤害但也毫无必要。看到别人项目里的 .git 文件夹，就说明「这是个被 Git 管理的项目」。

5.2 查看状态：git status（你最亲密的伙伴）

git status 是你用得最多的命令，没有之一——迷路了就敲它，Git 永远会告诉你「现在什么情况、接下来能干什么」。先制造一点「情况」：

终端
echo "这是我的第一个 Git 项目" > readme.txt  # 创建 readme.txt 并写入一行内容
                                              # （CMD 用户：echo 这是我的第一个项目>readme.txt，或用记事本直接建）
git status                                   # 看看 Git 怎么「看待」这个新文件
On branch main                     ← 当前在 main 分支上
No commits yet                    ← 相册还是空的：还没有任何提交
Untracked files:                  ← 「未跟踪」名单：Git 发现了新面孔
  (use "git add <file>..." to include in what will be committed)
        readme.txt                ← 新文件站在门口，等你发话
nothing added to commit but untracked files present   ← 暂存区空空如也

看到了吗？Git 不但报告了状态，还贴心地把下一步命令都写在括号里提示你了。跟着提示走：

5.3 登记进名单：git add

终端
git add readme.txt   # 把 readme.txt 登记进「上镜名单」（暂存区）
git status           # 再看状态：它应该变绿了（Changes to be committed）
Changes to be committed:          ← 名单区（绿色）：这些将被拍进下一张照片
  (use "git rm --cached <file>..." to unstage)
        new file:   readme.txt    ← 新文件已登记，就等快门

git add 还有几个常用变体，一次登记多个文件时很方便：

终端
git add .            # 登记当前目录下「所有」变动（新文件、修改、删除一网打尽，最常用）
git add *.txt        # 登记所有 .txt 结尾的文件（* 是通配符：任意名字）
git add -A           # 登记整个仓库中所有的变动（不限当前目录）
git add 文件1 文件2   # 登记指定的多个文件，空格隔开
技巧日常 95% 的场景就是 git add 文件名（精细控制）或 git add .（全都要）。点（.）代表「当前文件夹」，所以这条命令读作「把这里的一切变动都登记上」。

5.4 按下快门：git commit

终端
git commit -m "第一次提交：添加项目说明文件"  # 按下快门！把名单内容定格为一张永久快照
                                            # -m 是 message（留言）的缩写，引号里写本次提交说明
git status                                  # 再看状态：干净了（nothing to commit）
[main (root-commit) a1b2c3d]    ← 提交成功：进入了 main 分支，编号 a1b2c3d（每次提交的唯一指纹）
 1 file changed, 1 insertion(+)  ← 变化统计：改了 1 个文件，新增了 1 行
 create mode 100644 readme.txt
类比提交说明（message）就像写在照片背面的备注：「2026.09.13 全家福，小王第一次下厨」。半年后翻相册时，备注就是唯一的线索——所以要写清楚「这次做了什么」，而不是敷衍地写「修改」「更新」「aaa」。

一个进阶变体：-a 能把「已跟踪文件」的修改直接带进名单，省去 add 那一步：

终端
git commit -am "更新说明文件"   # -a：先把所有「已跟踪文件」的改动自动 add，再提交
                                # 注意：全新文件（未跟踪）不适用，仍需先手动 git add

5.5 翻看相册：git log

终端
git log                       # 查看完整提交历史：编号、作者、日期、说明，从新到旧
git log --oneline            # 精简模式：一行一条，只显示短编号和说明（看得最舒服）
git log --oneline -3         # 只看最近 3 条（-n 数字随意）
git log --author="小王"      # 只看某位作者的提交
git log -p readme.txt        # 查看某文件历次提交的具体改动（-p = patch，逐行差异）
git log --oneline --graph --all  # 用字符图形画出所有分支走向（多分支时一目了然）
a1b2c3d (HEAD -> main) 第一次提交：添加项目说明文件   ← --oneline 模式示意
                                     ↑ HEAD 书签指向最新一张，且在 main 分支上

嫌按 Q 退出长列表太隐蔽？对——当 log 内容超过一屏时，会进入翻页模式：空格键翻页，按 Q 退出回到终端。

5.6 逐行对比：git diff

diff（difference，差异）用来回答「到底改了哪几行」。先改点东西再看：

终端
echo "追加的第二行内容" >> readme.txt  # >> 表示「追加」一行而不覆盖（CMD 写法相同）
git diff                             # 对比「工作区 vs 暂存区」：刚改了还没 add 的部分
git diff --staged                    # 对比「暂存区 vs 最近一次提交」：已 add 还没 commit 的部分
git diff HEAD                        # 对比「工作区 vs 最近一次提交」：改动总账（HEAD 指最新快照）
diff --git a/readme.txt b/readme.txt    ← 对比的是 readme.txt
+ 追加的第二行内容                     ← 前面是 + 号 = 新增的行
- 被替换掉的旧行                        ← 前面是 - 号 = 删除/被改掉的行
                                       ← 上下文行不带头衔，仅作参照
记忆add 之前看 git diff，add 之后看 git diff --staged。判断标准就一条：你想比较的是「没进名单的改动」还是「已进名单的改动」。

5.7 禁拍名单：.gitignore

总有些文件不想进相册：临时文件、日志、密钥、体积巨大的依赖文件夹……在项目根目录新建一个名为 .gitignore 的文本文件，把「禁拍规则」写进去：

文件：.gitignore（放在项目根目录）
# 井号开头的是注释
node_modules/      # 忽略整个 node_modules 依赖文件夹（体积大且随时能重新安装）
*.log              # 忽略所有以 .log 结尾的日志文件（* 通配任意文件名）
*.tmp              # 忽略所有临时文件
dist/              # 忽略构建产物文件夹（打包生成的成果，不需要进历史）
.env               # 忽略环境变量文件——里面常有密码，绝不能上传！
!important.log     # 感叹号 = 例外：唯独这个文件虽然匹配 *.log 但别忽略它
类比.gitignore 就是贴在照相馆门口的「谢绝入内」名单：名单上的人（文件），git add . 再怎么「见人就拉」也会绕开他们。
注意.gitignore 本身应该提交进仓库，让全组共享同一份「禁拍规则」。另外它只对未跟踪的文件生效——如果文件早已被提交过，需先执行 git rm --cached 文件名（取消跟踪但保留硬盘文件）再写进 ignore。

5.8 删除与重命名：git rm / git mv

终端
git rm 旧文件.txt          # 删除文件，并把这个「删除」动作直接登记进暂存区
                           # （对比：直接 rm 删除后，Git 会显示 deleted 且需要再 git add）
git mv 旧名字.txt 新名字.txt  # 重命名文件 = mv + git add 一步到位（历史记录会跟随改名）
git rm --cached 密码文件.txt  # 让 Git 停止跟踪某文件，但文件本身保留在硬盘上（补救误提交）
动手练习 02
  1. 新建 git-practice 文件夹，完成 git init；
  2. 创建两个文件，分别体验「只 add 其中一个」然后 commit——用 git status 观察另一个文件是否还是红色；
  3. 再改一次文件，用 git diff 看差异，然后 add + commit；
  4. 用 git log --oneline 欣赏你的两笔历史；最后新建 .gitignore，随便忽略一种文件试试效果。

撤销与回退：Git 的后悔药全集

人生没有后悔药，Git 有的是——按「后悔的深度」对症下药

改乱了想恢复、add 错了想撤回、commit 说明写错了想改、想整个穿越回昨天——这些「后悔」的深度不同，用的药也不同。本章把它们一网打尽。双平台通用

你后悔的事该吃的药见哪节
只是把工作区改乱了，还没 addgit restore 文件6.1
add 错了 / add 多了git restore --staged 文件6.2
commit 的说明写错了 / 漏了文件git commit --amend6.3
想穿越回几个版本之前git reset6.4
已经推送给别人，想安全地撤销git revert6.5
reset 错了，想把丢失的找回来git reflog6.6

6.1 后悔深度 ★：丢弃工作区的改动

场景：你把一段代码改得一团糟，还没 add，只想让文件恢复成上次提交的样子：

终端
git restore readme.txt     # 丢弃该文件在工作区的改动，恢复成「暂存区或最近提交」的样子
git restore .              # 丢弃当前目录下所有未提交的工作区改动（范围大，想清楚再敲）
注意丢弃 = 真的没了，没有回收站。敲之前先用 git diff 确认你要丢的东西。老教程里的 git checkout -- 文件名 是同一件事的旧写法，见到别陌生。

6.2 后悔深度 ★★：把文件撤出暂存区

场景：手滑 git add 了不想提交的文件（改动本身想留着）：

终端
git restore --staged readme.txt  # 把文件从「上镜名单」里撤下来，改动原样保留在工作区
                                  # 它只是撤销「登记」这个动作，绝不会动你的文件内容
类比拍照前老师喊错了人：「小刚你先回去坐下」——人还是那个人（改动还在），只是不在下一张照片里了。旧写法是 git reset HEAD 文件名，效果相同。

6.3 后悔深度 ★★★：修补最后一次提交

终端
git commit --amend -m "新的说明"   # 修改最后一次提交的说明文字（照片备注写错了，重新写）
git commit --amend --no-edit       # 把刚 add 的内容并入最后一次提交，且不改动原说明
                                   # --no-edit 读作「备注不动，只把新东西塞进这张照片」
类比拍了合照发现小刚闭眼了——不用另拍一张新照片占地方，直接重拍覆盖同一页：照片还是「那张」，只是内容更新了。
注意amend 会「改写历史」。如果那次提交已经 push 给别人看过，就别 amend 了（别人手里的相册会对不上页码）——那要用 6.5 的 revert。

6.4 后悔深度 ★★★★：版本回退 git reset

场景：最近几次提交都不想要了，想「穿越」回某个历史版本。reset 有三档火力，区别在于穿越之后，你的改动还剩多少：

模式改动去哪了类比什么时候用
--soft完整保留在暂存区妆都没卸，准备直接重拍想把多次提交合并成一次
--mixed
（默认）		保留在工作区妆卸了，道具都还在桌上回退后想重新挑选要提交的内容
--hard全部丢弃（危险）连人带景整个抹掉，回到那天确定那些改动全是垃圾
终端
git log --oneline            # 第一步永远是它：找到要回到的版本号（如 a1b2c3d）
git reset --soft a1b2c3d     # 回到该版本：之后的提交撤销，改动全留在暂存区
git reset --mixed a1b2c3d    # 回到该版本：改动退回工作区（不带参数时默认就是它）
git reset --hard a1b2c3d     # 回到该版本：之后的提交和改动全部清空（危险！）
git reset --hard HEAD^       # 一步回退到上一个版本（^ 的个数 = 回退几步）
git reset --hard HEAD~3      # 回退到 3 个版本之前（~n 比 ^^^ 写法省力）
警告--hard 会把未提交的改动和之后的提交一起销毁。三思而后敲：先 git status + git diff 看清楚会失去什么。同样地：已 push 给别人的提交，永远不要 reset。

6.5 安全撤销：git revert（公共分支专用）

场景：某次提交已经推送、被同事看到了（甚至大家基于它开工了），现在想撤销它。不能撕别人手里的日记——正确做法是在后面再写一页「更正声明」：

终端
git revert a1b2c3d           # 生成一笔「反向提交」，精确抵消指定提交的所有改动
                             # Git 会弹出编辑器让你确认说明，保存退出即可（Vim 逃生见第 12 章）
git revert --no-commit a1b2c3d  # 只应用反向改动、不自动提交，方便和其他内容合并成一笔
类比reset 是把日记撕掉重写——自己的日记随便撕；revert 是在日记后面郑重写一页「第 38 页作废」——历史原封不动，大家手里都多了同一页更正。所以公共分支（别人看得到的）一律用 revert。

6.6 后悔药的后悔药：git reflog

场景：reset --hard 敲完一拍脑门——删多了！别慌，Git 没有真销毁任何东西（默认保留 30 天以上）。reflog（reference log，引用日志）记录着 HEAD 书签的每一次移动，堪称行车记录仪：

终端
git reflog                   # 查看书签的每一次移动记录（包括被你 reset 掉的版本）
# 输出类似：a1b2c3d HEAD@{0}: reset: moving to HEAD~3   ← 你刚才那次鲁莽的回退
#           e4f5g6h HEAD@{1}: commit: 添加登录功能        ← 「丢失」的提交其实记着地址呢
git reset --hard e4f5g6h     # 对着记录里的编号，一步穿越回去，一切失而复得
定心丸记住这句话：只要提交过（commit 过），就几乎永远找得回来。真正无法挽回的只有一种情况——从未提交过的改动被 restore / reset --hard 丢弃。所以勤 commit，是最便宜的保险。

分支：开启平行宇宙

大刀阔斧地实验而不伤主线——Git 最优雅的发明

如果说「提交」是 Git 的心脏，那「分支」就是 Git 的灵魂。它让你可以同时维护多条互不干扰的时间线，大胆实验、并行开发、紧急救火。双平台通用

7.1 为什么需要分支？

想象你要给项目加一个很炫的新功能，要大改两周。没有分支的话，你的项目在这两周里永远处于「半成品」状态——中途线上出了紧急 Bug，你只能在一堆改了一半的代码里修，修完还不知道怎么把功能捡回来。

类比分支就是平行宇宙：从今天开始复制出一个「宇宙 B」，你在里面随便折腾新功能，怎么炸都炸不到「主宇宙」；与此同时主宇宙该修 Bug 修 Bug、该发版发版。等宇宙 B 的功能做完验收合格，再把它的成果合并回主宇宙——主宇宙仿佛瞬间学会了新技能，而中间那些试错的烂摊子从不曾存在。

7.2 分支的增删改查

终端
git branch                  # 列出所有本地分支；当前所在分支前有 * 号
git branch feature-login    # 创建一个叫 feature-login 的新分支（创建后人还站在原地）
git switch feature-login    # 切换过去：从这一刻起，你的所有提交都发生在新宇宙里
git switch -c feature-pay   # 创建 feature-pay 分支并立刻切换（-c = create，一步到位）
git checkout -b feature-pay # 与上一条等效的旧写法（老教程里常见，认识即可）
git switch -                # 切回「刚才」所在的分支（像电视机的返回上一频道）
git branch -m main          # 把当前分支重命名为 main（比如想把 master 改成 main 时）
git branch -d feature-login # 删除已合并的分支（Git 会检查，不让误删没合并的成果）
git branch -D feature-login # 强制删除：连未合并的成果一起扔掉（想清楚了再敲）
类比git branch 是「开宇宙」，git switch 是「穿越过去」。只开不穿，人还在原宇宙——所以新手最常犯的错就是「以为自己在 A 宇宙干活，其实提交到了 B 宇宙」。动手前先 git branch 确认 * 号在哪。

7.3 合并宇宙：git merge

终端
git switch main             # 先切回主分支——想把别人合并进来，自己得先站在主位
git merge feature-login     # 把 feature-login 的成果合并进「当前所在」的 main 分支
git merge --no-ff -m "合并登录功能" feature-login  # 强制生成一条合并记录，保留分支拓扑
                            # （--no-ff = no fast-forward：即使能快进也走正式合并流程）
git merge --abort           # 合并遇到大麻烦时紧急刹车：恢复到合并开始前的状态

合并分两种情况，了解一下更有底气：

情况发生条件Git 的做法
快进合并
(fast-forward)		主分支自岔出后没有新提交直接把指针一挪，追上分支——像两条车道并一条，直接开过去
三方合并
(merge commit)		两边都有各自的新提交找出共同祖先，综合两边的成果生成一张新的「合并提交」照片

7.4 冲突：当两个宇宙记忆不合

合并最怕的就是冲突（conflict）：两个分支改了同一个文件的同一片区域，Git 不知道该听谁的——它没法替你做决定，只能把两个版本都摆出来，请你来当裁判。

类比两个人合写一首歌，都在第 8 小节填了不同的旋律。合并时 Git 只能摊手：「第 8 小节 A 写的是红烧肉，B 写的是炸鸡，您定夺。」——它报的不是错误，而是需要人工裁决的事项。

亲手制造并解决一次冲突（强烈建议照做）

终端 · 制造冲突
git switch -c feature-lunch    # 开一条「午餐宇宙」分支并切换过去
echo "今天食堂吃炸鸡" > lunch.txt # 在新宇宙里写一份午餐计划
git add lunch.txt              # 登记这个新文件
git commit -m "午餐宇宙：决定吃炸鸡"  # 在新宇宙存档
git switch main                # 穿回主宇宙
echo "今天食堂吃红烧肉" > lunch.txt # 在主宇宙写一份「内容不同」的午餐计划
git add lunch.txt              # 同样登记
git commit -m "主宇宙：决定吃红烧肉"  # 主宇宙也存档——冲突的火药埋好了
git merge feature-lunch        # 尝试合并 → Git 立刻举手：CONFLICT!
CONFLICT (add/add): Merge conflict in lunch.txt   ← 冲突发生在 lunch.txt
Automatic merge failed; fix conflicts and then commit the result.   ← 请修复后手动提交

此时打开 lunch.txt，你会看到 Git 留下的三行「分界标记」：

文件：lunch.txt（冲突标记长这样）
<<<<<<< HEAD
今天食堂吃红烧肉        ← ======= 上方：当前分支（HEAD，即 main）的版本
=======
今天食堂吃炸鸡          ← ======= 下方：被合并进来的 feature-lunch 的版本
>>>>>>> feature-lunch
终端 · 裁决并完成合并
# 第一步：打开文件，把七行标记连同两边内容，改成你最终想要的文字
#         比如改成「今天食堂吃炸鸡和红烧肉」，保存关闭
git add lunch.txt              # 第二步：告诉 Git「这里我裁决完了」
git commit -m "解决午餐冲突：都吃"  # 第三步：完成这次合并（相册里从此多一张合并快照）
心法解决冲突三板斧：① 改文件（删掉所有标记行、留下最终内容）→ ② add 标记解决 → ③ commit 完成合并。搞砸了随时 git merge --abort 推倒重来。另外，冲突不是事故——多人协作的正常组成部分，遇到不要慌。

7.5 团队的「宇宙管理局」：分支策略

分支虽好，也不能乱开。业界最常用的一套简单规范（小团队直接照抄即可）：

分支名角色类比
main正式发布版，永远可用、随时能上线店铺的「营业大厅」，只摆验收合格的成品
develop日常开发汇总，最新但不完全稳定「后厨」，菜做好还没上桌
feature/xxx每个新功能一条独立分支，做完合并「实验小灶」，一道菜一个灶台互不打扰
hotfix/xxx线上紧急修复，从 main 岔出、修完立刻并回「消防通道」，救火专用直达快线
铁律main 分支永远不直接提交代码——所有改动都走 feature 分支合并进去。这样 main 的每一版都是「验过货的」，出问题随时能安全回退或上线。
动手练习 03
  1. 在练习仓库里开一条 feature-test 分支，提交一笔，切回 main 看看它「消失」了（其实在新宇宙里）；
  2. 合并它，用 git log --oneline --graph 欣赏合并拓扑；
  3. 按 7.4 的步骤亲手制造一次冲突并解决它——这将是你在团队里最值钱的一次练习。

08

远程仓库：连接 GitHub

把相册存进「云端保险柜」，从此换电脑、找队友都不是问题

前 7 章的一切都发生在你自己的电脑上。现在把世界连起来：注册平台、配置「电子门禁卡」、推送、克隆、拉取——走完团队协作的第一公里。双平台通用（Windows 请全程使用 Git Bash，和 Linux 命令完全一致）

8.1 远程仓库是什么？

远程仓库（remote repository） = 放在服务器上的仓库副本。它干两件事：云端备份（电脑丢了代码还在）和协作中转（你和同事都对着它推拉代码）。

类比本地相册放在你家书柜；远程仓库就像在银行租了个保险柜 + 开了个共享大厅：你把照片复印一份存进去（push），同事把他们拍的也存进去；想看大家最新的成果就去大厅取一份（pull）。GitHub 就是全球最大的那家「共享照相馆」（国内可用 Gitee / 码云，操作完全同理）。

8.2 注册与建仓库

  1. 注册账号：打开 github.com（国内可用 gitee.com），Sign up 填邮箱、密码、用户名，完成邮箱验证。
  2. 新建仓库：登录后点右上角 + → New repository。
  3. 起名：Repository name 填一个名字（如 my-project），建议小写、用连字符。
  4. 选公开还是私有：Public = 任何人可见（开源精神）；Private = 只有你和你邀请的人可见。
  5. 勾选 README：新手建议勾上「Add a README file」，仓库首页会自动生成说明文档。
  6. 点 Create repository，跳转到仓库页面——你的「云端保险柜」开张了。先别关网页，地址马上要用。

8.3 配置「电子门禁卡」：SSH 密钥

每次推送都要输密码太烦了。SSH 密钥 = 一把永不外借的私钥 + 一把见人就发的挂锁：把「挂锁」（公钥）挂在 GitHub 门口，你口袋里揣着唯一的「钥匙」（私钥），以后 Git 传输自动验明正身、免密通行。

第一步：生成钥匙对

终端（Windows 用 Git Bash 执行）
ssh-keygen -t ed25519 -C "xiaowang@qq.com"  # 生成一对密钥：-t 指定算法，-C 写备注（通常填邮箱）
# 接下来连按三次回车：
#   ① 存放位置 → 直接回车用默认（用户主目录的 .ssh 文件夹）
#   ②③ 设置口令 → 直接回车留空（小白阶段强烈建议留空，否则每次都要多输一次）

第二步：把「挂锁」挂到 GitHub 上

终端
cat ~/.ssh/id_ed25519.pub   # 查看公钥（挂锁）内容；~ 代表你的用户主目录
                            # Windows 的实际位置是 C:\Users\你的用户名\.ssh\id_ed25519.pub
# 复制输出的全部内容（以 ssh-ed25519 开头、以你的邮箱结尾，一整行）
# 打开 GitHub → 右上角头像 → Settings → SSH and GPG keys → New SSH key
# Title 随便起（如「我的电脑」），Key 粘贴刚才的内容 → Add SSH key

第三步：测试门禁

终端
ssh -T git@github.com       # 敲门测试：GitHub 会核实你的钥匙
# 首次连接会问 Are you sure you want to continue connecting? → 输入 yes 回车
Hi xiaowang! You've successfully authenticated...   ← 看到这句 = 门禁配好了，以后免密通行
小知识Gitee 配置方法一模一样：把公钥贴到 Gitee 的「设置 → SSH 公钥」里即可，两家的钥匙可以通用同一把。

8.4 关联远程仓库：git remote

让本地仓库「认识」云端那间保险柜。仓库页面那个以 git@github.com: 开头的地址（SSH 地址）就是它：

终端
git remote add origin git@github.com:xiaowang/my-project.git  # 建立关联：给远程仓库起昵称 origin
git remote -v               # 查看已关联的远程仓库（-v 显示具体地址，fetch/push 各一行）
git remote remove origin    # 解除关联（地址填错了就先解除，再重新 add）
git remote rename origin upstream  # 改昵称：把 origin 改叫 upstream
origin  git@github.com:xiaowang/my-project.git (fetch)   ← origin 就是个「昵称」，叫啥都行
origin  git@github.com:xiaowang/my-project.git (push)    ← 但全世界都默认叫它 origin，随大流最省心
地址仓库页面上还有个 https://github.com/... 开头的地址也能用，但每次都要输账号密码；SSH 地址配合上一节的门禁才是长期饭票。认准 git@github.com: 开头的。

8.5 推送：git push

终端
git push -u origin main     # 第一次推送：把本地 main 推上云端；-u 顺手记住对应关系
git push                    # 之后的日常推送只需这四个字母（因为 -u 已经牵好线了）
git push origin dev         # 把本地 dev 分支推上云端（云端没有就自动创建）
类比-u 相当于和快递公司签了长期合约：第一次把地址电话都登记好，以后只要喊一声「寄！」（git push），什么都不用再填。所以每个分支的第一次推送记得带 -u。

8.6 克隆：git clone

换新电脑了 / 想参与别人的项目 / 电脑坏了要复原——把远程仓库整套复印到本地：

终端
git clone git@github.com:xiaowang/my-project.git  # 复制整个仓库到当前目录（含全部历史）
git clone git@github.com:xiaowang/my-project.git mydir  # 复制时顺便给本地文件夹改名 mydir
cd my-project               # 克隆完记得进去——这就是你的新工作区
# 克隆是「全自动一条龙」：自动关联 remote、自动建好 main、自动跟踪远程分支
冷知识克隆别人的开源项目不需要任何权限（Public 仓库随便克隆）；但你没有权限直接 push——想贡献代码要走 8.8 的 Fork + PR 流程。

8.7 拉取：git fetch 与 git pull

同事往云端推了新东西，你要把它取回来。两个命令，性格迥异：

命令它做什么类比
git fetch只把远程新内容取回来看，本地分支一个字都不动先取快递单看一眼，不拆包
git pull取回并立刻合并进当前分支（= fetch + merge）取回来直接拆开装好
终端
git fetch origin            # 取回远程最新动态（内容进入本地，但还没合进你的分支）
git diff main origin/main   # 看看「我的 main」和「云端的 main」到底差了什么
git merge origin/main       # 确认没问题后，再把云端改动合并进来（origin/main 叫「远程跟踪分支」）
git pull                    # 新手日常够用的懒人版：取回 + 合并，一步到位
git pull --rebase           # 取回并「变基」合并（历史更整洁；团队有约定再用，见第 10 章）
节奏团队铁律一句话：push 之前先 pull。就像发朋友圈前先刷一下别人的动态，避免「撞车」被拒绝推送。

8.8 参与别人的项目：Fork + Pull Request

直接 push 别人的仓库？不行（谢天谢地）。开源世界的正确姿势是「复印 → 改 → 发合并请求」：

  1. Fork（叉走）：在别人仓库页右上角点 Fork——把整个仓库复印一份到你自己的账号下。
  2. Clone 你的复印版：照 8.6 克隆你账号下那个仓库到本地，正常建分支、改代码、提交。
  3. Push 到你的复印版：git push origin feature-xxx，改动上云。
  4. 发起 Pull Request（PR）：回到你的仓库页面，点 Compare & pull request，写清楚「我改了什么、为什么」，提交给原作者。
  5. 等作者审核：作者点头点 Merge，你的改动就正式进入了原仓库——恭喜，你是开源贡献者了。
类比Fork = 把书店的书整本复印回家随便做笔记；PR = 把你批注好的版本寄给原作者说「我有些改进建议」；作者觉得好，就吸收进下一版正式发行。Gitee 上同款流程叫「Pull Request / 合并请求」。

8.9 远程分支的管理

终端
git branch -a               # 列出所有分支：-a 含远程分支（红色的 remotes/origin/xxx）
git switch dev              # 本地没有 dev 时，Git 会自动按同名远程分支创建并跟踪
git push origin --delete dev  # 删除云端上的 dev 分支（本地分支不受影响）
git remote show origin      # 查看远程仓库的详细信息（有哪些分支、跟踪关系如何）

标签与储藏

给里程碑贴金标签，把半成品塞进抽屉——两个日常高频的小神器

本章两个工具都不难，却常常被初级教程忽略——而真实工作里你几乎每周都会用到它们。双平台通用

9.1 标签 git tag：相册里的金箔书签

某次提交特别重要——「v1.0 正式上线了！」「论文盲审版送出去了！」——给这个时刻贴一张不会移动的标签，以后一喊名字就能瞬间定位，不用去背 a1b2c3d 这种天书编号。

类比提交号像图书馆的索书号（精确但没人记得住），标签就是书脊上烫金的书名。分支名会随提交移动，标签永远钉死在那张照片上。
终端
git tag                              # 列出所有标签（按字母排序）
git tag v1.0.0                       # 给「当前提交」打一个轻量标签（只是个书签，不带说明）
git tag -a v1.0.0 -m "第一个正式版！"  # 打「附注标签」：带说明、日期、作者（推荐日常用这种）
git tag -a v1.2.0 a1b2c3d -m "补打"  # 给历史中的某次提交补打标签（编号来自 git log）
git show v1.0.0                      # 查看标签指向的那次提交详情
git tag -d v1.0.0                    # 删除本地标签（打错了随手删，无副作用）
注意标签不会随 git push 自动上传！要单独推： git push origin v1.0.0 推一个，或 git push origin --tags 一把全推。
终端
git push origin v1.0.0               # 把指定标签推送到云端
git push origin --delete v1.0.0      # 删除云端上的标签
git checkout v1.0.0                  # 「翻看」历史版本：进入只读的过去（看完记得切回来）
git switch -                         # 从历史版本切回原来的分支（用完历史，回到当下）

9.2 储藏 git stash：桌面太乱，先塞抽屉

经典场景：功能写到一半、改了一堆文件还没提交，老板突然喊「线上炸了，立刻修！」。这时候既不能把半成品提交上去（脏），也不能切换分支（Git 会拦住你或把改动带过去乱套）。——把它们整个塞进抽屉：

终端
git stash                    # 把工作区和暂存区所有未提交的改动「整体收进抽屉」，桌面瞬间清爽
git stash push -m "登录页写到一半"  # 收纳时贴个标签，方便之后认领是哪一摊活
git stash list               # 看看抽屉里收了哪几摊（stash@{0} 是最新塞进去的）
git stash pop                # 取出「最新那一摊」并从抽屉删除记录（最常用：救完火回来继续干活）
git stash apply stash@{1}    # 取出指定的一摊，但抽屉里继续保留（想在多处复用同一份改动时）
git stash drop stash@{0}     # 扔掉抽屉里指定的一摊（确认不要了）
git stash clear              # 清空抽屉（不可恢复，慎用）
类比客人突然来访，书桌上一堆摊开的手稿：全部原样码进抽屉（stash），桌面立刻体面；客人走了再原样摊回桌面（pop），接着写——一字不差。
动手练习 04
  1. 随便改两个文件不提交，git stash 后用 git status 感受「桌面突然干净」；
  2. git stash pop 取回来，确认改动一字不少；
  3. 给你的 main 分支打上 v0.1-practice 附注标签并推送到远程，去仓库页面看看 Releases 旁边是否亮起了标签。

进阶操作

摘樱桃、整理时间线、追查真凶、二分捉虫——高手都在用的四板斧

基础三件套（提交、分支、远程）已经能应付 90% 的日常。剩下 10% 的疑难杂症，靠本章四件兵器。双平台通用

10.1 摘樱桃：git cherry-pick

场景：dev 分支上有 5 笔提交，其中只有一笔修 Bug 的改动是 main 现在急需的，其他 4 笔还没做完。整支合并？不行。把那一笔「摘」过来：

终端
git switch main                # 先切到「接收成果」的分支
git cherry-pick a1b2c3d        # 把那次提交原样复制一份，落到当前分支（新提交、新编号）
git cherry-pick a1b2c3d e4f5g6h  # 连摘两颗：依次写多个编号，空格隔开
git cherry-pick -n a1b2c3d     # 只应用改动、不自动提交（-n = --no-commit，方便再加工）
类比别人的果树上结了一颗特别甜的樱桃——不必买下整棵树（merge），只把这一颗嫁接到自家树上（cherry-pick）。紧急修 Bug 时它是救命的快枪。

10.2 整理时间线：git rebase

merge 合并会在历史上留下「打结」的轨迹；rebase（变基）则是把你的提交整串摘下来、重新串到对方的最新提交之后，让历史变成一条清爽的直线。

对比项git mergegit rebase
历史形状有分叉、有结，真实还原协作过程一条直线，干净漂亮
做法新增一张「合并提交」照片把你的提交「搬走重拍」，编号全变
安全性只加不改，绝对安全改写历史——公共分支上禁用
适用合并公共分支（main ← feature）同步最新代码、整理自己私人分支
终端
git switch feature-x          # 进入自己的功能分支（rebase 只在自家院子里整）
git rebase main               # 把本分支的提交整体搬到 main 最新提交之后（时间线变直线）
git rebase --continue         # 搬家途中遇冲突：解决后用它继续搬（不用手动 commit）
git rebase --abort            # 搬砸了：一键回到 rebase 开始前的样子（后悔药常备）
git pull --rebase             # 拉取远程更新时顺便变基：push 前历史自动理顺（推荐习惯）
黄金法则rebase 只能收拾自己已经摊开、别人还没看过的东西。凡是 push 过、别人可能基于它工作的分支，一律禁止 rebase——否则等于把别人手里的相册抽页重排，天下大乱。

10.3 查真凶：git blame

看到一行奇葩代码，想知道谁、什么时候、在哪次提交写的？一行命令，全招了：

终端
git blame readme.txt          # 逐行标注：每行的最后修改者、提交号、日期，一览无余
git blame -L 5,12 readme.txt # 只看第 5 到 12 行（-L 起,止，聚焦可疑区域）
a1b2c3d (小王 2026-09-01 10:20:01 +0800  1) 这是我的第一个 Git 项目   ← 第 1 行的「出生证明」
类比blame（直译「怪罪」）是给每一行代码办出生证明。注意礼仪：查明真相是为了理解上下文，不是为了甩锅——很多「凶手」其实是在修更早的坑。

10.4 二分捉虫：git bisect

场景：项目突然出 Bug，但最近有 100 笔提交，不知道是哪一笔引入的。逐笔回退测试？太傻。bisect 用二分查找：每次跳到中间版本让你测一下「好坏」，范围对半砍——1000 笔提交最多 10 次就能锁定元凶。

类比猜 1~100 之间的数字，每次都猜中间数：「大了」「小了」……七次必中。bisect 就是让 Git 和你玩这个游戏，只不过猜的是「哪笔提交引入了 Bug」。
终端
git bisect start             # 宣布：捉虫行动开始
git bisect bad               # 标记当前版本「有虫」（Bug 现在就能复现）
git bisect good v1.0.0       # 标记 v1.0.0「无虫」（那时还好好的；Git 随即跳到中间版本）
# —— 你现在测试中间版本，然后继续报告 ——
git bisect good              # 中间版本没虫 → 元凶在更新的另一半，Git 继续折半
git bisect bad               # 中间版本有虫 → 元凶在更老的另一半
# —— 几轮之后，Git 打印出「元凶是 xxxx 提交」——
git bisect reset             # 收工：回到捉虫前所在的分支（别忘这步！）
配合找到元凶提交后，用 git show 提交号 看它改了什么、git blame 找到作者请教，或用 git revert 直接抵消它——组合拳闭环。

13.1 提交的艺术：小步提交 + 走心说明

每笔提交应该是一个独立、完整、能说清自己的最小改动单元。对比一下：

坏提交（看不懂）好提交（一眼看懂）
修改修复：登录页在 Safari 下按钮错位
更新了一些东西新增：用户头像上传并裁剪功能
aaa文档：补充 Linux 安装步骤说明
一次提交塞了 30 个文件的五件事五件小事拆成五笔提交，各自说明

业界广泛使用 Conventional Commits（约定式提交）规范：说明以「类型」开头，一眼分类：

前缀含义示例
feat:新功能feat: 支持深色模式切换
fix:修 Bugfix: 修复首页白屏问题
docs:只改文档docs: 更新 README 安装说明
style:格式调整（不改逻辑）style: 统一缩进为 4 空格
refactor:重构（不改功能）refactor: 抽取登录逻辑为公共模块
test:测试相关test: 补充登录接口单元测试
chore:杂务（依赖、配置）chore: 升级依赖包版本

13.2 绝对不要提交的东西

  • 密码、密钥、 token：提交历史是「永久」的，删掉提交也很难保证清干净（.git 里的旧快照还在）——真泄密了，唯一正解是立刻轮换密钥，而不是删文件；
  • 依赖文件夹（如 node_modules/）：动辄几万个文件，队友拿到代码自己装即可；
  • 构建产物（dist/、.exe）：由源码随时生成，进历史纯属浪费；
  • 日志、临时文件、编辑器私有配置（.idea/、.vscode/ 视团队约定）。
好习惯新项目第一笔提交就放好 .gitignore（各语言模板搜「gitignore templates」现成可抄）——防泄密从第一天开始，成本最低。

13.3 团队协作的日常节奏

类比把协作想象成「合租一间厨房」：早上进门先看一眼冰箱（pull），做饭勤收拾（小步提交），睡前把公共区域归位（push），想大动灶台先占个标签（开分支）。
  1. 开工先拉：git pull，和云端对齐再动手；
  2. 活儿拆小：一个功能一条 feature/ 分支，别在 main 上直接写；
  3. 勤提交：完成一小块就 add + commit——commit 是免费的保险，提交越勤「后悔药」越新鲜；
  4. 收工必推：git push 上云——电脑丢失 / 硬盘罢工时，你会感谢今天的自己；
  5. 推送前再拉一次：有人抢先推了就先合并，避免被拒；
  6. 合并走正规流程：功能分支合入 main 前最好过一道 PR / 代码评审，多双眼睛少个 Bug。

第 15 章

实战续：把网站真正发布上线（GitHub Pages 全流程）

第 11 章带你实现了一次「本地 → GitHub」的完整推送。这一章是它的续集：我们做的静态网站（比如你自己的教程站），能不能像真正的网站一样，用一个网址在浏览器里访问？答案是可以——用 GitHub Pages。这一章完整体现了个人教程站从"本地文件夹"到"线上网址"的真实流程，也是本教程站本身的搭建方式。

15.1 先搞清楚：Git 上传 ≠ 网站上线

关键执行完 git push，代码确实到了 GitHub，但它还只是"躺在仓库里的文件"。要让别人（或你自己）用浏览器访问，需要额外一步「开启站点服务」。这一步就是 GitHub Pages——GitHub 免费给每个仓库提供的静态网页托管。
  • 你的资料托管在 GitHub 上；
  • GitHub Pages 从仓库里挑一份文件当"首页"，用 https://用户名.github.io/仓库名/ 提供出来；
  • 整个过程免费、无需数据库、无需自己买服务器。

15.2 两种仓库名，决定你的网址长短

仓库名部署后网址说明
你的用户名.github.iohttps://你的用户名.github.io/个人站点，一个账号只能有一个，网址最短
其他名字（如 wx）https://你的用户名.github.io/wx/项目站点，可建很多个

不管是哪种，所有内部链接、CSS/JS 引用都必须用相对路径（如 docs/xxx.html），不能以 / 开头，否则部署在子路径时会 404。

15.3 本地准备：建一个纯静态站点

网站本质就是一堆 HTML / CSS / JS 文件加一张"清单"。例如在项目根目录建：

项目结构示意
教程站/                   ← 本地项目根目录（也是一个 git 仓库）
├── index.html             ← 首页
├── assets/
│   ├── style.css
│   └── app.js             ← 前端逻辑（渲染目录卡片、搜索过滤）
├── data/
│   └── manifest.json      ← 教程清单（标题/简介/分类/路径）
└── docs/                  ← 教程正文 html

15.4 用 git 推到 GitHub（你已会的部分）

这条和第 3、5、8、11 章讲的完全一致，一气呵成：

终端：把整个站点推上 GitHub
git init                                  # 1. 在当前文件夹初始化仓库（一次即可）
git branch -M main                        # 2. 确保默认分支叫 main（GitHub 默认分支名）
git add .                                 # 3. 登记全部文件
git commit -m "首次提交：搭建教程站"        # 4. 提交一个快照
git remote add origin https://github.com/你的用户名/你的仓库名.git   # 5. 连接远程仓库
git remote -v                             # 6. 确认远程地址（可选）
git push -u origin main                   # 7. 首次推送，-u 记下默认推送目标
凭证推送时 GitHub 已经不再支持输账号密码。它会弹出浏览器授权，或在命令行要求输入「用户名 + Personal Access Token（PAT）」。token 在 GitHub: 头像 → Settings → Developer settings → Personal access tokens → Generate new token (classic)，勾选 repo 后生成的一串 ghp_...。

15.5 关键一步：开启 GitHub Pages

网页操作（浏览器点一点，不是命令）
  1. 打开仓库网页 https://github.com/你的用户名/仓库名；
  2. 点顶栏 Settings；
  3. 左侧菜单找 Pages（在 "Code and automation" 分组下，比较靠下）；
  4. Source 选 "Deploy from a branch"；
  5. Branch 选 main，目录选 / (root)；
  6. 点 Save，等待约 1~2 分钟构建；
  7. 页面顶部出现 Your site is ready to be published at https://你的用户名.github.io/仓库名/。
类比git push 是把"相册"整体扛到 GitHub 的储藏室；开启 Pages 则是把其中一册放到橱窗上，路人（浏览器）通过橱窗玻璃就能直接看到。推送 ≠ 上橱窗，两件事都要做。

15.6 访问与代码更新

  • 访问根网址后会默认展示仓库里的 index.html（首页）。
  • 更新内容：改完本地文件后 git add . && git commit -m "更新" && git push，等 1 分钟左右站点自动更新（刚 push 完立即刷新可能短暂 404，稍等即可）——比 Gitee 那种"要在网页手动点更新"的体验顺畅得多。
  • 新加一篇教程：把 html 放进仓库的 docs/ 目录，在 manifest.json 里加一行记录，再推送，首页目录卡片会自动出现。
