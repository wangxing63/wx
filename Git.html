01开始之前

先花两分钟搞清楚 Git 到底帮你解决什么麻烦。

你一定遇到过的场景

写一份文档或者一个作业，改到最后文件夹里变成这样：

不用 Git 的时候，文件夹长这样示意
报告.docx
报告-最终版.docx
报告-最终版2.docx
报告-真的最终版.docx
报告-给老师看的最终版.docx
报告-最终版2-改.docx  ← 到底哪个才是最新的？昨天改的那段去哪了？

问题有三个：不知道哪个最新、删掉的内容找不回来、两个人同时改会互相覆盖。Git 就是专门解决这三个问题的工具。

打个比方（全书只用这一个）

把 Git 想成一台会自动给文件夹拍照片的相机。你每完成一件小事，就按一次快门存一张「存档照」。以后想看某天文件夹长什么样，把那张照片调出来就行；改坏了，直接把照片里的状态恢复回来。整本书都只用这个说法，不用记别的比喻。

Git 和 GitHub 不是一回事

名字是什么装在哪
Git一个软件，负责拍存档照、回退、开分支。不联网也能用。你的电脑里
GitHub一个网站，负责把照片存到云上、给别人看、多人协作。类似网盘，但专门放 Git 仓库。互联网上
Gitee / GitLab和 GitHub 同类的网站，只是国内／自建的选择，用法几乎一样。互联网上

所以：前 7 章完全不联网，你自己一个人就能练完。第 8 章才需要注册 GitHub。

2026 年，你该按哪套写法学

老教程常见写法本教程用的现代写法为什么
master（默认分支名）mainGitHub、GitLab 和 Git 官方都已把新仓库默认分支定为 main
git checkout 分支名git switch 分支名switch 只管切分支，意思单一，新手不会误用
git checkout -- 文件git restore 文件restore 只管恢复文件，看名字就知道在干嘛
git push 时输账号密码访问令牌 PAT 或 SSH 密钥GitHub 已停用密码推送，密码怎么输都会失败
git init 后再改名git init -b main建仓库时直接指定分支名，一步到位
检查点

读完这章，你只需要记住一句：Git 是装在电脑里、给文件夹拍存档照的软件。下面开始动手。

2.2 认识一下命令行

别怕黑窗口。它其实只做一件事：你打一行字，按回车，它执行并回一段话。

先记住 4 个和 Git 无关、但天天要用的小命令：

命令逐词意思作用
pwdprint working directory＝打印工作目录告诉我「我现在在哪个文件夹」
lslist＝列出列出当前文件夹里有什么
cd 文件夹名change directory＝切换目录走进某个文件夹
mkdir 文件夹名make directory＝新建目录新建一个文件夹
新手最容易卡住的地方

cd 后面跟的文件夹必须真的存在，而且路径写错一个字就会报 No such file or directory（没有这个文件或目录）。不确定时先敲 pwd 看自己在哪，再敲 ls 看有哪些文件夹可进。

切换目录的完整方法（含中文名、空格、跨盘符）

cd 文件夹名 有个前提：那个文件夹必须就在你当前所在的目录里面。如果你想去的文件夹在别处，就要写「从盘符开始的完整路径」，或者先退到上一级再进。

Git Bash · 切到任意文件夹的通用套路逐行敲，每行回车
$ pwd
#  print working directory；先看清楚「我现在站在哪」
$ ls
#  list；看当前目录里有哪些文件夹可以进（中文名会直接显示）
$ cd /c/Users/Administrator/Desktop/git教程
#  绝对路径：从盘符写全，跟你现在在哪无关，一步到位
$ pwd
#  再确认一次；应显示 /c/Users/Administrator/Desktop/git教程
写法意思 / 什么时候用
cd git教程进入当前目录下叫 git教程 的子文件夹；中文名可以直接写，不用加引号
cd .... ＝上一级目录；退回上一层
cd ~~ ＝家目录（Windows 上通常是 /c/Users/你的用户名）；一秒回家
cd ~/Desktop/git教程从家目录出发写相对路径，比写全一串短很多
cd /c/Users/Administrator/Desktop/git教程绝对路径；/c/ 表示 C 盘，斜杠用正斜杠 /，不是反斜杠 \
cd /d/项目名去 D 盘；Git Bash 里盘符写成 /c/、/d/，不写 D:\
cd "我的 项目"名字里有空格时，必须用英文双引号把整个路径包起来，否则会被当成两个参数
cd git 然后按 Tab让终端自动补全文件夹名，中文名、长名字都不用手打，也不会打错
cd -一个减号＝切回刚才所在的那个目录，两个目录来回跳很省事
两条会直接报错的写法，别敲

① cd change git教程 / cd = change git教程 → 报 bash: cd: too many arguments。原因是 cd 只接受一个参数；change directory 是注释里的英文翻译、= 是「意思是」，都不是命令。
② 当前目录下没有这个文件夹却写 cd git教程 → 报 No such file or directory。先 ls 看有没有，没有就先 cd .. 退上去，或者直接用绝对路径。

检查点

敲 pwd，显示的路径末尾是你想去的文件夹名（例如 .../Desktop/git教程），提示符里那段紫色/蓝色路径也跟着变了 → 切换成功。路径前缀是 ~、/c 还是 /c/Users/... 都正常，取决于你一开始站在哪。

2.3 三条一次性配置

Git 每次存档都要记下「谁存的」，所以第一次用要先报上名字和邮箱。这三条一台电脑只做一次，以后所有仓库都自动带上。

Git Bash / 终端 · 一行一行敲，每行敲完按回车把名字邮箱换成你自己的
$ git config --global user.name "张三"
$ git config --global user.email "zhangsan@example.com"
$ git config --global init.defaultBranch main
三行敲完不会有任何提示，这是正常的——Git 默认「没消息就是好消息」。
git config --global user.name "张三"
git程序名，每条 Git 命令的固定开头。（英文里是「家伙」的俚语，只是软件名，不用记）
configconfiguration 的缩写＝配置。改 Git 的设置。
--globalglobal＝全局。这条设置对你这台电脑上所有仓库都生效；去掉它就只对当前仓库生效。
user.nameuser＝用户，name＝名字。合起来＝「存档时署谁的名」。
"张三"你起的署名。引号里的空格要靠这对英文双引号包住，必须是英文引号。
user.emailemail＝邮箱。存档时留的联系邮箱，随便填能收到信的即可，本地练习不校验。
init.defaultBranchinit＝初始化，default＝默认，Branch＝分支。合起来＝「以后新建仓库，主分支默认叫 main」。2026 年的标准写法，装上就设好，省得以后改名。
检查点：确认配置写进去了 
$ git config --global --list
#  list = 列出；把刚才存的所有设置打印出来看看

能看到 user.name=张三、user.email=...、init.defaultbranch=main 三行，就成功了一半。

03第一次提交（手把手）

这一章不要问「为什么」，照着敲就行。敲完你就已经会用 Git 了，原理放到第 4 章再讲。

1建一个练习文件夹，并走进去

打开 Git Bash，敲下面两行（每行回车）。只敲带蓝色 $ 的两行，绿色注释是讲解、不要敲：

Git Bash只敲 $ 开头的两行
$ mkdir my-first-repo
#  mkdir 是 make directory 的缩写，意思是「新建文件夹」；my-first-repo 是我起的文件夹名
$ cd my-first-repo
#  cd 是 change directory 的缩写，意思是「切换目录」；后面只跟一个文件夹名
#  上面两处英文都只是翻译，不要敲进终端；等号、空格也都不是命令的一部分
你会看到（下面两种都对，取决于你一开始站在哪）
■ 情况 A：从家目录开始（提示符是 ~）
user@pc ~ $ mkdir my-first-repo
user@pc ~ $ cd my-first-repo
user@pc ~/my-first-repo $   ← 末尾多了 my-first-repo，成功

■ 情况 B：从 C 盘根目录开始（提示符是 /c，很多人的实际情况）
Administrator@WIN-xxx MINGW64 /c
$ mkdir my-first-repo
Administrator@WIN-xxx MINGW64 /c
$ cd my-first-repo
Administrator@WIN-xxx MINGW64 /c/my-first-repo   ← 末尾多了 my-first-repo，成功
关键：路径前缀不一定是 ~。你在哪建的文件夹，提示符就显示哪：从家目录开始是 ~/my-first-repo，从 C 盘根开始是 /c/my-first-repo，从桌面开始是 /c/Users/.../Desktop/my-first-repo。只要末尾变成 my-first-repo，就说明走进去了。
mkdir 和 cd 成功时不会打印任何文字，只有提示符变了——这是正常的，别以为没执行。
检查点：不确定就问一句
$ pwd
#  打印当前完整路径；末尾是 my-first-repo 就对了

如果显示还在上一级，说明没进去；重敲一次 cd my-first-repo。想切到别处（比如桌面上的 git教程 文件夹），见 2.2 节「切换目录的完整方法」。

2让 Git 接管这个文件夹
Git Bash · 当前在 my-first-repo 里核心命令
$ git init -b main
#  init   = initialize 初始化；把这个文件夹变成「Git 能管的仓库」
#  -b     = branch 分支（b 是缩写）；后面跟分支名
#  main   = 给主分支起的名字，2026 年的标准默认名
#  合起来：初始化仓库，并且一开始就把主线叫 main
git init -b main
git程序名，固定开头。
initinitialize＝初始化。在这个文件夹里生成一个隐藏的 .git 文件夹，之后所有存档照片都存在它里面。
-bbranch 的缩写＝分支。一个减号开头的短选项，后面要接一个值。
main主线分支的名字。写成 master 也能用，但 2026 年主流平台统一用 main。
你会看到
Initialized empty Git repository in C:/Users/.../my-first-repo/.git/
Initialized＝已初始化；empty Git repository＝空的 Git 仓库；.git/＝那个隐藏文件夹。
意思是：相机已经架好，但一张照片都还没拍。
看不见 .git 文件夹？

它是隐藏的，Windows 资源管理器默认不显示，这很正常。想验证就敲 ls -a（-a = all 全部，把隐藏文件也列出来），能看到 .git 就对了。永远不要手动去改或删这个文件夹。

3造一个文件出来

Git 是给「文件」拍照的，得先有东西可拍。用最简单的方式建一个文本文件：

Git Bash也可以用记事本手写，效果一样
$ echo "我的第一个 Git 项目" > readme.txt
#  echo  = 回声／输出；把引号里的文字打印出来
#  >     = 重定向符号；把本来要打印到屏幕的文字，改写成「存进后面那个文件」
#  readme.txt = 文件名；不存在就自动新建
$ ls
#  ls = list 列出；确认文件真的建出来了
你会看到

这一步等于把要拍的东西摆到桌上。桌上有东西了，但相机还没拍，Git 目前只当它「没登记过」。

4问一句：现在什么情况？

git status 是你会敲得最多的一条命令，意思是「告诉我现在的状况」。任何时候迷路了就敲它。

Git Bash随时可用，不会改任何东西
$ git status
#  status = 状态；查看此刻仓库里每个文件处于什么状态
你会看到（逐行翻译在下面）
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        readme.txt

nothing added to commit but untracked files present (use "git add" to track)
On branch main＝你现在站在 main 这条主线上。
No commits yet＝还没有任何存档照（一张都没拍）。
Untracked files＝未跟踪的文件：Git 看见了 readme.txt，但还没登记它。
use "git add ..." to include ...＝提示你：想把它算进下一次存档，就用 git add。
nothing added to commit but untracked files present＝待拍清单是空的，因为还有文件没登记。
打个比方

相机说：「桌上有个 readme.txt，但我没把它放进待拍清单，待会儿按快门不会拍到它。」红色的文件名＝还没进清单。

5把文件放进「待拍清单」
Git Bash核心命令
$ git add readme.txt
#  add   = 添加；把指定文件登记进「下一次要拍的清单」
#  readme.txt = 要登记的文件名，换成你自己的文件名即可
git add readme.txt
git程序名，固定开头。
add添加。英文原义就是「加进去」。这里＝把文件从「桌上」挑进「待拍清单」。
readme.txt路径／文件名。路径里有空格时要用英文引号包起来，例如 git add "我的 文档.txt"。
再敲一次 status 看看变化
$ git status
On branch main
No commits yet
Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   readme.txt
Changes to be committed＝已经列进待拍清单的改动。
new file: readme.txt＝新建一个文件，已进清单。
关键变化：readme.txt 从红色变成绿色了——绿色＝快门按下时会被拍进去。
打个比方

这一步是把要入镜的东西挑出来摆进取景框。桌上别的东西不摆进去，就不会被拍到。这也是为什么 Git 要分两步：让你能自己决定「这一张照片拍哪些改动」。

以后再看：一次把很多文件加进清单（现在不用敲） 
$ git add .
#  . = 当前目录；把当前文件夹里所有变动一次性加进清单（最常用）
$ git add *.txt
#  * = 通配符；只加所有 .txt 结尾的文件
$ git add -A
#  -A = All 全部；连删除的文件也一起登记，比 . 更彻底

插曲：Windows 上 git add 时的黄色换行符警告（没看到可以直接跳过）

这一节专讲 Windows + Git Bash 下跟着第 3 章操作时最常冒出来的一条黄字。它不是报错，文件也没坏，add 已经成功了；看完可以直接回步骤 6 继续 commit。

① 你会看到什么

执行 git add readme.txt 之后（截图里的原文）
$ git add readme.txt
warning: in the working copy of 'readme.txt', LF will be replaced by CRLF
the next time Git touches it.
warning＝警告（不是 error 错误）；in the working copy of 'readme.txt'＝在 readme.txt 这份「桌面上的副本」里；
LF＝Line Feed「换行」，写作 \n，是 Linux / macOS / Git 仓库内部的行尾；

② 为什么偏偏在这里出现

← echo 生成的是这个 我的第一个 Git 项目\r\n CRLF（\r\n）＝Windows 记事本　← 系统习惯的是这个 桌面（工作区） Windows 想要 CRLF 仓库（相册） Git 统一存 LF 再取回桌面 自动换回 CRLF git add CRLF→LF checkout LF→CRLF 链条：用 Git Bash 的 echo "..." > readme.txt 建文件 → 写出来是 LF；而 Windows 装 Git 时默认 core.autocrlf=true（自动转换），约定「仓库存 LF、桌面按系统习惯」。 于是 add 时 Git 发现「这份工作副本是 LF，但按配置以后取回应是 CRLF」，就打了这条招呼。纯提示，不改内容、不阻止提交。
打个比方

同一张纸，Windows 的打印机在每行末尾习惯多盖一个「回车」章；Git 把纸收进相册时统一把章擦掉，取回 Windows 桌面时再盖回去。这条黄字就是打印机提前告诉你：「下次我会盖章，别奇怪」。纸上的字一个没变。

关于 --hard，说清楚但不拦着你

git reset --hard HEAD~1 会把桌面上的文件也强行改回旧版，尚未 commit 的改动会消失且不在 reflog 里，找不回来。
要用就先敲 git status 确认是干净的，再执行。刚 reset 完想反悔，立刻敲 git reflog 找到刚才那一串编号，用 git reset --hard 编号 就能回去——reflog 是 Git 给的最后一道保险。

本章检查点

随便改一下 readme.txt，练一遍 git restore readme.txt，再敲 git status 看到「干净」。能把改动撤销回来，就说明你真的理解三个区了。

07分支与合并

主线先放着不动，另开一条线随便试，试好了再并回来。这是 Git 最有用的功能，也是协作的基础。

7.1 为什么需要另开一条线

假设你想给项目加一个新功能，但改到一半不确定好不好。直接在主线上改，会把能用的版本弄乱。分支的做法是：照着当前照片复制一条新线出来，在新线上随便折腾，主线一点不受影响。

打个比方

相册里同一页开始，另起一册草稿本接着画。草稿本怎么涂都不影响正式那册；画得满意，把草稿本上的成果誊回正式册（这叫合并）；画废了，把草稿本一合扔掉就行。

7.2 手把手：开一条分支、改点东西、并回来

1先确认你现在站在主线上
$ git status
#  看到 On branch main 就对了
2新建并立刻切到一条分支
Git Bash核心命令
$ git switch -c feature-about
#  switch = 切换；换到另一条分支上站好
#  -c     = create 创建；顺手把这条分支新建出来
#  feature-about = 我起的分支名，建议用「用途」命名，别用中文和空格
git switch -c feature-about
switch英文原义切换（开关）。只负责「换一条分支站上去」，不碰文件内容以外的东西。2026 年官方推荐用它替代 git checkout 分支名。
-ccreate 的缩写＝创建。不加 -c 是「切到已存在的分支」，加了是「新建并切过去」。
feature-about分支名。feature＝功能，about＝关于。团队习惯用 feature/xxx、fix/xxx 这类前缀；自己练随便起。
你会看到
Switched to a new branch 'feature-about'
Switched to＝已切换到；a new branch＝一条新分支。现在你站在草稿本上了。
3在这条分支上改东西、拍一张
$ echo "关于我：正在学 Git" > about.txt
#  新建一个文件；> 是覆盖写入，>> 是追加
$ git add .
#  . = 当前目录；把这次所有变动加进清单
$ git commit -m "新增关于页面"
#  在 feature-about 这条线上拍一张新照片
亲眼看一下「两条线不一样」

现在敲 ls，能看到 about.txt。接着敲 git switch main 切回主线，再敲 ls——about.txt 不见了！因为它只存在于草稿本那条线上。再敲 git switch feature-about，它又回来了。这个「文件内容自动跟着分支变」的现象，是理解分支最直观的一步，一定要亲手试。

4切回主线，把成果并回来
Git Bash合并一定先切回「要并进去的那条线」
$ git switch main
#  先回到 main（接收方）
$ git merge feature-about
#  merge = 合并；把 feature-about 这条线上的成果并进当前所在的 main
git merge feature-about
merge英文原义融合／合并。把另一条分支的改动接到当前分支上。
feature-about被并进来的那条分支名。顺序很重要：先 switch main 站到接收方，再 merge 别的分支。
你会看到
Updating a1b2c3d..f7g8h9i
Fast-forward
 about.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 about.txt
Fast-forward＝快进：main 自己没往前走过，Git 只要把 main 的指针直接挪到草稿本最新那张就行，不用额外拍合并照。没有冲突，最省事的一种合并。
5看图确认，顺手删掉用完的分支
$ git log --oneline --graph --all
#  --graph = 画成线图；--all = 所有分支一起画
$ git branch -d feature-about
#  branch = 分支；-d = delete 删除；已合并过的分支可以安全删掉

7.3 冲突：两个人改了同一行

如果两条线都改了同一个文件的同一行，Git 不敢替你选，会停下来让你自己定。别怕，它把两边内容都摆在文件里了。

1亲手制造一次冲突（练手，故意的）
Git Bash · 在 main 上照敲即可，出错正是我们要练的
$ git switch -c team-a
#  新建并切到 team-a 分支
$ echo "标题：小明写的主页" > title.txt
$ git add . && git commit -m "A 写标题"
#  && = 「前一条成功了才执行后一条」，把两条命令串成一行
$ git switch main
#  回到主线（注意：一定要切回去，别在 team-a 上继续）
$ echo "标题：小红写的主页" > title.txt
$ git add . && git commit -m "B 写标题"
现在两条线各拍了一张、都新建了 title.txt，但内容不同。下一步合并必然冲突。
2合并，看冲突长什么样
$ git merge team-a
你会看到
Auto-merging title.txt
CONFLICT (add/add): Merge conflict in title.txt
Automatic merge failed; fix conflicts and then commit the result.
Auto-merging＝正在自动合并；CONFLICT＝冲突；add/add＝两边都新增了同名文件；
Merge conflict in title.txt＝title.txt 这个文件有冲突；
fix conflicts and then commit the result＝把冲突改好，然后再 commit 一次。
注意：这不是报错，是 Git 在等你做决定，此时什么东西都没坏。
3打开文件，你会看到这样的标记
用记事本打开 title.txt，内容如下（不是命令，别敲）
<<<<<<< HEAD
标题：小红写的主页
=======
标题：小明写的主页
>>>>>>> team-a
三行标记把两种版本隔开：上＝当前分支（HEAD，也就是 main），下＝要并进来的分支，中间 ======= 是分界线。
4解决它：改文件 → 加清单 → 拍合并照
先用记事本把上面三行标记删掉、内容改好并保存然后回终端
$ git add title.txt
#  告诉 Git：这个文件我已经改定了，冲突解决了
$ git status
#  应看到 All conflicts fixed but you are still merging（冲突都解决了，还差最后一次提交）
$ git commit -m "合并两条标题，解决冲突"
#  拍下这张「合并照」，合并到此结束
检查点

再敲 git status 显示 working tree clean，敲 git log --oneline --graph --all 能看到两条线汇到一起，就成功了。

2026 新增：更安全的解决冲突方式（Git 2.56）

老办法 git add . 有个隐患：如果桌面上还有跟冲突无关的其他改动，会被一起塞进清单；万一某个文件里还留着冲突标记，也会稀里糊涂提交进去。
Git 2.56 加了 git add --resolved：只看真正冲突过的文件，还会先检查标记有没有删干净，没删干净就直接拒绝并告诉你哪个文件还有残留。

$ git add --resolved
#  --resolved = 已解决的；只暂存冲突文件，且自动检查残留标记
#  若没删干净会报：fatal: the following paths still have conflict markers: title.txt

注意：不能和 git add -A / -u 一起用。你用 2.55 或更老版本时，用传统的 git add 文件名 效果一样，只是没有自动检查。

打个比方

两本草稿本在同一行写了不同的字，负责誊抄的人不敢替你选，就把两种写法并排抄在纸上、画了条分界线，请你自己圈一个。你圈完、把分界线擦掉，他才继续誊。

08连上 GitHub

前 7 章全在你自己电脑里。这一章把相册备份到云上，顺便学会怎么把别人的项目拿下来。

push 是把你新拍的照片传上去；pull 是把别人新拍的照片取下来并接上。方向别记反：push 出、pull 进。

8.1 2026 年的登录方式：账号密码已经不能用了

先避开这个大坑

GitHub 早已停用「账号 + 登录密码」来推送代码。如果你在推送时输自己的登录密码，一定看到 Support for password authentication was removed / Authentication failed。改密码也没用，因为根本不是密码错了，是这个通道关了。必须用下面两种之一。

方式怎么做适合谁
① HTTPS + PAT
（最省事）		GitHub 网页 → 右上角头像 → Settings → 左下 Developer settings → Personal access tokens → Fine-grained tokens → Generate new token；权限只勾这个仓库的 Contents: 读和写，设个到期时间，生成后立刻复制（只显示一次）。推送时让输密码，把这一串令牌粘进去当密码。新手、临时电脑、公司网络屏蔽 SSH 时。Windows 装 Git 时自带的凭证管理器会帮你记住，只需输一次。
② SSH 密钥
（一劳永逸）		终端敲 ssh-keygen -t ed25519 -C "你的邮箱"，一路回车；用 cat ~/.ssh/id_ed25519.pub 打印公钥，粘到 GitHub 的 Settings → SSH and GPG keys → New SSH key；仓库地址改用 git@github.com:用户名/仓库.git 这种形式。自己长期用的电脑。配好之后推送再也不问密码。
SSH 方式的三条命令（选它才敲）每条都拆给你
$ ssh-keygen -t ed25519 -C "zhangsan@example.com"
#  ssh-keygen = SSH 密钥生成器；-t = type 类型，ed25519 是目前推荐的算法
#  -C = Comment 备注；后面那串只是给密钥贴个标签，一般写邮箱
$ cat ~/.ssh/id_ed25519.pub
#  cat = concatenate 查看文件内容；~ = 家目录；.pub = public 公钥（可以给别人的那个）
#  把打印出来的整行复制，粘到 GitHub 网页上
$ ssh -T git@github.com
#  -T = 不分配终端，只测试连接；看到 Hi 用户名! 就说明通了
怎么选

只想赶紧推上去 → 用 HTTPS + PAT，五分钟搞定。打算天天用 → 配一次 SSH，以后零输入。
令牌／私钥都不要写进代码或提交到仓库；令牌只显示一次，丢了就重新生成一个。

8.2 手把手：把本地仓库推上去

1在 GitHub 网页上建一个空仓库

登录 GitHub → 右上角 + → New repository → 填仓库名（比如 my-first-repo）→ 选 Public / Private → 不要勾选「Add a README file」「Add .gitignore」（我们要推的是本地已有内容，勾了会让两边历史对不上）→ 点 Create repository。

建好后会看到一页提示，找到类似这样一行地址，复制它：

https://github.com/你的用户名/my-first-repo.git     # HTTPS 形式（配 PAT 用这个）
git@github.com:你的用户名/my-first-repo.git         # SSH 形式（配密钥用这个）
.git 结尾只是仓库地址的后缀，不是文件类型；https:// 和 git@ 开头决定用哪种登录方式。
2给云端地址起个小名
Git Bash · 回到 my-first-repo 文件夹把地址换成你复制的
$ git remote add origin https://github.com/你的用户名/my-first-repo.git
#  remote = 远程；add = 添加；origin = 给这个远程地址起的默认小名
git remote add origin https://github.com/xxx/my-first-repo.git
remote英文原义遥远的／远程。这里作名词＝远程仓库，也就是云端那份相册。
add添加。登记一个新的远程地址（不是加文件）。
origin英文原义源头／起点。Git 圈子里约定俗成给「最主要的那个远程仓库」起的名字，改成别的也行，但大家都写 origin，建议照用。
https://....git仓库地址。git remote -v（-v = verbose 详细）可以随时查登记了哪些。
检查点

敲 git remote -v，能看到 origin 后面跟着 fetch 和 push 两行地址，就登记好了。此命令不联网、不传文件，只是记个地址。

3推上去
Git Bash第一次推送
$ git push -u origin main
#  push   = 推／上传；把本地相册里云端没有的照片传上去
#  -u     = upstream 上游；记住「本地 main 对应云端 origin/main」，以后只写 git push
#  origin = 上一步登记的那个远程小名
#  main   = 要推上去的本地分支名
git push -u origin main
push英文原义推。方向：本地 → 云端。
-uupstream 的缩写＝上游／跟踪关系。第一次推送时加上，等于告诉 Git「以后这个分支默认就往 origin/main 推」。只需加一次，之后再推直接写 git push。
origin推到哪个远程仓库（小名）。
main推哪条本地分支。格式永远是 push 远程名 分支名。
你会看到（第一次可能弹出登录框，按 8.1 节处理）
Enumerating objects: 6, done.
Writing objects: 100% (6/6), 512 bytes | 512.00 KiB/s, done.
To https://github.com/你的用户名/my-first-repo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
Enumerating / Writing objects＝正在打包、上传照片；[new branch] main -> main＝云端新建了 main 分支；
set up to track 'origin/main'＝跟踪关系已建立（就是 -u 干的事），以后直接 git push / git pull 就行。
检查点

刷新 GitHub 那个仓库的网页，readme.txt、about.txt 等文件都出现了，提交记录也在 → 推送成功。

8.3 把别人的项目拿下来：clone / pull / fetch

一点不动。 先看看，不合并 git pull pull＝拉／下载并合并 = fetch + merge 两步并一步， 云端新照片直接接到你 桌面正在用的分支上。 每天开工先敲它
三条命令逐词翻译按需使用
$ git clone https://github.com/别人/项目.git
#  clone = 克隆／复制；把远程仓库整包下载成一个新文件夹
#  执行完会多出一个「项目」文件夹，cd 进去就能用
$ git pull
#  pull = 拉；取回云端新提交并合并到当前分支（已建立 -u 跟踪关系后才能省略参数）
$ git fetch origin
#  fetch = 取回；只看不并，之后用 git log origin/main 或 git merge origin/main 决定怎么办
日常三步曲（背下这一条就够）

开工 git pull → 干活 git add . + git commit -m "说明" → 收工 git push。
多人协作时 push 之前先 pull：别人先推了新东西，你直接推会被拒绝（rejected / non-fast-forward），先 pull 把别人的接上、有冲突就按 7.3 节解决，再推就顺了。

8 章常见报错

① remote origin already exists → 已经登记过 origin 了，不用再 add；想改地址用 git remote set-url origin 新地址（set-url＝设置网址）。
② Authentication failed → 别输登录密码，回到 8.1 用 PAT 或 SSH。
③ rejected · non-fast-forward → 云端有你本地没有的照片，先 git pull 再 git push。
④ failed: could not read Username → 终端没能弹出登录框，改用 SSH 地址最省事。

09完整实战：从零到上线

把前面所有动作串成一条线，做一个能打开的真实小网页，最后推到 GitHub 并发布成网址。全程照敲，不用回头翻别的章节。

1新建一个项目文件夹并走进去
Git Bash · 打开就能敲逐行回车
$ mkdir my-site
#  mkdir = make directory 新建文件夹
$ cd my-site
#  cd = change directory 走进去；提示符路径会变成 ~/my-site
2写一个真实的网页文件

用记事本在这个文件夹里新建 index.html，把下面内容原样粘进去保存（注意文件名必须是 index.html，网页服务器默认找它）：

index.html 的内容（这是文件内容，不是命令）用记事本保存
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>我的第一个网页</title>
</head>
<body>
  <h1>你好，Git！</h1>
  <p>这个页面是用 Git 管理并发布上线的。</p>
</body>
</html>
不想用记事本也行，在 Git Bash 里敲 ls 确认文件存在即可；Windows 记事本保存时「保存类型」选所有文件，否则会变成 index.html.txt。
3初始化、拍第一张照片
$ git init -b main
#  init = 初始化；-b main = 主线直接叫 main
$ git status
#  应该看到红色的 index.html（还没进清单）
$ git add .
#  . = 当前目录全部变动，进清单
$ git commit -m "首次提交：搭建网页骨架"
#  -m = message 说明；按下快门
你会看到
[main (root-commit) 1a2b3c4] 首次提交：搭建网页骨架
 1 file changed, 10 insertions(+)
root-commit＝第一张照片；1 file changed, 10 insertions(+)＝1 个文件、新增 10 行。
4开一条分支，试着加点内容
$ git switch -c add-footer
#  switch -c = 新建分支并切过去（create 创建）
#  现在把 index.html 里 </body> 前面加一行：<p>页脚：2026 年</p>，然后保存
$ git add .
$ git commit -m "给网页加页脚"
检查点

敲 git log --oneline 能看到 2 行。此时 git switch main 切回主线，用记事本打开 index.html，页脚那行会消失——这正说明分支把两条线隔开了。

5合并回主线
$ git switch main
#  先站到接收方 main
$ git merge add-footer
#  merge = 合并；把 add-footer 的成果接进来
$ git log --oneline --graph --all
#  --graph 画线，--all 显示所有分支，确认两条线汇合了
你会看到（大意）
Updating 1a2b3c4..9z8y7x6
Fast-forward
 index.html | 1 +
6在 GitHub 网页上建空仓库

登录 GitHub → + → New repository → 仓库名填 my-site → 选 Public → 三个初始化选项都不要勾 → Create repository。复制它给你的地址，形如：

https://github.com/zhangsan/my-site.git
示例里 zhangsan 要换成你自己的 GitHub 用户名。若按 8.1 配了 SSH 密钥，就用 git@github.com:zhangsan/my-site.git 这种形式。
7登记地址并推送
Git Bash · 仍在 my-site 文件夹里把 zhangsan 换成你的用户名
$ git remote add origin https://github.com/zhangsan/my-site.git
#  remote add = 登记远程仓库；origin = 给它起的默认小名
$ git push -u origin main
#  push = 推上去；-u = upstream 记住对应关系，以后只写 git push
你会看到
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
看到 set up to track 就说明成功。第一次会弹登录，按 8.1 节用 PAT 或 SSH 处理。
检查点

刷新 GitHub 仓库网页，index.html 在文件列表里，点开能看到你写的 HTML → 云端备份完成。

8把网页发布成一个能访问的网址

还在 GitHub 那个仓库的网页上操作（这次不用敲命令）：

  1. 点仓库顶部的 Settings（设置）。
  2. 左侧栏找到 Pages，点进去。
  3. 在 Build and deployment 里的 Source 选 Deploy from a branch（从分支部署）。
  4. Branch 选 main，目录选 / (root)（根目录，因为 index.html 就在最外层），点 Save。
  5. 等 1～2 分钟，刷新页面，顶部会出现一行绿色网址：https://zhangsan.github.io/my-site/。
检查点

点开那个网址，浏览器显示「你好，Git！」→ 从空文件夹到线上网页，全程走完。

如果打开是 404

① 文件名必须是 index.html，且位于仓库根目录（不是套在某个子文件夹里）；② 分支要选 main；③ 刚保存要等一两分钟；④ 改了内容后要重新 git add . → git commit -m "更新网页" → git push，云端才会更新。GitHub 界面改版时，认准 Source / Branch 这两个词即可。

9以后每次改网页，只要三条
$ git add .
#  把改动挑进清单
$ git commit -m "改了标题"

10.2 status 的紧凑格式：两列字母到底什么意思

文件一多，git status 的长输出刷屏。用 -s 可以让每个文件只占一行，左边两列字母就是状态码。

Git Bash只看不改
$ git status -s
#  -s = short 简短（也可写 --short）；每个文件一行
你会看到（示意，一次出现好几种状态）

M  readme.txt

第一列＝清单（暂存区）的状态；第二列＝桌面（工作区）的状态。两列分开看就不会乱：
A ＝Added 已新增并进清单（绿色）；M ＝Modified 修改已进清单（绿色）；

MM＝进清单之后又改了一次（两边都有 M）；R ＝Renamed 改名；D ＝删除已进清单。

11.1 diff 到底在比哪两个东西

新手最晕的是：明明改了文件，git diff 却什么都没显示。原因是 diff 默认只比「桌面」和「清单」。只要记住下面这张图，四种比较一次分清。

git diff HEAD~1 HEAD＝比上一张和这一张；git diff main..dev＝比两条分支；git diff 编号 编号 -- 文件名＝只比某个文件。 常见困惑：add 之后 git diff 变空是正常的（桌面和清单一致了），此时要看改动得敲 git diff --staged 或 git diff HEAD。
四条比较命令，逐词注释全都不改文件
$ git diff
#  diff = difference 差异；默认比「桌面 ↔ 清单」
$ git diff --staged
#  --staged = 已暂存的；比「清单 ↔ 最新照片」（等价写法 --cached）
$ git diff HEAD
#  HEAD = 最新那张照片；比「桌面 ↔ 照片」，一次看全所有改动
$ git diff HEAD~1 HEAD -- readme.txt
#  HEAD~1 = 上一张；-- = 分隔符，后面只跟文件名（只看这个文件的差异）
$ git diff --stat
#  --stat = statistics 统计；只看「哪些文件、各改了几行」，不展开正文

11.3 追查问题四件套

① 这行代码是谁、哪次改的 —— git blame

Git Bash只看不改
$ git blame readme.txt
#  blame = 归咎／追责；逐行标出「这行是谁、在哪张照片里写成这样的」
#  注意：不是骂人，是查来源，团队里天天用
你会看到（示意）
^a1b2c3d (张三 2026-11-04 00:12:01 +0800 1) 我的第一个 Git 项目
e4f5g6h7 (张三 2026-11-04 00:20:00 +0800 2) 第二行：今天学会了 git add
从左到右：照片编号（^ 表示这是第一张就有的）、作者、日期时间、行号、该行内容。看到可疑行，拿编号去 git show 编号 就能看当时整次改了什么。

② 哪一次提交引入了 bug —— git bisect（手把手）

假设相册有 20 张照片，你知道现在是坏的、第 1 张是好的，想找出「从哪张开始变坏」。一张张翻要 20 次，bisect 用对半查找只要约 5 次。

Git Bash · 依次敲bisect = 二分
$ git bisect start
#  bisect = 对半切分；start = 开始排查
$ git bisect bad
#  bad = 坏的；标记「当前这张有问题」
$ git bisect good a1b2c3d
#  good = 好的；a1b2c3d 换成你确定没问题的那张照片编号
#  接下来 Git 会自动切到中间某张，你运行一下项目，然后回答：
$ git bisect good      # 这版没问题 → 继续往新的半边找
$ git bisect bad       # 这版有问题 → 继续往旧的半边找
#  重复几轮，直到屏幕打印「xxxx is the first bad commit」
$ git bisect reset
#  reset = 复位；排查结束，回到你原来站的那张照片（千万别漏这一步）
2026 新增

Git 2.56 的 git bisect run --reset-when-found 可以把「自动测试 + 找到后自动复位」合成一次，省掉最后的 reset。手动流程照样通用。

③ 在全部文件／全部历史里搜内容 —— grep 与 -S

$ git grep "TODO"
#  grep = 搜索文本（Unix 经典工具名）；在当前所有被跟踪的文件里找含 TODO 的行
$ git grep -n "登录"
#  -n = number 行号；把行号一起显示
$ git log -S"函数名" --oneline
#  -S = string 字符串（也叫 pickaxe 镐）；找出「哪几次提交增删了这个字符串」，比 blame 更适合找被删掉的代码
$ git log --all --oneline -- "*.js"
#  --all 所有分支；-- 后面是路径／通配符，只看动过这些文件的提交

④ 同时开两个工作目录 —— git worktree

常见场景：正在一条分支上改到一半，老板让你立刻去主线修个 bug。用 stash（第 15 章）可以，但 worktree 更干净：在同一个仓库里再开一个文件夹，两个文件夹各站一条分支，互不干扰。

Git Bash · 在仓库里敲2026 年推荐的现代做法
$ git worktree add ../hotfix main
#  worktree = 工作树；add = 新增一个；../hotfix = 新文件夹路径；main = 这个文件夹站哪条分支
#  现在 cd ../hotfix 就能在 main 上改 bug，原来的文件夹还停在你没做完的分支上
$ git worktree list
#  list = 列出；看看现在开了几个工作目录
$ git worktree remove ../hotfix
#  remove = 移除；改完推上去后，把这个临时文件夹注销掉

同一台相机、同一本相册，但另摆一张桌子：这边摊着画到一半的草稿，那边摊着正式稿，两桌互不碰。想回哪桌就走过去，不用把半成品先收起来。

① add 之后 git diff 为空，能说出该改敲哪条；② 能用 git log --oneline --graph --all 看全部分支；③ 知道查「这行谁改的」用 blame、查「哪次改坏了」用 bisect、查「某个词在哪次被删」用 log -S。

12撤销与回退全解

第 6 章只给了「够用」的三味药。这一章把 restore、reset、revert、amend、reflog 的全部参数、全部场景摊开，并配一次「误删后找回」的完整实战。

12.1 restore：从哪儿恢复、恢复到哪儿

git restore 文件名＝把桌面文件还原成「清单」里的样子（默认源是清单，若没进过清单则是 HEAD）。 git restore --staged 文件名＝把清单还原成 HEAD，桌面不动；git restore --source=HEAD~1 文件名＝直接拿上一张照片覆盖桌面和清单。
restore 全部参数，逐词注释按需取用
$ git restore readme.txt
#  默认：用清单里的版本覆盖桌面；没进过清单就用 HEAD
$ git restore --staged readme.txt
#  --staged = 只动清单；把清单还原成 HEAD，桌面改动原样保留
$ git restore --staged --worktree readme.txt
#  --worktree = 只动桌面；两个一起写＝清单和桌面都还原成 HEAD
$ git restore --source=HEAD~1 readme.txt
#  --source = 来源；指定拿「上一张照片」当样板，而不是默认的 HEAD
$ git restore --source=a1b2c3d -- readme.txt
#  也可直接给照片编号；-- 是分隔符，后面只跟文件名
$ git restore .
#  . = 当前目录；一次还原所有被修改的文件（未跟踪的新文件不会被删）

12.2 reset 三种模式：差别只在「动到哪一格」

--soft 最温柔（什么都没丢），--hard 最狠（未提交的改动真的消失）。
模式逐词意思典型用途
--softsoft＝软的，最轻「刚才那张照片拍早了，我想重新拆成两张」——改动还在清单里，直接重新 commit
--mixedmixed＝混合；不写模式时就是它「add 加多了，整个清单推倒重来」——内容不丢，只是要重新 add
--hardhard＝硬的，全清「这一版彻底不要了，桌面也给我退回原样」——未提交改动会消失
--keepkeep＝保留类似 hard，但若退回会覆盖本地未提交改动，就拒绝执行，更安全一点
Git Bash · 三种写法对照目标可以是 HEAD~1、编号、分支名
$ git reset --soft HEAD~1
#  只挪指针；上一次的改动还在清单里，git status 显示绿色
$ git reset HEAD~1
#  不写模式 = --mixed；指针回退、清单清空，改动退回桌面（红色）
$ git reset --hard HEAD~1
#  指针、清单、桌面全部回到上一张；未 commit 的改动消失
$ git reset --hard a1b2c3d
#  也可以直接跳到某个编号的照片，不必用 ~ 数
用 --hard 之前的两个动作

① 先敲 git status 看清有哪些没提交的改动，确认真的不要了；② 记下当前的照片编号（git log --oneline），万一后悔，用 git reflog + git reset --hard 编号 还能回来。没进过任何照片的新文件不在保护范围内，--hard 也救不回来，所以重要东西先 commit。

12.3 revert 的完整用法

Git Bash适合已经 push、别人也看得到的提交
$ git revert HEAD
#  反向拍一张，抵消当前这张的改动；会弹编辑器写说明
$ git revert --no-edit HEAD
#  --no-edit = 不编辑；用自动生成的说明，不弹 Vim（新手推荐）
$ git revert HEAD~2..HEAD
#  两点区间 = 连续撤销「最近 3 张」，会为每张各生成一张反向照片
$ git revert -n a1b2c3d
#  -n = no commit 不自动提交；只把反向改动放进工作区，让你合并成一张再 commit
$ git revert --abort
#  --abort = 中止；撤销过程中撞上冲突、想放弃时用，回到 revert 之前
$ git revert -m 1 合并照片编号
#  撤销一次 merge 时必须指定 -m 1：保留第 1 条父线（主线）为「主」
revert 和 reset 到底选哪个

一句话：只在你自己电脑上、还没 push → reset；已经 push、别人可能拉过 → revert。reset 会改历史（把照片从链上摘掉），revert 只增不减（新拍一张反向照片），后者在团队里不会让别人的仓库对不上。

12.4 amend：改最后一次提交

Git Bash只改「最后一张」，且还没 push 时用
$ git commit --amend -m "改好的说明"
#  --amend = amend 修正／修补；重拍最后一张，只换说明
$ git add forgotten.txt
$ git commit --amend --no-edit
#  漏了文件：先 add 补进清单，再 --amend 把它并进最后一张；--no-edit 沿用原说明
注意

--amend 不是「修改照片」，是重拍一张新的，编号会变。如果这张已经 push 过，再推就要用强推（见 17 章 --force-with-lease），团队场景下尽量别这么做。

12.5 实战：reset --hard 之后把照片找回来

这是最让人心跳加速的场景，但 Git 预留了后路：HEAD 每一次移动都记在 reflog 里。

1故意弄丢一次
$ git log --oneline
#  先看清现在的照片编号，例如 e4f5g6h 是最新的
$ git reset --hard HEAD~1
#  退掉最新那张（练手用；真实场景换成你误操作的那一刻）
你会看到
HEAD is now at a1b2c3d 第一次提交：加入说明文件
HEAD is now at＝现在站在这张照片上了。git log 里最新那张看起来「没了」——别慌，它只是没挂在任何分支上，照片本体还在。

$ git reflog

Git Bashmerge 全参数

13.4 冲突进阶：不止「改同一行」

冲突类型屏幕提示怎么处理
两边改了同一行CONFLICT (content)按 7.3 节：删标记 → 改成最终内容 → add → commit
两边都新建同名文件CONFLICT (add/add)同上，把两个版本的内容合成一份
一边改、另一边删CONFLICT (modify/delete)决定「留改动的」还是「就删掉」：git add 文件名 留，git rm 文件名 删
二进制文件（图片、Word）CONFLICT (binary)没法按行合并，只能选一边：git checkout --ours 文件名 或 --theirs
合并到一半想反悔—git merge --abort，干净回到合并前
「选一边」的两条命令，逐词拆冲突期间才有效
$ git checkout --ours logo.png
#  --ours = 我们的；保留「当前所在分支」（接收方）那一版
$ git checkout --theirs logo.png
#  --theirs = 他们的；保留「被并进来那条分支」那一版
$ git add logo.png
#  选完还要 add 标记已解决，再 commit
$ git mergetool
#  mergetool = 合并工具；调用图形化对比工具（需自行配置），左右两栏点选更直观
冲突其实可以少发生

① 分支别活太久，小步快合；② 开工前 git pull；③ 团队里约定谁负责哪些文件；④ 用 .gitattributes 给易冲突的生成文件指定合并策略（第 16 章）。另外 Git 2.56 的 git add --resolved（7.3 节）会在标记冲突解决前自动检查标记有没有删干净，比 git add . 安全得多。

本章检查点

① 能用 git branch -vv 看出本地比云端多几张；② 知道 -d 和 -D 的区别；③ 能说出 --no-ff 会多出什么；④ 合并中途想放弃时敲得出 git merge --abort。

14变基与挑拣

两条「整理历史」的命令：rebase 把分支接到新的最新位置上，cherry-pick 把某一张照片单独复制过来。团队里很常用，但有一条铁律必须记住。

14.1 rebase 在干什么

你在 dev 上干活的两天里，main 被同事往前推了两张。结果两条线分叉了。此时有两条路：merge（把两条线汇在一起，留一张合并照片），或 rebase（把你 dev 上的照片重新拍一遍，接到 main 最新的后面，看起来像一条直线）。

打个比方

你照着昨天那张照片摆好了一组东西（a、b），今天相册里又多了两张新照片。rebase 就是把今天的样子铺在桌上，照着它把你那组东西重新摆一遍再拍——摆法一样，但拍摄时间和编号都换成新的了。

14.2 merge 还是 rebase

对比merge 合并rebase 变基
历史形状保留真实分叉，多一张 M 合并照片拉成一条直线，更干净
照片编号原封不动全部重生成
已 push 的共享分支安全，随便用禁止（会让别人手里的历史对不上）
冲突处理一次解决全部冲突可能每张照片都要解决一次
适合把功能并进 main、多人协作、留审计痕迹自己本地还没 push 的分支整理、同步主线
唯一必须背下来的铁律

永远不要 rebase 已经 push 到远程、别人可能拉过的提交。 因为 rebase 会换掉编号，别人手里还是旧编号，两边一对齐就会重复、冲突、甚至覆盖。
安全用法只有一种：rebase 自己本地、还没推上去的分支。推上去之后想整理历史，先跟团队说一声，并改用第 17 章的 --force-with-lease。

14.3 手把手做一次 rebase

1先把主线更新到最新

$ git pull
#  pull = 拉；把同事新推的照片接进来
2回到自己的分支，换基座
Git Bash核心命令
$ git switch dev
$ git rebase main
#  rebase = re + base 「重新定基座」；把 dev 上独有的照片，逐张重新接到 main 最新后面
git rebase main
rebasere＝重新，base＝基座／起点。合起来＝把这条分支的起点换成别的照片。
main新的基座（目标分支）。整句读作「把当前分支 dev 变基到 main 上」。
你会看到

Successfully rebased＝变基成功；refs/heads/dev＝dev 这条分支的引用已更新。此时 git log --oneline --graph --all 会看到一条直线。
3如果中途报冲突
#  Git 会停在某一张照片上，提示 CONFLICT，并告诉你下一步
#  ① 用记事本改好冲突文件（和 7.3 节一样删标记、留最终内容）

git log --oneline --graph --all 里 dev 的照片排在 main 最新那张之后；git status 干净。注意照片编号和之前不一样了，这是正常的。

14.4 交互式 rebase：把 3 张照片整理成 1 张

本地连着拍了几张细碎的照片（「改个字」「再改个字」「忘了加分号」），推上去之前想合并成一张干净的。-i 会打开一张「待办清单」让你逐张安排。

Git Bash只整理本地未 push 的照片
$ git rebase -i HEAD~3
#  -i = interactive 交互式；HEAD~3 = 整理最近 3 张照片
#  会打开编辑器，列出这 3 张，每行前面有个动作词
编辑器里看到的清单（示意，不是命令）改最左边的词即可
pick a1b2c3d 改个字
squash e4f5g6h 再改个字
squash f7h8i9j 忘了加分号

# 保存退出后，3 张会合成 1 张，并让你重新写一句说明
动作词英文原义作用
pick（p）挑选保留这张，什么都不改（默认）
reword（r）重新措辞内容不变，只改说明
edit（e）编辑停在这张，让你补改文件／拆成多张
squash（s）压扁／挤压把这张并进上一张，说明也合并
fixup（f）修补同 squash，但丢掉这张的说明
drop（d）丢弃整张删掉（也可直接删掉这一行）
还能调整行序：把某行拖到另一行前面，就能改变照片的先后顺序。
2026 的两种新写法

Git 2.55 加了 git history fixup（把清单里的改动直接并进某张旧照片，省掉 fixup! + rebase --autosquash 两步）；2.56 加了实验性的 git history drop 编号（一行删掉历史中间某张，并自动把后面的接好）。都是把交互式 rebase 的常见操作变成一条命令，属于「等遇到再查」的范畴。

14.5 cherry-pick：只把某一张照片拿过来

场景：bug 在 dev 上修好了（照片 x9y8z7w），但 main 现在也需要这个修复，又不想把 dev 上其他没做完的东西一起并过来。这时只复制那一张照片。

Git Bash · 先 switch 到接收方逐词注释
$ git switch main
#  先站到「要拿过来的那条分支」
$ git cherry-pick x9y8z7w
#  cherry = 樱桃，pick = 挑；习语「挑最好的那一颗」＝只复制这一张照片的改动
#  x9y8z7w = 用 git log --oneline 在 dev 上查到的照片编号
$ git cherry-pick x9y8z7w a1b2c3d
#  也可以一次挑多张，按顺序接在当前分支后面
$ git cherry-pick --no-commit x9y8z7w
#  --no-commit = 只把改动放进工作区和清单，不自动拍照片，方便再改改
$ git cherry-pick --abort
#  --abort = 中止；挑的过程中撞上冲突就放弃，回到操作前
本章检查点

① 能说出 rebase 和 merge 在「历史形状」和「编号是否改变」上的差别；② 背得出那条铁律；③ 知道 -i 清单里 squash 和 drop 各干什么；④ 遇到「只要某一个修复」时能想到 cherry-pick。

15储藏与标签

两个入门没讲、但天天会用到的功能：临时收起半成品（stash）和给重要照片贴固定名字（tag）。

15.1 stash：把半成品临时收起来

改到一半，突然要去另一条分支修个紧急 bug，但现在的改动乱得根本不配拍一张照片。stash 帮你把「桌面 + 清单」的状态临时存成一张不进相册的草稿照，桌面立刻干净，回头再原样摊开。

不属于任何分支、不进正式相册，切到哪条分支都能摊开（所以也能用来「把改动搬到另一条分支」）。

15.2 stash 全套命令

Git Bash · 每条都带逐词注释按需取用
$ git stash push -m "登录页改到一半"
#  stash = 储藏；push = 存进去；-m = message 给这份草稿写句说明
$ git stash push -u
#  -u = untracked 未跟踪的；连新建的、还没 add 过的文件一起收（默认不收）
$ git stash list
#  list = 列出；stash@{0} 是最近一份，@{1} 是上一份，数字越大越旧
$ git stash show -p stash@{0}
#  show = 展示；-p = patch 补丁；看这份草稿里具体改了哪些行
$ git stash apply stash@{0}
#  apply = 应用／摊开；把草稿摊回桌面，但草稿本身还留着（可重复使用）
$ git stash pop
#  pop = 弹出；摊回桌面 + 把这份草稿删掉（最常用，默认取 stash@{0}）
$ git stash drop stash@{1}
#  drop = 丢弃；只删某份草稿，不改桌面
$ git stash clear
#  clear = 清空；删掉全部草稿（不可恢复，先 list 确认）
$ git stash branch fix-from-stash stash@{0}
#  基于那份草稿新建并切到一条分支；草稿内容自动摊到新分支上，适合改成正式成果
git stash pop
stash英文原义藏匿／储存处。这里＝临时草稿区，专门放不值得正式拍照片的半成品。
pop原义弹出（栈数据结构用语）：取出最上面那份，并把它从栈里移除。对照 apply＝取出但保留。
1实战：被打断的活，怎么完整接回来
照着敲一遍，体会最直观在任意有改动的仓库里
$ echo "写到一半的功能" >> readme.txt
#  ① 正在改东西……
$ git stash push -m "功能写了一半"
#  ② 收起来，桌面变干净
$ git status
#  ③ 应显示 working tree clean
$ git switch -c hotfix main
#  ④ 放心去开分支修 bug（不 stash 的话，带着脏改动切分支容易出乱子）
#     ……改完、commit、切回来……
$ git switch main
$ git stash list
#  ⑤ 确认草稿还在：stash@{0}: On main: 功能写了一半
$ git stash pop
#  ⑥ 摊回桌面，草稿自动删掉
检查点

git status 里 readme.txt 又变回红色（改动回来了），git stash list 空了。如果 pop 时提示冲突，按 7.3 节同样的方法改标记 → add → commit 即可。

stash 和 worktree 怎么选

只被打断几分钟 → stash 最轻。要同时在两条分支上持续干几天 → 用 11 章的 git worktree 另开一个文件夹，两边互不遮挡，不用反复收摊。

15.3 tag：给重要的照片贴一个固定名字

照片编号是 e4f5g6h 这种随机串，没人记得住。发布版本时给它贴个 v1.0.0，以后说「回到 v1.0.0」就行。标签就是贴在某一张照片上的固定便签，不会随新提交移动（分支会移动，标签不会）。

标签不动。这就是标签和分支的根本区别。
两种标签命令区别
轻量标签git tag v1.0.0只是给照片起个别名，不存作者、日期、说明。临时用够。
附注标签git tag -a v1.0.0 -m "首个正式版"-a = annotated 附注的；会存打标签的人、时间、说明，还能签名。正式发布推荐用这个。

$ git tag
#  不带参数 = 列出所有标签（按字母序）
$ git tag -l "v1.*"
#  -l = list 列出并过滤；"v1.*" 只列 v1. 开头的（* 是通配符）
$ git tag -a v1.0.0 -m "首个正式版"
#  -a = annotated 附注的；-m = message 说明；贴在当前 HEAD 上
$ git tag -a v0.9.0 -m "补打旧版标签" a1b2c3d
#  末尾跟编号 = 给某张旧照片补标签
$ git show v1.0.0
#  show = 展示；看这个标签指向哪张照片、写了什么说明
$ git tag -d v0.9.0
#  -d = delete 删除；只删本地标签
$ git push origin v1.0.0
#  标签默认不会被 git push 带上去，要单独推；origin = 远程名
$ git push origin --tags
#  --tags = 所有标签；一次把本地全部标签推上去
$ git push origin --delete v0.9.0
#  删除云端标签：--delete = 删除，后面跟标签名
$ git switch -c hotfix-v1 v1.0.0
#  从某个标签开新分支，用来给旧版本修 bug（别在 detached 状态直接提交）
实战：发布一个 v1.0.0

① git status 确认干净 → ② git tag -a v1.0.0 -m "首个正式版" → ③ git tag 看到 v1.0.0 → ④ git push 推提交 → ⑤ git push origin v1.0.0 推标签 → ⑥ 刷新 GitHub 仓库页，右侧 Releases / Tags 里出现 v1.0.0 就成功了。

版本号怎么写

常见的是语义化版本 v主版本.次版本.修订号，例如 v1.2.3：改了不兼容的大功能 → 主版本 +1；加了向下兼容的新功能 → 次版本 +1；只修 bug → 修订号 +1。

16.5 .gitattributes 与换行符

Windows 换行是 CRLF（回车+换行），Linux/macOS 是 LF（换行）。同一份文件在两边来回传，可能整文件都显示成「被修改过」。用设置统一掉：

core.autocrlf 的值行为适合
true存进仓库时转 LF，取回桌面时转 CRLFWindows（推荐）
input存进仓库时转 LF，取回时不转换macOS / Linux
false完全不转换，原样存纯单平台项目／需要字节级一致时
更现代的做法：把规则写进仓库，跟代码一起走文件名 .gitattributes
* text=auto              # text=auto：让 Git 自动判断哪些是文本文件并统一成 LF
*.bat text eol=crlf      # eol = end of line 行尾；Windows 批处理必须保留 CRLF
*.sh  text eol=lf        # Shell 脚本必须 LF，否则在 Linux 上跑不起来
*.png binary             # binary = 二进制；别对图片做换行转换，也别按文本合并
*.lock -diff             # -diff = 不做文本差异；依赖锁文件太大，diff 里跳过
package-lock.json merge=ours  # 指定合并策略：冲突时优先保留当前分支那一版（需先在 config 里定义 driver）
大文件、子项目、超大仓库（知道有这回事即可）

Git LFS（Large File Storage）：把几百 MB 的设计稿／模型存到专门服务器，仓库里只留一个小指针；用 git lfs track "*.psd"。
submodule 子模块：仓库里嵌另一个仓库，git submodule add 地址 目录，克隆时要加 --recurse-submodules。
sparse-checkout 稀疏检出：超大仓库只检出自己需要的几个目录，git sparse-checkout set 目录名。
partial clone 部分克隆：git clone --filter=blob:none 地址 先不下载历史大文件，用到时再取；Git 2.56 的 git repack --drop-filtered 就是把取回来的大文件再清掉。这四项都是「仓库大到普通办法不好使了」才用，新手跳过完全不影响。

17远程仓库与协作全解

17.1 三个 main，别搞混

git fetch 只更新 ②；git pull ＝ fetch（更新 ②）＋ merge（把 ② 并进 ①）；git push 把 ① 送到 ③，并顺手把 ② 也挪过去。 这三份可以各自停在不同的照片上——git branch -vv 里的 ahead / behind 说的就是 ① 和 ② 差了几张。

17.6 强推的正确姿势

改了已经 push 过的历史（amend、rebase、交互式整理）后，普通 git push 会被拒绝，因为本地和云端对不上。这时需要强推，但别用 --force。

Git Bash改过已 push 的历史时才用
$ git fetch origin
#  ① 先把云端最新情况取回来，让本地的 origin/main 是最新的
$ git push --dry-run --force-with-lease
#  ② --dry-run 预演，看看将要覆盖什么
$ git push --force-with-lease
#  --force = 强制覆盖；with lease = 带「租约」：
#  只有当我上次看到的云端状态没被别人改过，才允许覆盖；否则拒绝，避免抹掉同事的提交
对照记忆

--force＝「我说覆盖就覆盖」，可能直接抹掉别人刚推的东西；--force-with-lease＝「如果云端跟我上次看到的一样，我才覆盖」，多一道保险。共享分支要改历史，先跟团队说一声；公共主干（main）通常在平台侧设了保护规则，直接禁止强推。

本章检查点

① 能画出 本地 main / origin/main / 云端 main 三者关系；② 知道 pull = fetch + merge，并能拆开敲；③ 会删云端分支（push origin --delete）；④ 知道标签要单独推；⑤ 强推时能说出为什么用 --force-with-lease。

18.1 团队每天在跑的流程

不在 main 上直接改：每个改动开一条短命分支；　② push 之前先 pull；　③ 提交说明写「为什么」，不写「改了啥」（改了啥看 diff 就知道）。 PR 不只是「交代码」，还是让别人 review、让 CI 自动跑测试、给后来人留下一份「这次为什么改」的记录。
分支策略怎么分适合
GitHub Flow（推荐）只有一条长期 main，其余都是短命功能分支，合并后删掉网页项目、小团队、持续发布
Git Flowmain + develop + feature/release/hotfix 多类分支有固定版本发布节奏的传统软件；对新手偏重
主干开发大家直接小步提交到 main，靠特性开关隐藏未完成功能成熟团队 + 完善自动化测试

18.2 提交说明怎么写（Conventional Commits）

格式：类型(范围): 一句话说明。好处是能一眼扫过历史，还能自动生成更新日志。

类型英文原义什么时候用例子
featfeature 功能新增功能feat(login): 支持手机号登录
fix修复修 bugfix(cart): 修复数量为零时仍能结算
docsdocuments 文档只改文档docs: 补上部署步骤
style样式／格式空格、缩进、分号，不改逻辑style: 统一缩进为 2 空格
refactor重构改结构但不改行为refactor: 抽出公共校验函数
test测试加／改测试test: 覆盖空购物车场景
chore杂务构建脚本、依赖、配置chore: 升级依赖版本
perf / ci / build性能 / 持续集成 / 构建对应专项改动ci: 增加 Node 20 的测试任务
两条实操建议

① 一次提交只做一件事：把「重构」和「修 bug」分开拍两张，以后回滚才不会连带；② 说明用祈使句、中文也行、不加句号，需要解释原因就在下面空一行写正文（git commit -m "标题" -m "正文"）。

18.3 实战一：给开源项目提一个 PR（完整手把手）

Fork 的意思是：把别人仓库复制一份到你自己的 GitHub 账号下，你在自己那份上随便改，改完请求原作者把你的改动收进去（这个请求就是 PR）。

1网页上 Fork

打开原项目页面 → 右上角点 Fork → 保持默认 → Create fork。几秒后你账号下出现一份一模一样的仓库。

2克隆你自己的那份
$ git clone https://github.com/你的用户名/项目名.git
#  注意：地址里是「你的用户名」，不是原作者的
$ cd 项目名
$ git remote -v
#  此时只有一个 origin，指向你的 Fork（clone 自动配好）
3额外登记原项目地址
$ git remote add upstream https://github.com/原作者/项目名.git
#  upstream = 上游；单独登记原项目，专门用来同步它的最新改动
$ git remote -v
#  应看到两组：origin（你的 Fork）、upstream（原项目）
4开分支、改东西、提交
$ git switch -c fix/typo
#  -c = create 创建；分支名写清用途，别用 patch、test 这种没信息量的词
#  ……用记事本改文件，比如修正 README 里的一个错别字……
$ git add .
$ git commit -m "docs: 修正 README 中的错别字"
5推到你的 Fork
$ git push -u origin fix/typo
#  推到 origin（你的 Fork），不是 upstream；-u 记住跟踪关系
6网页上开 Pull Request

打开你 Fork 的页面 → 顶部通常直接出现黄色提示条 Compare & pull request，点它 → 确认 base 是「原作者仓库的 main」、compare 是「你的 fix/typo」→ 填标题和说明（写清「改了什么、为什么改、怎么验证」）→ Create pull request。

7评审期间被要求再改一下
#  不用重新开 PR！在本地同一条分支上继续 commit，再 push 一次，PR 会自动更新
$ git add .
$ git commit -m "docs: 按评审意见补充示例"
$ git push
#  已经用 -u 建过跟踪，直接 push 即可
8合并之后收尾
$ git switch main
$ git fetch upstream
#  从原项目取回最新（你的改动已被合并进去了）
$ git merge upstream/main
#  把上游的 main 并进你本地 main
$ git push origin main
#  顺手让你自己的 Fork 也跟上
$ git branch -d fix/typo
#  -d = delete；合并完的分支删掉，保持清爽
$ git push origin --delete fix/typo
#  云端那条也一起删（可选）
检查点

PR 页面显示 Merged（紫色），原项目历史里能看到你的提交，你的 Fork 也同步到了最新 → 完整走完一次开源贡献。

18.4 PR 的三种合并方式

按钮结果适合
Merge commit保留分支上每一张照片，额外生成一张合并照片想完整保留开发过程
Squash and merge把分支上所有照片压成一张再并进 main最常用：main 历史干净，一条 PR 一张照片
Rebase and merge把每张照片逐个接到 main 后面，不生成合并照片提交拆得很干净、想保持线性时
配套机制（知道是什么就行）

issue＝问题／需求单，讨论和跟踪用；Code Review＝在 PR 里逐行评论、批准或要求修改；CI 检查＝合并前自动跑测试、格式检查，不通过就不让合；保护分支＝禁止直接 push 到 main、强制 PR + 若干人批准 + 检查通过；CODEOWNERS＝指定哪些文件必须由谁审。

18.5 实战二：两个人改同一处，怎么完整解决

不用真的找第二个人：在同一台电脑上建两个文件夹，就当是两台电脑。这是练协作最省事的办法。

Git Bash · 在桌面新建一个空文件夹做演练逐段执行
# ── 准备：建一个「云端」裸仓库模拟 GitHub ──
$ mkdir team-demo && cd team-demo
$ git init --bare server.git
#  --bare = 裸仓库；只存 .git 内容、没有工作区，专门当「服务器」用

# ── 甲：克隆 → 写第一行 → 推 ──
$ git clone server.git person-a
$ cd person-a
$ git config user.name "甲" && git config user.email "a@test.com"
#  这里用 --local 级别的默认配置，只为区分两个人；不影响你电脑的全局设置
$ echo "标题：甲写的版本" > title.txt
$ git add . && git commit -m "docs: 甲写好标题"
$ git push -u origin main

# ── 乙：也克隆一份，改同一行（但先不推） ──
$ cd ..
$ git clone server.git person-b
$ cd person-b
$ git config user.name "乙" && git config user.email "b@test.com"
$ echo "标题：乙写的版本" > title.txt
$ git add . && git commit -m "docs: 乙换了个标题"
乙如果直接 push，会被拒绝
$ git push
! [rejected] main -> main (fetch first)
error: failed to push some refs to '.../server.git'
hint: Updates were rejected because the remote contains work that you do not have locally.
rejected＝被拒绝；fetch first＝先取回；the remote contains work that you do not have locally＝云端有你本地没有的提交。这就是「push 之前先 pull」这条规矩的由来。
乙的正确做法：先拉，解冲突，再推照敲
$ git pull
#  甲那张照片被拉下来，两人改了同一行 → 必然 CONFLICT
#  ① 用记事本打开 title.txt，删掉 <<<<<<< / ======= / >>>>>>> 三行标记
#  ② 把内容改成两人都认可的最终版，例如「标题：甲乙共同确定的版本」，保存
$ git add title.txt
$ git commit -m "merge: 合并两人对标题的修改"
$ git push
检查点

切回 ../person-a 敲 git pull，看到 title.txt 变成协商后的最终内容；两边 git log --oneline --graph 都能看到「甲 → 乙 → 合并」三张照片。这就完整演练了真实协作里最常出问题的那一环。

18.6 团队协作节奏表

时机敲什么为什么
每天开工git pull（或 --ff-only）别在过期版本上干活
开始一个改动git switch -c 用途/简述隔离，main 永远干净
做到一小段git add . + git commit -m "类型: 说明"小步存档，方便回滚和评审
推之前git pull + 解冲突避免 rejected
推分支git push -u origin 分支名第一次带 -u
交付网页开 PR → 评审 → Squash merge留记录、跑 CI
合并后git switch main + git pull + git branch -d 旧分支回到最新，清掉用完的分支
发版本git tag -a v1.x.x -m "..." + git push origin v1.x.x给发布点钉一个固定名字
本章检查点

① 能说清 origin 和 upstream 各指什么；② 独立完成一次「Fork → 分支 → commit → push → PR」；③ 被评审要求修改时知道直接 push 就会更新 PR；④ 遇到 push 被拒能按「pull → 解冲突 → commit → push」走完。

19.2 Git 2.56 里，普通用户用得上的新东西

新命令 / 新选项解决什么麻烦
git add --resolved解决合并冲突时，只暂存真正冲突过的文件，还会先检查冲突标记有没有删干净。已在 7.3 节讲过，这是 2.56 最实用的一条。
git branch --delete-merged 'origin/*' 'topic-*' --dry-run批量列出「已经合并完、可以删掉」的本地分支。引号里是分支名匹配模式（* 通配）；--dry-run＝空跑／预演，只列不删；确认后去掉它才真删。
git history drop <提交编号>实验性新命令：一行删掉历史中间某次提交，并自动把后面的提交接好，不用再手动交互式 rebase。
git bisect run --reset-when-found自动找「哪一次提交引入了 bug」时，找到后顺手复位，不用再手动 git bisect reset。
命令纠错提示把 git push origin/main 写错成斜杠、或 --set-upstream-to 少写等号时，Git 会直接建议正确写法，不再冷冰冰报一句失败。
git refs create / update / delete / rename面向脚本的底层引用管理命令。日常用 git branch / git tag 就行，这条知道有即可。
透明提速合并基准计算、大仓库的 git diff / git status 明显变快（Linux 内核某个用例从 0.29 秒降到 0.01 秒）。不用改任何命令，升级就受益。
新手要不要现在就学这些

不用。除了 git add --resolved 值得在解冲突时顺手用一下，其余都是「等真遇到那个场景再查」。Git 的核心动作十年来没变：add → commit → switch / merge → push / pull，你在前 9 章学的就是这套核心动作。

19.3 Git 3.0 会改什么，会不会白学

变化说人话对你有影响吗
默认哈希 SHA-1 → SHA-256照片编号的算法换成更长、更安全的那种没有。编号只是变长，命令一字不改；已有的老仓库照常工作
默认引用存储 → reftable分支／标签的存法换成更快的格式没有。只影响大仓库的速度，git switch 照样敲
默认分支名 → main官方正式把新建仓库的主线定名为 main你早就在用了：第 2 章配了 init.defaultBranch main，第 3 章用了 init -b main
Rust 成为必需依赖编译 Git 源码时必须要 Rust 工具链没有。只影响自己编译 Git 的人，下载安装包的用户无感
一句话结论

3.0 改的是底层默认配置，不是日常命令。而且这些改动只作用于「新建的仓库」，不会自动改造你现有的仓库。现在学的这套，到 3.0 照样能用。

19.4 前一个版本 Git 2.55 带来了什么

2.55 发布于 2026-06-29，是 2.56 之前的最新版（本机实测环境就是 2.55.0.windows.3）。它的改进偏「用起来更顺」，日常会有感觉：

特性说人话
git history fixup实验性 git history 家族的新动作：把清单里的改动直接并进某张旧的提交，省掉「写 fixup! 说明 → 再 rebase --autosquash」两步。第 14 章的交互式 rebase 有对照。
增量 multi-pack-index 重打包大仓库整理存档时，可以只往元数据里追加一小层，不必每次全量重写，git maintenance 变便宜。
并行 hooks（钩子）互不依赖的自动检查（比如代码格式检查 + 单元测试）可以同时跑，提交前的等待更短。
Linux fsmonitor 守护进程Linux 终于也有了 macOS / Windows 早有的「文件变动监听」，大仓库里 git status、git add 明显变快。
过滤远程进度里的终端控制字符远程发回来的进度文字里若藏有终端转义序列，会被清掉，堵住一类终端注入花招。
Rust 从「可选」转为默认启用为 3.0 把 Rust 变成必需依赖做铺垫；下载安装包的用户无感。

屏幕上出现的英文意思是敲这条

20.2 Vim 逃生（新手第一大坑）

不带 -m 敲 git commit，或执行 git revert、git merge 时，可能弹出一个叫 Vim 的编辑器：满屏文字，按键没反应，看起来像卡死。它其实在等你写说明。

从根上绕开它

A附录 A：Git 内部是怎么存的

这一节完全可以跳过，不影响使用。放在这里只是为了满足「想知道相机肚子里长什么样」的人，以及让「全」字名副其实。

隐藏的 .git 文件夹里，核心是四样东西。用前面那套说法翻译一遍：

每张照片存的是「全部文件的完整快照」， 不是「只存改了哪行」（Git 内部会自动去重压缩， 所以不会真的把仓库撑爆）。 blob＝文件内容 每个文件的每一次不同内容，压缩后存成一个 blob ＝「照片里那一页纸上的字」 tree＝目录结构 记录「哪个文件夹里有哪些 blob / 子 tree」 ＝「这一页的目录清单」 还有 refs＝书签：分支（会往前走）和标签（钉死不动）都只是一个指向某张照片的小文件；HEAD 通常指向当前分支名。
名字英文原义作用
blobbinary large object 二进制大对象存一个文件的完整内容，不存文件名
tree树存一层目录：文件名 → 对应 blob / 子 tree
commit提交一张照片：指向一个 tree、若干 parent、作者时间、说明
ref / refsreference 引用分支、标签这些「有名字的指针」，存在 .git/refs/
HEAD头通常是一个写着 ref: refs/heads/main 的小文件
index索引就是「待拍清单」的那个文件 .git/index
哈希编号hash 散列对内容算出来的固定长度指纹；内容一样，编号就一样；改一个字，编号全变。当前默认 SHA-1（40 位），3.0 起新仓库默认 SHA-256（64 位）
.git/objects对象库上面 blob/tree/commit 压缩后存放的地方；git gc / git maintenance 负责整理
理解到这一层，有几个现象立刻说得通

为什么 rebase 之后编号全变了？→ 因为 parent 变了，照片内容变了，指纹当然变。
为什么删掉的提交还能用 reflog 找回？→ 因为照片本体还在 objects 里，只是没有书签指着它了。
为什么 commit 完就「丢不了」？→ 因为整张快照已经落进对象库。
以上都不用背，用得多了自然就懂。

#问题回答
1git add 之后 git diff 为什么是空的？因为 diff 默认比「桌面 ↔ 清单」，两者已经一致了。改敲 git diff --staged（比清单 ↔ 照片）或 git diff HEAD（桌面 ↔ 照片）。见 11.1。
2commit 和 push 到底差在哪？commit 把照片存进你电脑上的相册，断网也能做；push 把照片传到云端，需要联网。没 commit 的东西永远推不上去。
3main 和 origin/main 是一回事吗？不是。main 是你能改的本地分支；origin/main 是本地存的「云端快照」，只读；云端 GitHub 上还有第三个 main。见 图 17-1。
4fetch、pull、clone 怎么分？clone＝第一次整包搬回家；fetch＝以后只下载不合并；pull＝fetch + merge 一步做完。见 图 8-2、图 17-2。
5什么时候用 merge，什么时候用 rebase？把功能并进公共主线用 merge；整理自己本地、还没 push 的分支用 rebase。铁律：永远不要 rebase 已经共享出去的提交。见 14.2。
6reset 和 revert 选哪个？没 push、只有你自己 → reset（改历史）；已经 push、别人可能拉过 → revert（新拍一张反向照片，历史只增不减）。见 12.3。
7status 里红色和绿色分别代表什么？红＝还没进待拍清单（或改了但没 add），绿＝已经进清单，下次 commit 会拍到。什么都不显示＝桌面和相册一致。见 图 4-2、10.2。
8冲突标记要删到什么程度？<<<<<<<、=======、>>>>>>> 三行全部删掉，内容改成最终想要的，保存后 git add 文件名 → git commit。用 2.56 的 git add --resolved 会自动帮你检查残留。见 7.3。
9已经 push 的提交还能改吗？能，但要先想清楚：改说明用 --amend、整理历史用 rebase -i，然后用 git push --force-with-lease；共享分支务必先跟团队沟通。更安全的做法是干脆 git revert。见 12.3、14.2、17.6。
10断网能用 Git 吗？密码能提交进仓库吗？断网可以：init / add / commit / branch / merge / log / diff / reset 全在本地。只有 push / pull / fetch / clone 需要网。密码、令牌、密钥绝对不要提交；误提交了要立刻吊销或改掉，再从历史里清除（见 10.4）。
11照着教程敲 cd，为什么报 bash: cd: too many arguments？而且路径跟教程里写的不一样？① 你多半把绿色注释行 # cd = change directory ... 也敲进去了——= 是「意思是」、英文只是翻译，只敲带 $ 的那一行，cd 后面只跟一个文件夹名。② 教程旧版写死「路径会变成 ~/my-first-repo」不准确：从 C 盘根开始就是 /c/my-first-repo，前缀取决于你的起点，末尾变成 my-first-repo 才算成功。见开头说明卡、2.2 节、第 3 章步骤 1。
12git add 之后冒出黄字 warning: ... LF will be replaced by CRLF ...，是出错了吗？文件会不会坏？不是错误，文件没坏，add 已经成功。LF（\n）是 Linux/仓库内部行尾，CRLF（\r\n）是 Windows 行尾；Git Bash 的 echo 写出 LF，而 Windows 装 Git 默认 core.autocrlf=true，所以 Git 提前通知「下次取回桌面会换成 CRLF」。直接忽略，继续 commit 即可。想统一规则：写 .gitattributes + git add --renormalize .；若变成 fatal: 被拦，设 core.safecrlf false。完整逐句翻译、成因图和三种办法见 第 3 章换行符专题 与 16.5 节。
