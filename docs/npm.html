01

初识 npm：世界快递网

为什么全世界的 JavaScript 程序员，每天都要敲一遍这三个字母

npm 是世界上最大的软件包仓库——没有之一。这一章回答三个问题：它解决什么痛？它是什么？它跟 Node.js、yarn、pnpm 什么关系？

1.1 没有包管理器的黑暗年代

假设你要在网页里用 jQuery（曾经最火的 JS 工具库）。没有 npm 的年代，流程是这样的：

  1. 打开搜索引擎，搜「jQuery 下载」，祈祷第一个结果不是盗版站；
  2. 进官网，找到下载页，挑一个版本，下载一个压缩包；
  3. 解压、把 jquery.min.js 拷进项目的 js/ 文件夹；
  4. 在 HTML 里手写一行 <script src="js/jquery.min.js"> 引入；
  5. 三个月后要升级？——从第 1 步全部重来。团队成员每人手里版本还各不相同。

一个 jQuery 尚且如此；现代项目动辄依赖几百个包（React、打包器、语法检查、测试框架……），手工管理等于自杀。于是 2010 年，npm 诞生了。

类比手工下载 = 装修全靠自己跑建材市场：买水泥要跑一趟、买钉子跑一趟、还价、运货、记小票，全手工；npm = 你把需求写成一张采购清单交给装修公司，第二天一早，所有材料精确到批次地码在你家门口。

1.2 npm 到底是什么：三位一体

名字拆开就懂一半：node package manager——「Node 包管理器」。但「npm」这个词其实同时指三样东西：

它指什么是什么类比
命令行工具你在终端里敲的 npm install 那个命令采购员（替你跑腿搬货的那位）
registry 仓库全球服务器上存放的 200 多万个包商城总仓库（货都在这儿）
npmjs.com 网站可以浏览、搜索包的官网门面商城的展示橱窗与收银台
类比把 npm 想成一座全球建材家具商城 + 配套物流系统：商城（registry，npmjs.com）里挂着 200 多万件商品（packages，包），每件商品有货号（包名）和批次（版本）；你在家写一张采购清单（package.json）交给采购员（npm 命令），他照单进货（install）到你家门口的仓库（node_modules）；将来你也能把自己的产品上架寄卖（publish）。

1.3 「包」到底是什么

包（package）= 一个有名字、有版本号、可以被安装的代码文件夹。它的「身份证」是一份叫 package.json 的文件：

包里的东西类比说明
package.json说明书 + 条码名字、版本、作者、入口（第 3 章逐字段精讲）
index.js 等代码商品本体真正干活的 JS 代码（「入口」由 package.json 指定）
README.md包装盒上的介绍商城详情页展示的使用说明
LICENSE使用许可别人能怎么用你的代码（MIT 最宽松常见）

1.4 npm vs yarn vs pnpm：三位采购员

用 npm 的人多了，就有人觉得「采购员可以更快更省」。于是出现了竞品。好消息：它们读同一张采购清单（package.json）、去同一家商城（registry），学会一个，另外两个看文档十分钟就能上手：

工具出身性格一句话点评
npmNode 官方自带稳重老大哥装完 Node 就有，生态默认标准，本教程主角
yarnFacebook 2016 年推出快而稳首创 lockfile（yarn.lock），逼得 npm 也出了 lock
pnpm社区黑马省空间所有项目共用一份全局仓库，硬链接省硬盘
先学谁零基础先学 npm：它随 Node 自带、资料最多、所有项目通用。之后想换 pnpm，命令几乎照抄（npm install → pnpm install），一天就换完。
动手练习 01
  1. 打开 npmjs.com，在搜索框搜 chalk（一个给终端文字上色的包）——看看商城详情页长什么样：右侧的版本号、周下载量、README；
  2. 再搜 react，感受一下「周下载量 2000 万+」是什么概念；
  3. 思考题：按照本章的类比，采购清单、家门口的仓库、采购小票 分别对应哪三个文件/文件夹？（答案在第 3、5、7 章揭晓）

02

地基与安装：Node 双套装

npm 不单独发售——它藏在 Node.js 的工具箱里。装 Node，送 npm

这一章把地基打好：认识 Node 与 npm 的关系，在 Windows 和 Linux 上各装一遍，跑通体检命令，最后学会「给 npm 自己升级」。

2.1 Node 与 npm：发动机与随车工具箱

类比Node.js = 发动机（让 JavaScript 能脱离浏览器、在你电脑上直接运行的运行时）；npm = 随车工具箱（装车时焊死在发动机旁边，负责管理零件）。所以装 npm 的唯一方式就是——装 Node.js。

「LTS」这个词先认识一下：Long Term Support（长期支持版）。Node 官网永远给你两个大按钮，零基础请永远选 LTS——它版本稍旧但稳定维护 30 个月，新版（Current）是尝鲜用的。

2.2 Windows 安装

  1. 打开 nodejs.org，点绿色的 「LTS」 下载按钮，得到一个 .msi 安装包；
  2. 双击运行，一路 Next（安装位置默认即可，组件保持默认勾选——里面那项 npm package manager 就是我们主角）；
  3. 装完msi 会自动把 node 和 npm 加进系统 PATH（环境变量），开个新的终端就能用。
Windows命令行（PowerShell 或 cmd）
node -v          # 命令 node：运行 Node.js；参数 -v（version）：只问「你是哪个版本」→ 输出版本号即安装成功
npm -v           # 命令 npm：npm 的总入口；-v 同上。npm 与 Node 一起装的，能出版本号就说明工具箱也在了
v20.17.0         ← Node.js 的版本号（v = version；LTS 大版本号是偶数）
10.8.2           ← npm 的版本号（注意：npm 的版本号和 Node 完全独立，各自发展）
winget 更快Windows懒人一行流：在 PowerShell 里执行 winget install OpenJS.NodeJS.LTS（winget = Windows 官方软件管家；这条命令指名要「OpenJS 组织的 NodeJS 长期支持版」），效果与安装包等同。

2.3 Linux 安装

Linux 上有两条路：发行版仓库（简单粗暴）和 nvm（版本车库，推荐）。先看简单版：

Linux / WSL命令行（Ubuntu / Debian 系）
sudo apt update          # 命令 sudo：以管理员身份执行；apt 是 Ubuntu 的软件管家；update = 刷新软件目录（先刷新，再安装）
sudo apt install nodejs npm -y   # 安装两个包：nodejs（发动机）和 npm（工具箱）；-y（yes）：所有确认自动答「是」
node -v && npm -v        # &&：前一条成功才执行后一条——两个版本号连着打出来就大功告成
apt 版本的坑Ubuntu 仓库里的 Node 常常老好几个大版本（比如你教材需要 20，仓库给 12）。要跑新项目、或者以后需要在多个 Node 版本之间切换，请用下面这位——

nvm：给 Node 建一个「版本车库」

类比nvm（Node Version Manager，Node 版本管理器）= 一个车库：里面可以同时停好几辆不同版本的 Node（发动机），一条命令切换「今天开哪辆」。旧项目要 Node 16、新项目要 Node 20？各停一辆，随时换。Windows 用户装 nvm-windows（同思路的另一个实现）。
Linux / WSL命令行：安装并使用 nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash   # 命令 curl：下载工具；-o-：把内容吐给屏幕；竖线 |：把下载的脚本直接喂给 bash 执行——nvm 官方安装法（版本号以 nvm 官方 GitHub README 为准）

source ~/.bashrc         # 命令 source：重新加载 bash 配置文件（nvm 刚把自己的配置写进去了）；~ = 你的家目录
nvm install --lts        # 命令 nvm install：装一个 Node 版本；--lts：指名要「最新的长期支持版」——注意 nvm 装的 Node 自带配套 npm
nvm use --lts            # 命令 nvm use：切换到这个版本（发动今天要开的那辆车）
nvm ls                   # 命令 ls（list）：列出车库里所有已装的 Node 版本，当前使用的那行带箭头
-> v20.17.0          ← 箭头 = 当前开着的这辆
   system             ← 系统自带/系统仓库装的（2.3 上半段 apt 装的那辆）

2.4 体检三连：版本、位置、医生

通用命令行
npm -v                     # 问版本（前面刚用过）
npm root -g                # 命令 root：报告「全局包装在哪个文件夹」；-g（global）：问的是全局那份——记下这个路径，日后排查「全局命令为什么找不到」会用到
npm config get registry    # 命令 config：读写 npm 配置；get registry = 查「默认去哪家商城提货」→ 正常应答官方地址 https://registry.npmjs.org/（换国内镜像见第 11 章）
npm doctor                 # 命令 doctor（医生）：自动体检——网络通不通、缓存坏没坏、权限对不对，一路打勾就是健康
10.8.2
C:\Users\你\AppData\Roaming\npm\node_modules    ← Windows 的全局包位置（Linux 是 /usr/lib/node_modules 或 nvm 目录下）
https://registry.npmjs.org/                       ← 默认商城地址
（doctor 会逐项打勾或报告问题）

2.5 给 npm 自己升级

npm 也是个软件，也发新版本。Node 附带的 npm 往往落后几版，一行命令把它拉到最新：

通用命令行
npm install -g npm@latest   # 命令 install：装包；-g：装到全局（工具箱自己当然住全局）；npm：要装的包名居然就是 npm 自己；@latest：@ 指定版本，latest = 最新稳定版
npm -v                      # 再看一眼——版本号变新了
帮助系统任何时候忘了命令：npm help 列出全部命令清单；npm help install 翻 install 的详细说明书；嫌长就 npm install -h（短版帮助）。npm 的说明书都在本地，断网也能查。
动手练习 02
  1. 装好 Node 后跑体检三连，把你机器上的 node -v、npm -v 抄在本子上——以后看教程对版本心里有数；
  2. 跑 npm root -g 记住全局包的位置（Windows 用户顺手用资源管理器打开看一眼这个文件夹）；
  3. 跑 npm help 浏览一遍命令总目录——不用记，混个脸熟即可，本教程会把高频的都教一遍。

03

第一份清单：package.json

npm init 办出一张「房产证 + 采购清单」——本教程最重要的一个文件

每个 npm 项目的根目录都躺着一份 package.json。它既是你项目的身份证，又是采购清单——项目叫什么、版本多少、需要哪些包、有哪些开关，全写在这一个文件里。这一章把它的每一栏都拆给你看。

3.1 npm init：办证窗口

新建一个文件夹，进去，敲下人生第一条 npm 命令：

通用命令行
mkdir my-shop      # 命令 mkdir（make directory）：新建文件夹 my-shop——我们的练手项目
cd my-shop         # 命令 cd（change directory）：进入这个文件夹（npm 的一切操作都以「当前所在文件夹」为项目）
npm init           # 命令 npm init（初始化）：办证窗口开始逐项提问——一路回车用默认答案，也可自己输入
package name: (my-shop) my-shop     ← 提问 1：包名（括号里 = 按回车就用的默认值）
version: (1.0.0)                    ← 提问 2：版本号
description: 我的第一个 npm 项目      ← 提问 3：一句话描述
entry point: (index.js)             ← 提问 4：入口文件
test command:                       ← 提问 5：测试命令（先留空）
git repository:                     ← 提问 6：Git 仓库地址（先留空）
keywords:                           ← 提问 7：搜索关键词（先留空）
author:                             ← 提问 8：作者（先留空）
license: (ISC)                      ← 提问 9：许可证
Is this OK? (yes)                   ← 终审：回车确认，package.json 出炉！
-y 快速办证通用npm init -y（y = yes）：所有提问全用默认答案，一秒出证——练手、做实验时几乎都用它，需要改哪个字段回头再编辑文件。

3.2 逐字段精讲：清单上每一栏都是干嘛的

打开刚生成的 package.json（就是个普通文本文件，VS Code 直接编辑）。下面是逐字段带注释的完整版——注意：JSON 文件真实使用时不能写注释，这里为教学加上（想练手就用复制按钮，去掉注释行再存）：

通用文件：package.json（教学示意版 · 真实文件不能写注释）
{
  "name": "my-shop",                        // 字段 name：包名——全球唯一的「货号」，发布后别人就靠它 install 你
  "version": "1.0.0",                       // 字段 version：版本号，格式「主版本.次版本.补丁号」（第 6 章精讲）
  "description": "我的第一个 npm 项目",      // 字段 description：一句话描述，会显示在商城搜索结果和详情页
  "main": "index.js",                       // 字段 main：入口文件——别人 import 这个包时，实际加载的那个 JS 文件
  "scripts": {                              // 字段 scripts：一键开关面板，键 = 开关名，值 = 按下后执行的命令（第 8 章精讲）
    "test": "echo \"Error: no test specified\" && exit 1"   // 脚本 test：npm test 时跑的命令（init 自带的占位，第 8 章换成真的）
  },
  "keywords": [],                           // 字段 keywords：关键词数组——别人在 npmjs.com 搜「shop」能搜到你的助力器
  "author": "",                             // 字段 author：作者，可以是名字或「名字 <邮箱> (网址)」的完整格式
  "license": "ISC"                          // 字段 license：许可证——ISC / MIT 都代表「随便用，出了事别找我」
}
类比package.json 的双重身份：对内是采购清单（dependencies 一栏写着要进的货）；对外是房产证（name + version + description 是这个项目作为「包」的身份登记）。它永远跟着项目走——克隆代码、拷贝项目，别的都可以不带，这份清单必须带。

3.3 name 的取名规矩

规矩正例反例（会被拒）
全小写my-shopMy_Shop、MyShop
不能有空格用连字符 - 连接my shop
发布到 npmjs.com 时必须全局唯一my-shop-2026express（早被别人注册了）
带 @ 前缀 = 「品牌专区」（scope 包）@alicelv/my-shop——
scope 包@用户名/包名 这种写法叫作用域包（scoped package）：斜杠前面是你的 npm 用户名（或组织名），相当于在商城里开了个个人专区——专区里名字随便取，不怕和全商城重名。不打算发布的练习项目，名字随便写，无人检查。

3.4 清单会「自己长大」

现在清单还很瘦。从下一章开始，你每装一个包，npm 都会自动往里面追加一栏 dependencies（进货台账）——你不需要手写它，但要看得懂它：

通用文件：package.json 片段（装包后自动长出来的部分）
  "dependencies": {              // 字段 dependencies：进货台账——「生产必需」的包（下一章会亲手写满它）
    "lodash": "^4.17.21"          // 依赖 lodash：金额是版本范围 ^4.17.21（^ 的意思第 6 章揭晓，别急）
  },
  "devDependencies": {            // 字段 devDependencies：施工队工具台账——只在「开发阶段」用的包（打包器、测试器）
    "vite": "^5.4.8"              // 依赖 vite：只管「把代码加工成成品」，不进最终产品
  }
动手练习 03
  1. 新建文件夹，用 npm init 走一遍完整问答（每题都自己输入答案），再用 npm init -y 在另一处对比速度；
  2. 用 VS Code 打开两份 package.json，对照 3.2 的字段表逐行认领：哪个字段管名字？哪个管入口？哪个是开关面板？
  3. 把 description 改成一句话介绍你自己的项目，保存（JSON 改完记得保存，逗号别多别少）。

04

装货的艺术：npm install

一条命令的四种用法：单件下单、照单全收、装施工工具、装全局利器

npm install（缩写 npm i）是整个 npm 里你敲得最多的命令——没有之一。这一章把它的四种姿势一次讲透，并揭开「按下回车后 npm 都干了什么」。

4.1 姿势一：npm install 包名 —— 单件下单

通用命令行（在 my-shop 项目里执行）
npm install lodash          # 命令 npm install：装包；参数 lodash：包名——去商城把这件「货」搬回家
                            # 等价缩写：npm i lodash（i = install，老手都这么敲）
added 1 package in 3s        ← 战报：added = 新装了几个包；1 package = 就 lodash 自己；3s = 花了 3 秒
                              ← 注意：装包后悄悄发生了三件事（见下文）

这一行命令背后，npm 同时干了三件事：

  1. 进仓库：项目里多了 node_modules 文件夹，lodash 的代码躺在里面（第 5 章进去逛）；
  2. 记台账：package.json 自动多出一栏 "dependencies": { "lodash": "^4.17.21" }；
  3. 开小票：package-lock.json 自动生成/更新，记下精确到个位的版本（第 7 章精讲）。
lodash 是谁最有历史地位的 JS 工具库（一件「万能瑞士军刀」：防抖、深拷贝、数组花式操作……），我们拿它当教学标本——就像物理课的小车。

4.3 姿势二：-D / --save-dev —— 施工队工具

同样是装包，有的货是给用户用的（沙发、床），有的是给施工队用的（电钻、脚手架）。装后者要加 -D：

通用命令行

dependencies（生产依赖）devDependencies（开发依赖）
类比正式入住的家具——用户要用的施工队的工具——装修完就带走
典型成员react、axios、lodash、dayjsvite、vitest、eslint、sass
装的时候npm i xxxnpm i -D xxx

4.4 姿势三：npm install（不带包名）—— 照单全收

当 npm install 后面什么都不写，npm 会读当前项目的 package.json，把台账上所有货全部补齐。这是它最常用却最少被讲的姿势——同事之间交接项目、服务器上部署项目，全靠它：

05

node_modules：家门口的仓库

所有到货的包都堆在这——进去逛一圈，你会发现仓库比想象中深

node_modules 是 npm 自动创建的文件夹——你从不清点它、从不编辑它、也从不提交它，但理解它的脾气，能帮你解开日后一半的灵异故障。

5.1 进仓库看一眼

通用命令行（my-shop 项目里）
dir node_modules        # 命令 dir（Windows）：列出文件夹内容；Linux/macOS 用 ls node_modules——看看仓库里都堆了谁
npm ls lodash           # 命令 npm ls（list）：画出「lodash 的收货链」——从谁手里装来的、版本多少
my-shop@1.0.0 C:\Users\你\Desktop\my-shop     ← 收货人：项目名 + 项目路径
`-- lodash@4.17.21                            ← 货：包名@精确版本（反引号画出的树形，一级一级往里缩）

5.2 依赖的依赖：仓库为什么这么深

你只下单了 2 个包，为什么 node_modules 里躺着一堆陌生的名字？因为包自己也下单：

类比你买了一套衣柜（vite），厂家发货时并不只寄衣柜——里面还带着螺丝、滑轨、内衬板（vite 的依赖 rollup、esbuild……），而滑轨厂又附带自己的小零件。传递依赖（transitive dependencies）就是「货里有货」：你的清单只写了直接依赖（direct dependencies），仓库里却是整整一棵供应链树。
通用命令行
npm ls --all            # 参数 --all：画出完整供应链树（直接依赖 + 传递依赖全展开）
npm ls vite             # 只看 vite 这条供应链——它一个人就拖家带口拖来一串
my-shop@1.0.0
`-- vite@5.4.8
  |-- esbuild@0.21.5          ← vite 的依赖：超快的编译器
  |-- rollup@4.21.2           ← vite 的依赖：打包器
  `-- postcss@8.4.45          ← vite 的依赖：CSS 处理器
      `-- nanoid@5.0.7        ← postcss 的依赖……货里有货，层层套娃

5.3 货架的玄机：扁平化与幽灵依赖

早期 npm 会把每个包的依赖藏在各自文件夹里（嵌套式），结果同一个 lodash 在仓库里出现 8 份、路径长到 Windows 都喊疼。于是 npm 3 起尽量拍扁：能共用的包全提到仓库第一层，像超市把爆款商品全部陈列到门口货架。

幽灵依赖拍扁带来一个暗坑：你没买过的包，也躺在第一层货架上——代码里 import 'nanoid' 居然能成功！但它没写进你的 package.json：哪天 vite 升级不再需要 nanoid，它一夜消失，你的代码当场崩掉。军规：代码里 import 的每个包，都必须亲手装进 dependencies——哪怕知道仓库里已经有了。

5.4 仓库里的暗门：.bin 文件夹

细看 node_modules 里面还有个 .bin 文件夹（bin = binary，可执行程序）——装 vite 时，它自带一个同名的命令行程序，就被安放在这里。这是第 8 章「npm scripts 能直接喊 vite」和第 9 章「npx」的秘密伏笔。

5.5 仓库不搬家：node_modules 为什么不进 Git

类比搬家时你带走采购清单和小票（package.json + package-lock.json），不带走满仓库的货（node_modules）——到了新家照单再买一份就是了。原因有三：① 仓库动辄几百 MB 到几个 GB，塞进 Git 仓库臃肿到没法协作；② 里面有大量二进制文件（编译过的、平台专属的），Git 没法高效处理；③ 清单在，货随时精确复原（这正是小票存在的意义）。
通用文件：.gitignore（放在项目根目录，Git 会照它忽略清单上的东西）
node_modules        # 仓库不搬家：Git 忽略整个 node_modules 文件夹
dist                # 打包产物（第 8 章会讲到 build 的输出）也不进 Git——它能随时重新生成
.env                # 环境变量文件里有密钥，绝对不进 Git（安全红线）
串门Git 本身不熟的话，这里有同目录的姊妹篇《Git 零基础完全教程》，第 6 章「.gitignore 禁拍名单」把这事讲得极细。

  1. 跑 npm ls --all，数一数你的仓库一共躺了多少个包（结尾有汇总行）；
  2. 对比实验：新建项目 A 只装 lodash（0 个传递依赖），项目 B 只装 vite——用 npm ls --all 感受供应链的差距；

06

版本号的哲学：semver

^ 和 ~ 这两个小帽子，是 npm 世界最重要的两个符号——一次讲透

「我们用的是 React 18」——这句话太粗糙了：18.0.0 和 18.3.1 是两个有明显差距的版本。npm 世界的版本有一整套国际公约，叫语义化版本（Semantic Versioning，简称 semver）。看不懂它，就看不懂 package.json 里的天书。

6.1 三段式：主版本.次版本.补丁号

类比版本号 4.17.21 读作「第 4 代产品的第 17 次添功能、第 21 次补小洞」：主版本（major）= 换代——产品推倒重来，旧用法可能不兼容；次版本（minor）= 添新功能——旧用法照旧，多了新玩具；补丁号（patch）= 补小洞——只修 bug，不改任何接口。
变化术语意味着举例（lodash）
4.17.21 → 5.0.0主版本升级（breaking）破坏性变更：可能有 API 被删改——升级前要读迁移指南4.x 的老代码不一定还能跑
4.17.21 → 4.18.0次版本升级新增功能，向后兼容——放心升多了个新函数而已
4.17.21 → 4.17.22补丁升级只修 bug，绝对安全——闭眼升某个边界 bug 修了

6.2 范围符号：^ 与 ~ 两个小帽子

package.json 里几乎从没见过裸的 "4.17.21"，而是 "^4.17.21"——帽子才是主角：

写法名字允许装的版本一句话性格
^4.17.21插入号（caret，默认）4.17.21 ～ 4.99.99（不越 4）「换代不行，添功能随便」
~4.17.21波浪号（tilde）4.17.21 ～ 4.17.99（不越 4.17）「添功能也不行，只准补洞」
4.17.21精确版本（裸数字）只有 4.17.21「批号锁死，一格都不动」
* 或 latest通配任意最新版「随便来，出事算我输」——别用
>=4.0.0 <5.0.0区间表达式大于等于 4、小于 5高级区间语法，偶尔在老项目里见到
帽子哲学默认的 ^ 是乐观主义：相信次版本升级不出事，让新功能有机会进来；~ 是保守主义；裸版本是锁死主义。主版本永远是一道闸门——不管多乐观，npm 都绝不自动帮你跨过 5.0 这道坎（破坏性变更必须人工点头）。这就是为什么 ^4.17.21 永远不会装出 5.x。

6.3 想锁死？--save-exact

通用命令行
npm install lodash --save-exact   # 参数 --save-exact（缩写 -E）：记台账时不要帽子，写死精确版本 4.17.21
npm config set save-exact true    # 命令 config set：把「默认精确」设为个人偏好——以后每次 install 都自动 -E

6.4 侦查版本：npm view

下单前先看看货架上有几批货：

通用命令行
npm view lodash version          # 命令 view：查包的「档案」；参数 version：只看最新版本号这一项
npm view lodash versions          # versions（复数）：这个包发布过的全部版本清单——一路从 0.1 排到今天的长龙
npm view vite dependencies        # dependencies：看 vite 自己的清单（它拖着谁）——下单前先看货里有货
4.17.21                          ← 最新版
[ '0.1.0', '0.2.0', … '4.17.20', '4.17.21' ]   ← 发布史长龙（节选）
{ esbuild: '^0.21.3', rollup: '^4.20.0', … }   ← vite 的依赖（它自己清单上的一栏）
0.x 时代的特殊性主版本是 0（如 ^0.5.3）意味着「产品还没定型」——公约规定此时次版本就可能有破坏性变更，所以 ^0.5.3 实际只允许 0.5.x（跟 ~ 一样保守）。看到 0 开头的依赖，升级更要看仔细。

07

package-lock：采购小票

清单只写「要沙发」，小票写死「哪厂哪批」——团队所有人拿到一模一样的货

如果只有 package.json，会发生可怕的事：同一份清单，不同时间补货，收到的货不完全一样。这一章讲 npm 如何用一张「小票」终结这种漂移。

7.1 漂移事故现场

假设清单上写着 "dayjs": "^1.11.0"：

  1. 周一，小明初始化项目——商城里 1.11 系最新是 1.11.10，装上了，顺手记进小票；
  2. 周三，dayjs 发布 1.11.11（修了个 bug）；
  3. 周五，小红拿到同一份清单（没有小票）重新补货——装到的是 1.11.11；
  4. 周六，线上出了个只在 1.11.11 出现的 bug——小明机器上却复现不了。「在我电脑上是好的啊」，史诗级甩锅现场。
类比package.json 写的是「要一张北欧风沙发」（范围）；package-lock.json 记的是「X 牌 Y 型号 Z 批次，单价 899，生产日期 2026-09-01」（精确到个位）。有小票在，任何时候任何机器照票补货，到手的都是同一批货。

7.2 小票长什么样

通用文件：package-lock.json 片段（教学示意 · 真实文件不能写注释）
{
  "name": "my-shop",                    // 锁文件也记着项目名（和 package.json 对应）
  "version": "1.0.0",                   // 项目版本
  "lockfileVersion": 3,                 // 字段 lockfileVersion：小票的格式版本（npm 自己的格式编号，v3 是 npm 9+ 的现行格式）
  "requires": true,                     // 字段 requires：历史遗留标记，意为「本小票覆盖所有子依赖」，固定 true
  "packages": {                         // 字段 packages：小票的正文——整棵供应链树，每个包一条记录
    "": {                               // 空字符串键 = 「项目自己」这一条
      "name": "my-shop",                // 项目名
      "dependencies": {                 // 项目直接依赖的精确版本（比清单更细）
        "dayjs": "^1.11.10"             // 清单上写的范围照抄在此
      }
    },
    "node_modules/dayjs": {             // 键 = 货物在仓库中的位置：每个包对应 node_modules 里的一条路径
      "version": "1.11.10",             // 字段 version：锁死的精确版本——小票的灵魂！周一装的 1.11.10 就锁在这儿
      "resolved": "https://registry.npmjs.org/dayjs/-/dayjs-1.11.10.tgz",   // 字段 resolved：这批货的「提货地址」——从哪个 URL 下载
      "integrity": "sha512-…"           // 字段 integrity：防伪钢印（内容哈希）——下载后重新算一遍，对不上就拒收
    }
  }
}

7.3 integrity：防伪钢印

哈希integrity 的值是下载内容的指纹（sha512 哈希算法算出的一串十六进制）：文件哪怕被篡改一个字节，重算的指纹就完全不同。npm 每次下载都会验印——这就是「供应链投毒」最难攻破的一环。你几乎不用管它，但要知道小票里这串乱码是保命的，别手贱删改。

7.4 npm ci：照小票精确补货

有个专门「严格照票办事」的命令——ci（clean install，干净安装）：

通用命令行
npm ci                 # 命令 ci：① 先把现有 node_modules 整个删掉；② 照 package-lock.json 一字不改地精确复原整棵供应链树
                       # 铁规矩：package.json 和 lock 对不上时它直接拒绝工作（宁可报错，不要漂移）
npm ci --omit=dev      # ci 也支持省略施工队工具——服务器部署的黄金组合
npm installnpm ci
听谁的package.json 为主，lock 为辅——范围允许时顺手升到范围内最新lock 为唯一圣旨——一字不改
会改文件吗可能更新 package.json 和 lock只读不写，两份文件一个字不动
速度较慢（要算范围、查最新）更快（照票搬货就行）
使用场合开发机日常增删依赖服务器 / CI 部署、同事接手项目首次装依赖

7.5 两条铁律

记进 Git① package-lock.json 必须提交进 Git（它和 node_modules 相反——小票要跟人走，货不用）；② 永远不要手动编辑 lock 文件——它由 npm 自动维护，你改它等于在小票上涂改批号。改版本的正道是：装/升指定的包，让 npm 自己刷新小票。
别的采购员yarn 的小票叫 yarn.lock，pnpm 的叫 pnpm-lock.yaml——格式不同、使命相同。一个项目里只应存在一种采购员的小票；混用两位采购员，等于两本账，迟早打架。

  2. 删掉 node_modules，分别体验 npm install 和 npm ci 的恢复过程，对比耗时与输出（ci 会报告 added N packages，且绝不改 lock）；
  3. 做个小实验：手动把 package.json 里 lodash 的版本改成 ^999.0.0 再跑 npm ci——欣赏它「宁可报错不要漂移」的暴脾气（记得改回来）。

npm scripts：开工面板

把常用命令做成一排开关——按下 npm run dev，后面一长串命令全自动执行

项目要跑开发服务器、要打包、要跑测试……这些命令又长又难记。scripts 一栏就是你的一键开工面板：把长命令接在短开关后面，从此只按开关。

8.1 第一个开关：npm run + 名字

通用文件：package.json 的 scripts 一栏（教学示意 · 真实文件不能写注释）
  "scripts": {                    // 字段 scripts：开关面板，键 = 开关名，值 = 按下后真正执行的命令
    "hello": "echo 你好，npm！"     // 开关 hello：接的命令是 echo（打印一句话）——用最简单的命令练手感
  },
通用命令行
npm run hello          # 命令 npm run + 开关名：按下 hello 这个开关——echo 被执行，屏幕打印一句话
npm run                # 不带名字：列出面板上所有开关——忘了有哪些开关就敲它
> my-shop@1.0.0 hello             ← npm 先报幕：哪个项目的哪个开关
> echo 你好，npm！                  ← 接着复述：实际执行的命令
你好，npm！                          ← 命令的真正输出

8.2 两个特权开关：start 与 test

绝大多数开关都要 npm run 名字，唯独两个是「贵族」，run 都能省：

通用命令行 vs scripts 一栏
npm start              # 等价于 npm run start——「启动项目」的官方保留开关
npm test               # 等价于 npm run test——「跑测试」的官方保留开关
npm run dev            # 自己起名的开关没有特权，必须带 run（dev = development 开发的常用缩写）
社区默契开关名是一套行业暗号：克隆任何项目，先看它的 scripts——dev（起开发服务器）、build（打包成品）、test（跑测试）、lint（查代码风格）、preview（预览打包结果）。你自己的项目照这个默契起名，别人（和未来的你）零成本上手。

8.3 scripts 的隐藏超能力：免路径直呼命令

这是 scripts 最重要的设计——没有它整个面板就不成立：

通用命令行对比
vite --version         # 直接敲 vite？报错！——系统 PATH 里根本没有这个命令（它藏在项目仓库的 .bin 暗门里）
npm run build          # 但在 scripts 里写 "build": "vite build"，npm run 时一切正常——为什么？
答案每次 npm run，npm 都会先给这条命令的 PATH 里注入本项目的 node_modules/.bin（第 5 章那个暗门文件夹）——所以 scripts 里可以裸写 vite、eslint、vitest，不用写一长串路径。这就是「装在项目里的命令行工具」的正确打开方式。

8.4 钩子：pre 与 post

通用scripts 一栏（教学示意 · 真实文件不能写注释）
  "scripts": {
    "prebuild": "echo ① 先清场地",     // 开关 prebuild：魔法前缀 pre——按 build 时它自动先执行
    "build": "echo ② 正式施工",        // 主开关 build
    "postbuild": "echo ③ 收工播报"     // 开关 postbuild：前缀 post——build 结束后自动跟上
  },
$ npm run build           ← 只按了 build 一个开关……
① 先清场地               ← prebuild 被自动带出
② 正式施工               ← build 本尊
③ 收工播报               ← postbuild 自动收尾

8.5 传参：两个减号是「交接棒」

通用命令行
npm run dev -- --host   # 空格 + 两个减号 --：交接棒——它后面的参数原样递给 dev 开关接的那条命令
                       # 假设 "dev": "vite"，最终执行的就是 vite --host（对外暴露开发服务器）
为什么要两个减号不写 -- 的话，npm 会以为 --host 是给npm 自己的参数而不认识、直接报错；写了 --，npm 就明白「后面这些是给开关里那条命令的，别拆包装，原样转交」。一根交接棒，避免两边抢包裹。

8.6 实战：给 my-shop 配齐四件套

通用文件：package.json（教学示意 · 真实文件不能写注释）
  "scripts": {
    "dev": "node server.js",                 // 开关 dev：用 node 直接跑 server.js（起个本地服务）
    "build": "echo 打包完成",                 // 开关 build：真实项目里这里是 vite build 之类的打包命令
    "test": "node test.js",                  // 开关 test：跑测试脚本
    "greet": "cowsay 一键开工！"              // 开关 greet：调个乐子——记得先 npm i -g cowsay（或者删掉这行）
  },
动手练习 08
  1. 给 my-shop 加 hello 开关并跑通；再加一对 prehello / posthello，观察执行顺序；
  2. 写一个 "tools": "npm ls --all" 开关，体会「开关里也能嵌 npm 命令」；
  3. 挑战：做一个 greet 开关，命令为 node -e "console.log(process.version)"（-e = 直接执行引号里的 JS 代码）——按开关打印出你的 Node 版本。

npx：租用不买断

只想用一次的工具，何必买回家占地方——扫码租用，用完即走

npx（Node Package eXecute）是 npm 自带的双胞胎兄弟：npm 管买，npx 管租。它是现代前端工作流里出镜率最高的两个字母。

9.1 痛点：为了切一次菜，买台切菜机？

想体验一个脚手架工具（比如 create-vite，一辈子可能就用十次）。老办法：先 npm i -g create-vite 装进全局——占地方、难升级、换电脑全没。npx 的方案：临时下载、立即运行、用完扔掉：

类比全局安装 = 买断一台占地方的家伙什；npx = 扫码租用：出门扫码即用，用完人家自己收走。第一次租要现场调货（慢），第二次租从缓存中转仓直接取（快）。

9.2 两个经典用法

通用命令行
npx cowsay 租来的牛      # 命令 npx + 包名 + 参数：先找本地有没有 cowsay——没有就临时下载一份来执行这条命令
npx create-vite my-app   # 经典场景：脚手架「租用」——不用装任何东西，直接现场调来 create-vite 创建一个新项目 my-app
Need to install the following packages:    ← 第一次租：npx 先打招呼「这货本地没有，我临时下一份」
create-vite@6.1.0                          ← 临时下载的包名与版本（从缓存/商城取）

Ok to proceed? (y)                        ← 出于安全要你点头——回车或 y 同意（这就是下一节的 --yes）
通用命令行
npx cowsay --yes 再租一次  # 参数 --yes（缩写 -y）：跳过「确认租用」的提问——写自动化脚本时必备
npx create-vite@5 my-app   # @5：连租都指定大版本——确保工具行为可预期（5 和 6 的交互可能不同）

9.3 npx 的两副面孔：本地优先

很多介绍只讲「租」，漏了 npx 的另一半性格：本地有，绝不外租：

情况npx 的行为例子
项目 node_modules/.bin 里有这个命令直接用本地的（绝不外借）——这就是为什么项目里 npx vite 永远跑你项目装的版本npx vite
本地没有临时下载执行，完事走人（缓存放中转仓）npx create-vite
两兄弟分工一句话记牢：要装回家用 package.json 管的 → npm i；只想跑一次、或者想用「本项目这一版」的 → npx。此外 scripts 里其实不用 npx（第 8 章讲过：npm run 自动注入 .bin 路径）——scripts 里裸写命令才是最优雅的。
动手练习 09
  1. npx cowsay 我是租来的，观察第一次的「临时下载提示」；紧接着再跑一遍——感受缓存提速；
  2. 在 my-shop 里装了 vite（第 4 章装过）后跑 npx vite --version——它跑的是本地版（输出里没有下载提示）；
  3. 挑战：npx http-server（一个零配置静态服务器）在你任意文件夹里起一个网站，浏览器访问它给的地址（Ctrl+C 关闭）。

卸载、更新与体检

退货、换新、盘点——让仓库始终保持「台账与货架一致」

装只是开始。这一章补齐包管理的日常运营：不想要的退掉（uninstall）、旧了的盘点换新（outdated + update）、仓库里来历不明的清走（prune）。

10.1 退货：npm uninstall

通用命令行
npm uninstall lodash         # 命令 uninstall（缩写 un / remove / rm 都认）：退货——从 node_modules 搬走，同时从 package.json 台账划掉，lock 同步更新
npm uninstall -D vite        # -D：从 devDependencies 台账划掉（装的时候挂哪本账，退的时候也找那本）
npm uninstall -g cowsay      # -g：退全局的货——第 4 章装的全局玩具，玩腻了就还回去
removed 1 package in 2s      ← 战报：removed = 退掉几个包
手动删除 ≠ 退货直接删 node_modules/lodash 文件夹或手动改 package.json，都是黑箱操作——lock 小票上仍记着这货在册，下次 npm install 它又回来了。退货请走柜台（uninstall），一次办三件事：撤货、销账、改小票。

10.2 盘点：npm outdated

项目跑久了，货架上的包都有新版了。盘点一下：

通用命令行
npm outdated                 # 命令 outdated：盘点表——列出所有「有新款可换」的依赖；没输出 = 全是最新，谢天谢地
Package  Current  Wanted  Latest  Location  Depended by
dayjs     1.11.10  1.11.11 1.11.11  dayjs    my-shop
vite      5.4.8    5.4.8   6.0.0    vite     my-shop
           ↑现在装的   ↑帽子允许的  ↑商城最新
           （Current）（Wanted） （Latest）
列名含义类比
Current现在装着的精确版本家里这台的出厂批号
Wanted按 package.json 的帽子（^/~）允许升到的版本保修条款内可免费换到的新款
Latest商城上的最新版（可能已越过大版本）展示厅里最新一代

看懂这张表就懂了升级的两种境界：Wanted ≠ Latest 时（如 vite 那行），说明新版跨了大版本——帽子拦着，得人工决策。

10.3 换新：npm update

通用命令行
npm update                   # 命令 update：把所有依赖升到各自的 Wanted 版本——帽子内的免费换新，安全
npm update dayjs             # 只给 dayjs 换新
npm install vite@latest      # 想跨大版本？update 不越雷池——改用 install 指定 @latest，等于重新下单最新款（台账帽子同步改写）
升级军规跨大版本（Current 4.x → Latest 5.x）= 有破坏性变更的可能。升级前：① 去该包的 GitHub/官网看 Migration Guide（迁移指南）；② 跑一遍项目测试；③ 小步快跑——别一次升五个大版本，出了问题都不知道谁干的。

10.4 清仓：npm prune 与杂项

通用命令行
npm prune                    # 命令 prune（修剪）：清掉「躺在仓库里但台账上没有」的包——手动删过 package.json 里的行？用它收尾
npm fund                     # 命令 fund：看看你的依赖里哪些作者在寻求资助（开源不易，有余力支持一下）
npm cache verify             # 命令 cache verify：校验中转仓的存货完整性（哪天安装总报怪错，先验货）
npm cache clean --force      # 命令 cache clean：清空中转仓；--force = 强制（npm 怕你误删特意加的门）——网络问题百药无效时的最后三板斧之一
灵异故障的万能起手式遇到「明明装了却找不到」「报错和昨天不一样」：① 删 node_modules；② npm ci 照小票复原。九成的「薛定谔依赖」一招治愈——货架可以随时重建，这是 npm 体系给你的底气。
动手练习 10
  1. 装个 axios 再 npm uninstall axios，对比前后 package.json 和 lock 的变化；
  2. 跑 npm outdated 看看你的 my-shop 有没有落后于时代的包；
  3. 完整体验万能起手式：删 node_modules → npm ci——记住这两步，够你吃十年。

配置与 .npmrc：偏好单

告诉采购员你的长期偏好：常去哪家分仓、要不要开发票（精确版本）

npm 的每个习惯都可以调：默认去哪家商城提货、全局包装在哪、要不要永远锁死版本……这些偏好就存在 .npmrc 文件里（rc = run commands，Unix 世界「运行配置」的老传统后缀）。

11.1 读写配置的三板斧

通用命令行
npm config get registry     # 命令 config get：读一项配置——现在默认去哪家商城（registry = 注册表/仓库地址）
npm config set registry https://registry.npmmirror.com   # 命令 config set：写一项——把默认商城换成 npmmirror（阿里维护的国内镜像站）
npm config list              # 命令 config list：把当前生效的配置整页打出来，逐行核对
npm config delete registry   # 命令 config delete：删掉这项自定义——恢复官方默认值 https://registry.npmjs.org

11.2 registry：官方仓 vs 国内分仓

类比registry = 提货点地址。官方仓（registry.npmjs.org）远在国外，国内直连常常龟速；npmmirror（原淘宝镜像）是阿里在国内开的分仓——货一样（每隔几分钟同步一次），路近了快十倍。发布自己的包时记得换回官方仓（镜像一般只进不出）。
通用命令行
npm install lodash --registry=https://registry.npmmirror.com   # 单次用法：--registry=地址 只对这一条命令生效——不想改全局偏好时的临时方案
npm ping                      # 命令 ping：测试与当前 registry 的连通性（像网络医生的听诊器），排查网络问题第一步

11.3 三张偏好单：优先级分明

层级文件位置影响范围典型用途
项目级（优先级最高）项目根目录 .npmrc只影响这个项目团队统一镜像源、统一 registry
用户级~/.npmrc（家目录）影响这台机器上的你个人镜像偏好、登录令牌
全局级（优先级最低）Npm 安装目录内影响所有用户极少改动
通用文件：项目里的 .npmrc（真实可用 · 这个文件本来就支持 # 注释）
registry=https://registry.npmmirror.com    # 配置项 registry：本项目一律去国内分仓提货（随项目提交进 Git，全团队共享）
save-exact=true                            # 配置项 save-exact：本项目装包默认锁死精确版本（第 6 章的 -E 变成常态）
查找顺序npm 找配置就像穿衣服：项目级穿最里层（贴身生效），用户级套外面，全局级最外。同一项冲突时，里层覆盖外层。所以「公司项目必须走内网仓库」写项目级、「我自己爱走镜像」写用户级，互不打架。

11.4 常用配置速查

配置项管什么示例
registry默认提货点npm config set registry https://registry.npmmirror.com
save-exact装包默认锁精确版本npm config set save-exact true
prefix全局包安装位置npm config get prefix（排查「全局命令找不到」看它）
proxy / https-proxy公司内网代理npm config set proxy http://proxy.company.com:8080
engine-strict强制检查 Node 版本要求npm config set engine-strict true

  1. 跑 npm config list 通读一遍你机器的生效配置（重点关注 registry 指向哪）；
  2. 体验优先级：用户级设 save-exact true，再在项目级 .npmrc 里写 save-exact=false，装个包看台账里帽子在不在；
  3. 跑 npm ping 确认你的 registry 通畅。

发布自己的包：上架全球商城

让全世界的 npm install 都能装到你的代码——这一章你从顾客变成商家

前面 11 章你都是顾客。这一章角色互换：写一个包，发布到 npmjs.com，从此任何人（包括未来的你）一条 npm install 就能用上它。

12.1 开店手续：注册与登录

  1. 去 npmjs.com/signup 注册一个免费账号（记住用户名——它就是你店面的招牌，也是 scope 包的前缀）；
  2. 开启两步验证（2FA，账号安全设置里）——官方强烈建议，发布会要求输入动态验证码（OTP）；
  3. 回到终端登录：
通用命令行
npm login          # 命令 login：登录——打开浏览器完成 npmjs.com 的账号验证，成功后终端自动续上
npm whoami         # 命令 whoami（我是谁）：验证登录状态——打出你的用户名就是登录成功
alicelv           ← 你的 npm 用户名（打出来的是谁，将来发布就以谁的名义）

12.2 备货：一个最小可发布的包

发布需要的家当少得惊人：package.json + 入口文件 + README，三样齐就能上架。新建项目 lucky-utils（一个「幸运抽奖」小工具包）：

通用文件：index.js（包的入口 · 每个函数、变量都有注释）
// 文件：index.js —— 包的入口（package.json 的 main 字段指向它）
// 这个包对外提供两个函数：randomLucky（幸运数）、pickOne（抽一个）

/**
 * 函数 randomLucky：返回一个 1 到 max 之间的随机整数（含两端）。
 * 形参 max：随机数上限，不传时默认 100。
 */
function randomLucky(max = 100) {              // 函数名 randomLucky（幸运数）；形参 max（上限）带默认值 100
  return Math.floor(Math.random() * max) + 1   // Math.random()：JS 内置方法，产生 [0, 1) 的随机小数；乘 max 得 [0, max)；Math.floor() 向下取整得 0 ~ max-1；+1 平移成 1 ~ max
}

/**
 * 函数 pickOne：从数组里随机抽出一个元素。
 * 形参 arr：待抽取的数组。
 */
function pickOne(arr) {                        // 函数名 pickOne（抽一个）；形参 arr（数组）
  const index = randomLucky(arr.length) - 1    // 常量 index（随机下标）：arr.length 是数组长度（JS 里合法下标是 0 ~ 长度-1），用 randomLucky 取 1~长度 再减 1 刚好对上
  return arr[index]                            // 返回：用随机下标从数组里取出元素
}

/**
 * 对象 lucky：把两个函数打包成一个对象对外提供（使用者可以 lucky.randomLucky(66) 这样点着用）。
 */
const lucky = { randomLucky, pickOne }         // 常量 lucky：ES6 简写——键名和函数同名时可只写一个（等价于 { randomLucky: randomLucky, pickOne: pickOne }）

module.exports = lucky                         // 变量 module.exports：CommonJS 导出机制——require() 这个包的人拿到的就是 lucky 这个对象
通用文件：package.json 关键字段（教学示意 · 真实文件不能写注释）
{
  "name": "@alicelv/lucky-utils",     // 字段 name：务必用 scope 包（@你的用户名/包名）——普通名字早被抢光了，专区里随便起
  "version": "1.0.0",                 // 字段 version：首次发布从 1.0.0 开始
  "description": "幸运抽奖小工具：随机数与随机抽取",   // 字段 description：商城搜索结果里的一句话介绍
  "main": "index.js",                 // 字段 main：入口——使用者 require 的就是这个文件（module.exports 就在它里面）
  "keywords": ["random", "lucky", "utils"],          // 字段 keywords：搜索关键词，帮助顾客搜到你
  "license": "MIT",                   // 字段 license：MIT = 最宽松的「随便用」协议
  "files": ["index.js"]               // 字段 files：上架清单——发布时只带上这些文件（README 和 package.json 永远自动带上）
}

12.3 上架：npm publish

通用命令行（在 lucky-utils 项目根目录）

全局工具与 npm link

命令行利器的正确养法，以及「边写边测」的本地联调神器

两类进阶玩法：一是全局 CLI 工具（装一次、满机跑），二是 npm link——你在写自己的包时，不用反复发布就能在真实项目里试用的「临时直通车」。

13.1 CLI 工具是怎么变成命令的：bin 字段

为什么装完 http-server 就多了个同名命令？秘密在包清单的 bin 字段：

通用文件：某个 CLI 工具的 package.json 片段（教学示意 · 真实文件不能写注释）
  "bin": {                          // 字段 bin：声明「我提供一个命令行程序」
    "http-server": "./bin/http-server"   // 键 http-server = 注册的命令名；值 = 命令背后真正执行的 JS 文件路径
  },

安装时（无论 -g 还是项目级），npm 把这个程序链接到「命令可达」的位置——全局装就链到系统 PATH，项目装就链进 node_modules/.bin。体验几个经典全局工具：

通用命令行
npm install -g typescript    # 全局装 TypeScript（给 JS 加类型的语言）；它带一个 bin 命令 tsc（编译器）
tsc --version                # tsc：TypeScript 编译器命令；--version 报版本——全局命令在任意文件夹可用
npm ls -g --depth=0          # 命令 ls -g：列出全局已装的包；--depth=0（深度 0）：只看第一层，别把传递依赖也倒出来
Version 5.6.2               ← tsc 活了
C:\Users\你\AppData\Roaming\npm   ← 全局仓库位置（第 2 章查过的那个）
├── cowsay@1.7.0             ← depth=0：一层清单，清爽

13.2 npm link：开发中包的「直通车」

场景：你在写 lucky-utils（第 12 章的包），想在 my-shop 项目里试试效果。老办法要 发布 → 安装 → 发现 bug → 改 → 再发布，一天发八个版本，商城变成你的草稿纸。npm link 的解法：把开发中的包直接「接线」到项目里：

类比npm link = 在「新品研发台」和「你的货架」之间拉一条传送带：研发台上改一版，货架上立刻同步——不用走「上架→下单→物流」的完整流程。测满意了再正式发布，传送带一撤，换上正经货。
通用命令行：link 两步走
cd lucky-utils            # 第一步：进入「正在开发中的包」的目录
npm link                  # 命令 link：把这个包登记为本机的「研发中新品」——在全局区挂一个指向当前文件夹的链接

cd ../my-shop             # 第二步：切到「要试用它的项目」
npm link @alicelv/lucky-utils   # link + 包名：把研发台的新品接进本项目——node_modules 里出现一个「活的」链接（不是拷贝）
通用文件：my-shop 里试用（test-lucky.js）
// 文件：test-lucky.js —— 在项目里直接试用开发中的包

通用命令行

link 的坑① link 进来的包不写进 package.json（它是「活的链接」不是「到货」），所以换台电脑就失效；② 忘了 unlink 又 npm install，可能出现「一半链接一半真货」的混血状态，症状诡异——排查口诀：npm ls 包名，看它是不是 LINK 标记。

安全审计：收货验货

货是别人送的——进货前验一验，供应链时代的安全必修课

你的项目 = 你的代码 + 几百个陌生人的代码。万一供应链上某个环节被投毒呢？npm 内置了验货员 npm audit——这一章学会读它的报告，也学会四条保命军规。

14.1 风险从哪来

类比供应链投毒不只是小说：历史上真实发生过某热门包的维护权被转让给陌生人、新「维护者」在里面塞了偷密钥的代码（著名的 event-stream 事件）；也有包名「傍大款」（typosquatting，拼错一两个字母的山寨包）骗安装。你的防线：小票锁批（lock 的 integrity）+ 定期验货（audit）+ 不乱装冷门包。

14.2 npm audit：验货报告

通用命令行
npm audit            # 命令 audit（审计）：把整棵供应链树逐包对照「已知漏洞数据库」，出一份体检报告
npm audit --json     # --json：输出机器可读的 JSON 格式（写自动化检查时用）
found 2 vulnerabilities (1 moderate, 1 high)    ← 总评：发现 2 个漏洞（1 个中危 + 1 个高危）

# Run npm audit fix to fix them, or npm audit for details    ← 提示：跑 audit fix 可自动修
严重级别含义应对
low（低危）理论可利用，条件苛刻记录在案，不慌
moderate（中危）特定场景下可被利用排期修复
high（高危）常见场景即可利用尽快修
critical（危急）可直接远程执行/泄密立刻修
看懂漏洞链条audit 详情会画出「谁 → 引入了谁 → 谁有毒」的链条：你的清单里只有 vite，但 vite 的依赖 X 的依赖 Y 有洞——这条链告诉你该催谁升级（通常是升最上游的 vite，让它甩掉旧 X）。

14.3 npm audit fix：自动验货员动手修

通用命令行
npm audit fix            # 命令 audit fix：在「帽子允许的范围内」自动升级有洞的包——安全，小票同步更新
npm audit fix --force    # 参数 --force：连大版本也敢跨——可能引入破坏性变更，先备份再跑，跑完立刻全量测试
为什么 --force 危险自动跨大版本 = 自动接受别人的破坏性变更。npm 把这个选择权强制留给人——它知道「能跑」和「行为没变」是两回事。--force 前先确认项目有测试、且代码已提交 Git（随时可回滚）。

14.4 四条保命军规

  1. 装前看三样：周下载量（过万的才靠谱）、最近发布时间（三年没动的要警惕）、依赖它的知名项目；
  2. 小票必进 Git + 部署用 npm ci：integrity 钢印防掉包（第 7 章）；
  3. 不装用不上的包：每加一个依赖 = 多签一份安全合同；npm install --ignore-scripts 可禁止包的安装脚本乱跑（更硬核的保险栓）；
  4. 定期 npm audit：把它加进 CI（持续集成）流水线，漏洞自动报警。

workspaces：一栋楼多个房间

几个项目共享一套基建——monorepo 的 npm 原生玩法

做产品常常是「一栋楼」：官网 + 管理后台 + 共享的组件库 + 工具函数库。每栋「房间」各自一份 node_modules 各自一份清单？workspaces（工作区）让你整栋楼统一采购、共享仓库。

15.1 多仓库的痛 vs 一栋楼的爽

多仓库（multi-repo）一栋楼（monorepo + workspaces）
类比每户各自买车、各自车库整栋楼共享一部货梯、一个大仓库
改一处公共代码发版 → 各仓库挨个升级改完立即全楼生效
重复安装同一份 lodash 装 N 遍全楼一份，省时省硬盘
适合互不相关的项目关系紧密的产品矩阵（App + 后台 + 共享库）

15.2 搭一栋楼

通用目录结构 + 根 package.json（教学示意 · 真实文件不能写注释）
my-tower/                    # 「楼」的根目录（monorepo 的根）
├── package.json             # 楼总的清单：声明哪些房间属于这栋楼
└── packages/                # packages：约定俗成的「房间」集中营
    ├── web/                 # 房间一：官网
    │   └── package.json     # 房间自己的小清单
    ├── admin/               # 房间二：管理后台
    │   └── package.json
    └── shared-ui/           # 房间三：全楼共享的组件库
        └── package.json
{
  "name": "my-tower",              // 楼名（根项目一般不发布，名字随意）
  "private": true,                 // 字段 private：true——根项目是「自住房」，永不发布上架（避免误发整栋楼）
  "workspaces": [                  // 字段 workspaces：房号登记簿——数组里列出「哪些文件夹算我的房间」
    "packages/*"                   // 通配写法：packages 下面每个文件夹都是一个房间（web、admin、shared-ui 全认领）
  ]
}

整栋楼只跑一次 npm install（在楼根目录）：所有房间的依赖统一采购，全部搬进楼根的一个 node_modules——这就是「共享大仓库」。

15.3 房间之间互相「串门」

通用文件：packages/web/package.json（教学示意 · 真实文件不能写注释）
{
  "name": "@my-tower/web",                // 房间也有自己的名字（用楼名当 scope 前缀，整齐）
  "version": "1.0.0",
  "dependencies": {
    "@my-tower/shared-ui": "^1.0.0"       // 声明依赖「同楼的另一个房间」——npm 发现这个名字就是自家房间，直接用符号链接接通（相当于全自动 npm link），改组件库立刻在官网生效
  }
}

15.4 分房间操作：-w 参数

通用命令行（都在楼根目录执行）
npm install dayjs -w web              # 参数 -w（workspace）+ 房间名：把 dayjs 装进「web 这个房间」的清单（而不是楼根的）
npm run build -w web                   # 跑 web 房间的 build 开关——不用 cd 进房间
npm run build --workspaces             # 遍历所有房间，挨个跑 build——整栋楼流水线一键启动（某房间没这个开关会跳过）
npm run build --workspaces --if-present # --if-present：没有该开关的房间安静跳过，不报错（更文明的遍历）
生态位置workspaces 是 npm 原生的「一楼多房」方案，够用且零门槛；楼上还有两位管家——lerna（老牌，管发版编排）和 turborepo（新贵，管构建缓存提速），它们不替代 workspaces 而是叠加其上。先用原生的，痛了再请管家。

第 2 步：写核心代码（三个函数，逐个有注释）

通用文件：index.js
// 文件：index.js —— fortune-num 包的入口。对外提供三个函数：rollDice / flipCoin / shuffle

/**
 * 函数 rollDice：掷骰子。返回 1 到 sides 之间的随机整数（含两端）。
 * 形参 sides：骰子有几面，默认 6。
 */
function rollDice(sides = 6) {                 // 函数 rollDice（掷骰子）；形参 sides（面数）默认值 6
  return Math.floor(Math.random() * sides) + 1 // Math.random()：内置方法，[0, 1) 随机小数；乘 sides 得 [0, sides)；Math.floor() 向下取整；+1 平移成 1 ~ sides
}

/**
 * 函数 flipCoin：抛硬币。随机返回字符串「正面」或「反面」。
 */
function flipCoin() {                          // 函数 flipCoin（抛硬币），无参数
  return Math.random() < 0.5 ? '正面' : '反面'  // 三元表达式「条件 ? 真结果 : 假结果」：随机数小于 0.5 走正面，否则反面
}

/**
 * 函数 shuffle：洗牌。返回顺序打乱的新数组，不修改传入的原数组。
 * 形参 arr：待打乱的数组。
 */
function shuffle(arr) {                        // 函数 shuffle（洗牌）；形参 arr（数组）
  const copy = [...arr]                        // 常量 copy：展开运算符 ... 把 arr 的元素逐个抄进新数组（浅拷贝）——原数组毫发无损
  for (let i = copy.length - 1; i > 0; i--) {  // 变量 i：从最后一位下标（长度-1）倒着循环到 1——Fisher-Yates 经典洗牌的骨架
    const j = Math.floor(Math.random() * (i + 1))   // 常量 j：0 ~ i 之间随机一个下标（要交换的搭档）
    ;[copy[i], copy[j]] = [copy[j], copy[i]]   // 数组解构交换：右边先打包成 [值A, 值B]，再拆开分别赋给左边的两个位置——行首分号是防止上一行被误拼接的保险栓
  }
  return copy                                  // 返回打乱后的新数组
}

module.exports = { rollDice, flipCoin, shuffle }   // 变量 module.exports：CommonJS 导出——require() 的人拿到 { rollDice, flipCoin, shuffle } 这个对象

16.2 实战二：CLI 工具 lucky-roll（终端掷骰器）

函数包的「插座」是 require；CLI 工具的插座是 bin 字段——把一个 JS 文件注册成人见人用的命令：

通用文件：package.json 关键新增字段（教学示意 · 真实文件不能写注释）
  "bin": {                              // 字段 bin：CLI 的注册表——声明「我提供一个命令」
    "lucky-roll": "./bin/lucky-roll.js"  // 键 lucky-roll：命令名（用户以后敲的就是它）；值：命令背后执行的文件
  },
通用文件：bin/lucky-roll.js（每个变量、方法都有注释）
#!/usr/bin/env node                       // shebang 行（#!）：告诉操作系统「用 node 执行本文件」；/usr/bin/env node = 「去 PATH 里找 node」——跨平台通用写法

const fortune = require('../index.js')     // 常量 fortune：require 加载上一级目录的 index.js（rollDice 就在里面）——CLI 直接复用函数包的代码

const args = process.argv.slice(2)         // 变量 process.argv：Node 内置对象 process 的 argv 属性——命令行参数数组（第 0 项 node 路径、第 1 项脚本路径）；方法 slice(2)：砍掉前两项，只剩用户传的参数
const max = Number(args[0]) || 6           // 变量 max：Number() 把字符串 '20' 转成数字 20；|| 6（逻辑或）：转换失败（NaN）或没传参时兜底用 6 面骰

console.log(`掷出 ${fortune.rollDice(max)} 点（${max} 面骰）`)   // 模板字符串（反引号）：${} 里嵌变量；调 rollDice 掷骰并打印结果
通用命令行：本地测试 → 发布 → 全球可用
npm link                      # 本地测试：登记研发中新品（第 13 章）——bin 声明的命令也会被临时注册进 PATH
lucky-roll 20                 # 直接敲命令试跑：掷一颗 20 面骰！（"lucky-roll" 不带参数则用默认 6 面）
lucky-roll                    # 默认模式
npm unlink -g                 # 测试满意，撤线

npm publish --access public   # 上架！
npm install -g @你的用户名/fortune-num   # 任何人在任何机器：全局装上你的工具

两种包的关系实战二直接复用了实战一的 index.js——真实世界里 CLI 工具的内核常常就是一层函数包，bin 文件只是「翻译官」：把用户敲的命令和参数翻译成对函数的调用。分两个包发布（函数包给开发者、CLI 给普通用户）是常见的产品分法。

常见报错急救站

红色报错不可怕——按错误代码对号入座，三分钟破案

npm 的报错信息出了名的长——但有用的永远是最顶上那几行：错误代码（code）+ 场景。这一章把最高频的十个病例挂墙，照方抓药。

17.1 十大高频病例总表

报错关键字病因药方
E404 Not Found包名拼错；或包太新、镜像还没同步到；或版本号不存在① 去 npmjs.com 搜正确拼法；② 官方仓验证 npm view 包名；③ 换回官方源重试（见 17.2 病例一）
EACCES permission deniedLinux/macOS 全局安装没权限写系统目录根治：改装 nvm（全局包进自己家目录，永无权限问题）；应急：sudo 只用于 -g 安装（治标）

读报错的姿势npm 报错动辄几十行，从上往下找三样：① code（错误代码，本表的挂墙号）；② while 字样那行（出事时在干什么）；③ errno（底层错误号）。中间大片 debug 日志 99% 是噪音——别从头读起，会被吓到放弃。

17.2 三个病例详解

病例一：E404 —— 「这货不存在」

通用命令行：破案三连
npm view loadsh              # 「loadsh」是拼错的 lodash——view 也报 404，证明商城压根没这号货
npm config get registry     # 查当前提货点：若是镜像站，可能是「官方已发布、镜像还没来得及同步」（新包发布后几分钟内的常见现象）
npm install lodash --registry=https://registry.npmjs.org   # 临时走官方仓装一次，绕过镜像延迟

病例二：JSON 改坏了 —— 一个逗号引发的血案

通用命令行
node -e "require('./package.json')"   # 借 Node 的 JSON 解析器给 package.json 做心电图：坏了会精确报出「第几行第几列 Unexpected token」——拎着坐标去改
npm pkg fix                 # 命令 pkg fix：npm 自带的清单修复器——能修常见的格式小伤（顺序、空白），修不了少逗号（那要人眼）

病例三：ELIFECYCLE —— 甩锅放大器

ELIFECYCLE 只是快递员告诉你「包裹里的东西碎了」——碎因在包裹本身。破案法：把报错里那句「> 命令名」下面的真实命令抠出来手动裸跑：

通用命令行
npm run build                # 报 ELIFECYCLE？记下报错幕布上的实际命令（比如是 vite build）
npx vite build               # 手动裸跑同一命令——vite 自己的报错立刻现形（多半是代码语法错、缺文件、端口占用）
                             # 修好真凶，npm run build 自然痊愈——npm 只是无辜的传令兵

17.3 万能起手式：三分钟自检流

通用命令行：顺序执行，多数怪病止步于第二步
npm doctor                   # 第一步：全面体检（网络、缓存、权限、Node 版本一目了然）
npm ls --all                 # 第二步：对照台账——看有没缺货、幽灵依赖（npm ls 会把「UNMET」「invalid」标出来）
rm -rf node_modules && npm ci   # 第三步：删仓库 + 照小票精确复原（Windows PowerShell 用：Remove-Item -Recurse -Force node_modules）
                             # 「货架可随时重建」——这一招是 npm 世界的重启大法

  2. 故意在 package.json 里删一个逗号跑 npm install，再用病例二的方法定位坐标；
  3. 把三分钟自检流完整跑一遍（在能正常工作的项目上），熟悉「重启大法」的手感。

最佳实践与速查表

十条军规保平安，四张速查表管全年——从入门到熟练的最后一站

最后一章是两样东西：军规（新项目开工前扫一眼）和速查表（忘了命令时直奔这里）。

18.1 十条军规

  1. 清单必进 Git，仓库绝不进——package.json + package-lock.json 提交，node_modules 写进 .gitignore；
  2. 部署用 npm ci，开发才 install——服务器要的是「一字不差」，不是「范围内最新」；
  3. 装必记账——代码里 import 的每个包都必须出现在 package.json 里（防幽灵依赖暴雷）；
  4. 生产依赖不加帽子也行，但心里要有帽子——读懂 ^ 和 ~（第 6 章），跨大版本升级前必读迁移指南；
  5. 能项目级，就不全局——全局只留真正全机通用的 CLI 工具；
  6. 用 npx 试用，用 scripts 日常——一次性工具 npx 租用，常用命令接进开关面板；
  7. 发布三查——查名字、查版本递增、查 npm pack --dry-run 清单（别把密钥发上去）；
  8. 换机器先想 .npmrc——镜像、代理、精确版本偏好都在配置里，项目级配置随仓库走；
  9. 定期 audit——本地月检，CI 每次构建必检；高危漏洞不过夜；
  10. 怪病先重启——删 node_modules + npm ci，九成灵异依赖一招治愈，别急着网上乱试偏方。
